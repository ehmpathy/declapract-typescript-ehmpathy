# deliver: #580 — the expo workflows honor a caller↔callee contract every callee declares

## what shipped

the `cicd-app-react-native-expo` templates now pass a caller↔callee reusable-workflow contract that
reconciles, and adopt the same oidc posture the `cicd-service` templates already declare go-forward:

- **`test.yml`** (the caller into `.test.yml`) — passes only the inputs `.test.yml` declares
  (`creds-aws-region`, `creds-aws-role-arn`) and `secrets: inherit`. it authenticates via the prep
  oidc role `${{ vars.CREDS_CICD_AWS_PREP_OIDC_ROLE_ARN }}` — the same role the deploy prep job uses,
  now that `deployment: false` (#578) removes the timeline-noise reason the prep arn was ever
  hardcoded elsewhere.
- **`.deploy-expo.yml`** (the callee) — its `github-environment` input is now **optional** (dropped
  `required: true`). expo has no plan phase, so it keeps ONE `creds-aws-role-arn` per env — no
  `-plan`/`-apply` split. the input stays singular `github-environment`, never `github-environment-apply`.
- **`deploy.yml`** (the caller into `.deploy-expo.yml`) — adopts the verified cicd-service prep/prod
  posture:
  - **prep job** OMITS `github-environment` and uses `${{ vars.CREDS_CICD_AWS_PREP_OIDC_ROLE_ARN }}`.
    the prep oidc role is repo-scoped (trusts any branch, no env claim), so an env claim would break
    oidc — this is why cicd-service's prep also omits it.
  - **prod job** uses `github-environment: production-on-main` + the prod-apply role
    `${{ vars.CREDS_CICD_AWS_PROD_OIDC_APPLY_ROLE_ARN }}`. `production-on-main` is the go-forward prod
    env name across cicd-service; every consumer adheres (no back-compat — they'll be bumped).

## why this is a real defect, not a hypothetical

a `job.uses: ./.github/workflows/<x>` call passes `with:`/`secrets:` that github validates against the
callee's `on.workflow_call.inputs`/`secrets` **only at run time** — an undeclared input errors, an
absent required input errors, and no gate sees either before the workflow runs. no `tsc`, no formatter
reads a yaml key mismatch. this is the wish's meta-lesson exactly: **a caller that emits a value
(a `with:` key) cannot verify its own output.** #580 is one instance; the whole
caller-without-callee class (#573 · D28/D29/D31/D52) is the same silent break.

## the durable guard — `src/workflowCallerCalleeReconciliation.declapract.integration.test.ts`

this is #573's explicitly-declared durable guard — *"reconcile every `uses:` against the callee's
declared `inputs:`/`secrets:`"* — realized as a clamp, built under #580 because #580 is the first
row it catches.

it walks every workflow TEMPLATE under `src/practices/**/.github/workflows/*.yml` (skips
`.test`/`__snapshots__`/`node_modules`), indexes the CALLEES (a template that declares
`on.workflow_call`) by BASENAME, collects every CALLER ref (a job whose `uses:` targets a local
`./.github/workflows/<x>`), and reconciles:

- **(anti-vacuity)** the walk reaches templates, callees, and caller refs
- **(b)** a basename that maps to >1 callee has identical declared contracts (resolution is unambiguous)
- **(c)** every caller ref resolves to a declared callee
- **(d)** no caller passes an input the callee does not declare — **the #580 break**
- **(e)** every required, un-defaulted input the callee marks is supplied
- **(f)** an explicit-`secrets:` caller passes no extra and omits no required secret (a `secrets: inherit`
  caller forwards all, so it is skipped)

### two YAML-parse edges the guard handles (documented in its header)

1. the `on:` key — under YAML 1.2 core `on:` is the string key `'on'`; a 1.1-mode parser folds it to
   the boolean key `true`. the guard reads both.
2. `workflow_call:` with an empty value parses to `null` — that file IS still a callee (e.g.
   `.publish-npm.yml`), so key-presence, not value-truthiness, decides. **this exact edge red-flagged
   `.publish-npm.yml` as "unresolved" on the guard's first run — a parser bug in the guard, not a
   workflow defect — and the repair is what made the guard sound.**

integration-classified by the same rule as `actionPins` / `workflowEnvDeploymentFalse`: it walks the
filesystem (`readFileSync` over every template), so `rule.forbid.unit.remote-boundaries` puts it in the
integration suite. no credential, no network.
