# 🌙 dream: git.release reads a stale check set as green; git.commit.push splits the pr number

- kind: reseed
- owner: ehmpathy/rhachet-roles-ehmpathy, role mechanic (git.release, git.commit.push)
- caught 2026-11-23

## .the cue that fired

on pr #839 of declapract-typescript-ehmpathy, `rhx git.release --watch` printed `👌 all checks passed` and `✨ done! 0s in action` while `gh pr checks 839` showed `suite / test-acceptance-locally fail`. the same pr, opened via `rhx git.commit.push --mode apply --auth as-human`, printed `pr: pr #839` then a stray `1` on the next line, and its watch refused: `--which must be a pr number; got '839\n1'`.

## .the gap, precisely

1. git.release reads a check set that omits a failed job from the prior push run, or reads it before the new run registers; either way it reports green over a red required check. a false green is the worst failure a release gate can emit.
2. git.commit.push captures the pr number from a command whose stdout holds two lines (the number, then a count or status), and passes both into `git.pull.watch set --which`.

## .the shape of the fix

1. git.release: read the full `gh pr checks` set for the head sha; treat any `fail` as red, any `pending` as inflight; never report green while a check on the head sha is absent or red. clamp: a fixture pr whose head sha holds one failed job.
2. git.commit.push: take only the first line (or `--jq .number`) of the pr lookup; clamp on the two-line stdout.

## .why it is not done in this round

both skills live in another repo; this pr verified ci by `gh pr checks` directly.
