# case=2 — the upgrade pr merges unstranded, and main applies green in one run (e2, e3)

## .narrative
ahbode/svc-images takes the upgrade. on 0.50.0 its pr read 19 green, approved, and `BLOCKED`: protection still wanted `test-commits`, and the workflow now reported `suite / test-commits`. then, after a manual protection edit and a merge, `github / apply` failed `plan is stale`, since github created `production-on-main` the moment the apply job named it, between the plan read and the apply.

after this release, the workflow adds one job, `test-passed`, that needs the whole suite. the inner checks keep their names in this release, so the old protection (`suite / test-*`) still sees every name it wants, and the pr merges. on main, `github / plan` runs in `production-on-main`, the same environment as `github / apply`, so github has created it before the plan reads it; the plan and the apply agree, and the apply lands green. that apply moves protection to `test-passed` + `pullreq-title`. from then on, a job rename never touches protection again.

the reviewer never edits protection by hand.

## .timeline
```
given('an adopter whose protection requires suite / test-*, upgraded to this release')
  when('[t0] the upgrade pr runs ci')
    then('every suite / test-* check reports')
    then('test-passed reports, and passes only if no suite job failed or was cancelled')
    then('the pr is mergeable once approved')
  when('[t1] the pr merges; provision runs on main')
    then('github / plan runs in production-on-main')
    then('github / apply runs in production-on-main and passes on the first run')
    then('protection now requires test-passed and pullreq-title')
  when('[t2] a later release renames an inner job')
    then('the next upgrade pr is mergeable with no protection change')

given('an adopter still on the pre-suite names (test-commits, ...)')
  when('[t0] the upgrade pr runs ci')
    then('the pr body and the issue reply name the one command to apply the github wish before merge')
```
