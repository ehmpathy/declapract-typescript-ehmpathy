# 1.vision — typescript 7 probe

## what this builds, and why it works

typescript 7 is no new tool to adopt. since 2026-07-08 it is the stable `typescript` package (latest `7.0.2`), and it still runs as `tsc`. so the probe swaps no binary. it is a version bump plus a tsconfig migration. our compiler footprint is small: `test:types` (`tsc --noEmit`) and `build:compile:tsc` (`tsc` + `tsc-alias`). jest transforms through `@swc/jest`, configs load through `esbuild-register`, declapract runs `.ts` through `tsx`, and node lint is biome. none of them import the compiler api, which 7.0 lacks until 7.1.

the work:

1. **migrate the node tsconfig to a shape valid on both 5.4.5 and 7.0.2.** drop `baseUrl` (removed in 7.0); give each `paths` entry a `./` prefix instead. drop `importsNotUsedAsValues` (deprecated in 5.0, still accepted by 5.5.4 and 5.9.3, rejected by 7.0 with TS5023; `remove` is the default elision anyway; F3). declare `"types": ["node", "jest"]`, since 6.0+ default `types` to `[]`.
2. **measure on this repo, one command, one tsconfig, four rungs** (F1, F4):
   `rm -f tsconfig.tsbuildinfo && /usr/bin/time -v npx tsc -p ./tsconfig.json --noEmit --incremental false --extendedDiagnostics`
   rungs `5.4.5` (today's pin) · `6.0.3` (lists deprecations by code) · `7.0.2` · `7.0.2 --singleThreaded`. one warm-up, then five cold runs per rung. report the median wall, cpu (user + sys), and peak rss, each with its min–max spread. rungs whose wall spreads overlap read "within noise", never a ratio. under ts7, cpu may exceed wall: parallel checkers spend cores to save seconds. the single-thread row separates the native gain from the parallel gain.
   the table names the machine: cpu model and core count. ts7's parallel checkers scale with cores, so a ratio means naught without them. the `--singleThreaded` row is the floor a 1-core runner would see.
3. **list every break and every behavior change** the rungs surface:
   - type errors: error code · option or construct · fix · fix valid on 5.4.5
   - emit: this repo builds via `declapract compile`, not `tsc`, so emit and the `tsc-alias` seam are read in the consumer repo `rhx declapract.walk --usecase lambda-service` builds from the practice templates. build `dist/` there under 5.4.5 and under 7.0.2, then diff the two trees, and grep for unrewritten `@src/` (case=7). each emitted-js difference is a behavior change, listed with whether it can change runtime.
4. **if it holds (F5), ship it as practice.** raise `typescript` to `7.0.2` in **typescript-node** (F2), not typescript-any. migrate the typescript-node tsconfig. add bad-practice `tsconfig-options-removed-in-ts7`, which strips `baseUrl` / `importsNotUsedAsValues`. as built it carries no manual part: the best-practice already sets `moduleResolution` to `node16` (F7, Q3). **every node adopter needs it, not only drifted ones.** today's practice ships `baseUrl` and `importsNotUsedAsValues` itself, and a `CONTAINS` fix adds keys but never deletes one. it follows the extant `legacy-tsconfig-lib` shape: a jsonc text edit that keeps adopter comments. typescript-any keeps its floor, so expo repos see no change.
5. **if it does not hold**, the pr carries the table and the wall, with no `src/practices/` change (case=2).

why it works: microsoft states that code clean on 6.0, with no `ignoreDeprecations`, compiles the same on 7.0. the 6.0.3 rung turns that promise into our break list before 7.0.2 runs. one tsconfig across all rungs leaves the compiler as the only variable.

## the outcome world

- **before**: `test:types` runs in every `npm run test` and every ci run, on typescript 5.4.x. the practice's floor is `5.4.5`, and its own tsconfig carries two options typescript 7 rejects: `importsNotUsedAsValues` (TS5023) and `baseUrl` (TS5102). 5.5.4 and 5.9.3 still accept both (read in execution), so the wall sits at 7.0, not 5.5. adopters sit two majors back.
- **after, if it holds**: `test:types` on a node repo runs at the measured ratio of its old wall time. the tsconfig holds only options typescript 7 accepts. an adopter got there via one reviewed `declapract` diff.
- **aha**: the speedup comes as a measured ratio with its command beside it. each break comes with its fix.

## mental model

- to a friend: "same `tsc`, rewritten in go. our typecheck got Nx faster; we deleted two dead tsconfig lines."
- analogy: a new engine in the same chassis. same pedals (`tsc`, `tsconfig.json`), and a few retired gauges removed.
- their words vs ours: they say "tsgo", "the go compiler", "native typescript". we say **typescript 7** and **`tsc`**. `tsgo` named the preview-only binary, now frozen at `7.0.0-dev.20260707.2`.

## evaluation

- **pros**: faster typecheck with no source change; tsconfig cleaned of options typescript removed; migrated tsconfig valid on 5.4.5, so the rollout tolerates a half-upgraded repo.
- **cons**: node and expo floors split for now (dream caught: `dreams/v2026_11_20.feat.expo-typescript-7-floor.md`). a small repo may understate the ratio (F1). no compiler api until 7.1, so any future tool that needs one must side-load `typescript6`.
- **edgecases + pit of success**:
  - drifted tsconfig → bad-practice folds it at `apply` (case=4, F7)
  - expo repo → floor never reaches it (forbidden row 15)
  - conformant repo with today's `baseUrl` + `importsNotUsedAsValues` → the bad-practice strips both; a `CONTAINS` fix alone would leave them (case=3)
  - unrewritten `@src/*` in `dist/` → the grep fails the probe before any practice ships (forbidden row 17, case=7)
  - half-upgraded repo (new tsconfig, old typescript) → still green, because each fix is valid on 5.4.5
  - `incremental: true` leaves a `.tsbuildinfo` that would fake a warm read → the probe deletes it and passes `--incremental false`

## open questions & assumptions

- **Q1 [wisher]**: the "holds" bar (F5). is a minimum speedup ratio wanted, or is "not slower + every break fixable" enough? the probe's measurements are the same either way; only the pr shape (case=1 vs case=2) turns on it.
- **Q2 [research]**: does `tsc-alias@1.9.x` rewrite `@src/*` imports when `paths` has no `baseUrl`? partial read: its config builder defaults the key (`const { baseUrl = '', … }` in `src/helpers/config-builder.ts`), so `paths` should map from the tsconfig's own dir. likely holds; the walked consumer's `dist/` grep proves it (case=7).
- **Q3 [answered]**: `moduleResolution node` → `node16` is no safe automatic fold. `node16` honors package `exports` maps, so a deep import that a package does not export breaks. as built, no repo meets it: the best-practice's contains-fix sets `node16` over any prior value, drifted or conformant, so the bad-practice needs no manual flag (F7; integration [case2] proves it on a `node` drift).
- **Q5 [research]**: an explicit `"types": ["node", "jest"]` stops auto-load of every other `@types/*` that declares globals (module imports still find their `@types`). typescript 6+ defaults `types` to `[]`, so every ts7 adopter meets this either way; the list only names it. does any practice template, or a common adopter dep, lean on a global-only `@types` package? the walked consumer's `tsc` run answers for the templates.
- **Q4 [research]**: does 7.0's `tsc` accept `--extendedDiagnostics` and `--incremental false` on the cli? if not, drop the flag; `/usr/bin/time -v` alone reads wall, cpu, and rss the same way on every rung.
- **Q7 [answered]**: does the practice change reach this repo itself? yes. `declapract.use.yml` sets `useCase: npm-package` with `declarations: ./`, and npm-package extends typescript-project, which carries typescript-node. so after the practice change, `rhx declapract.self.apply` lands it here too: `typescript` → 7.0.2, tsconfig stripped. ci's `test:types` then runs on ts7, which makes "green on ci" a true ts7 gate. on a `fails` verdict there is no practice change, so this repo stays on 5.4.5.
- **Q6 [answered]**: do `@tsconfig/strictest@2.0.5` and `@tsconfig/node20` set any option 7.0 removed? no. read from `node_modules/@tsconfig/*/tsconfig.json`: `@tsconfig/strictest@2.0.5` and `@tsconfig/node20` set no option 7.0 removed (read from `node_modules/@tsconfig/*/tsconfig.json`). `strictest` sets `checkJs: true`; it stays inert while `include` matches only `**/*.ts`, so 7.0's js-check differences do not apply.
- **assumption [wisher]**: this repo's typecheck scope (220 `src/**/*.declapract.ts` outside dot-dirs, 267 with them) is a fair stand-in for a consumer (F1). a larger repo would add a table row, no practice change; say so if one is wanted.
- **assumption [research]**: typescript-any and typescript-node both declare a `typescript` `minVersion` and still converge (F2). `rhx declapract.walk` proves it.

## groundwork

### external research
- typescript 7.0 stable 2026-07-08; ships as `typescript`, runs as `tsc`; no api until 7.1; `--singleThreaded`, `--checkers` flags; 6.0-clean ⇒ 7.0-same; `baseUrl`, `target es5`, `downlevelIteration` removed — [typescript 7.0 release post](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- npm dist-tags read 2026-11-20: `latest 7.0.2`, `beta 7.1.0-beta`, `rc 7.0.1-rc` — `npm view typescript dist-tags`
- 6.0 default changes (`types: []`, `rootDir: .`, `strict: true`, `module: esnext`) and deprecations removed in 7.0 — [typescript 6.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html); `moduleResolution node10` — [microsoft/TypeScript#62200](https://github.com/microsoft/TypeScript/issues/62200)
- `importsNotUsedAsValues` deprecated in 5.0 (the notes slate its removal for 5.5, but 5.5.4 and 5.9.3 still accept it; 7.0 rejects it with TS5023); `verbatimModuleSyntax` errors on esm `import` that would emit as `require` — [typescript 5.0 release notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-5-0.html)
- expo: no stable sdk supports ts7; `expo install --check` expects `~6.0.3` — [expo/expo#47627](https://github.com/expo/expo/issues/47627), [expo sdk 56 changelog](https://expo.dev/changelog/sdk-56)
- `tsc-alias` config builder defaults `baseUrl` to `''` — [src/helpers/config-builder.ts](https://raw.githubusercontent.com/justkey007/tsc-alias/master/src/helpers/config-builder.ts); its readme names no `baseUrl` requirement — `rhx get.package.docs readme --of tsc-alias`
- `tsc-alias@1.9.10` deps hold no `typescript` (it reads tsconfig via `get-tsconfig`); `declapract@0.13.27` deps hold no `typescript` (it runs `tsx`) — `npm view <pkg> dependencies`

## what is awkward?

- the floor splits by runtime for now. typescript-any calls itself the shared half, yet the typescript version it shares stays behind. this is a pragmatic tear, caught as a dream.
- a probe on the practice library measures a repo whose code is declarations, not services. it is honest but may undersell the ratio.
- the bad-practice catches only options we know of today. a future removal needs a new row.
