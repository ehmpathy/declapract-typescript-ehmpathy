## .the gap, precisely

the mechanic role has no rule on WHERE a file's namesake export sits. `rule.require.sync-filename-opname`
fixes WHICH export is the namesake (filename === operation name); no rule fixes its POSITION. so a
file may declare its leaf operations first and its orchestrator last — the reader meets the leaves
before the tree, and must scroll to the bottom to learn what the file does.

measured exemplar (before this round's fix-forward): `src/practices/tests-node/best-practice/useInfraWake.ts`
declared `export const useInfraWake` at line 142, below six leaf operations. hoisted to the top this
round (26 tests + types green — every test is substring/behavioral, so declaration order carries no
correctness weight).

## .the shape of the fix

### the rule content to seed

```md
# rule.prefer.namesake-export-first

## .what

the file's namesake export — the `export const` / class / function whose name matches the filename
(`useInfraWake.ts` → `export const useInfraWake`) — is declared at the TOP of the file, above the
leaf operations it composes. imports stay above it as usual.

pairs with `rule.require.sync-filename-opname`: that rule fixes WHICH export is the namesake
(filename === operation name); this rule fixes WHERE it sits.

## .why

- a file then reads as a treestruct: you see the tree (the orchestrator) before its leaves (the
  transformers/communicators it composes)
- a reader opens a file to answer "what does this do?" — the namesake export IS that answer. to bury
  it under its leaves forces a scroll past implementation detail to reach intent
- mirrors `philosophy.transformer-orchestrator-separation`: orchestrators are sentences, leaves are
  vocabulary. you read the sentence first, then look up a word only if you need it
- runtime-safe always: `const` arrow functions are not hoisted, but the namesake references its
  leaves only inside its body, which runs at call time — after the module has fully loaded top to
  bottom. so top placement never hits a temporal-dead-zone

## .the test

"is the file's namesake export the first declaration a reader meets (below the imports)?"

- yes → tree-before-leaves
- no → hoist it to the top; push the leaves below it, in the order the tree composes them

## .how

- declare `export const <namesake>` first (below imports)
- place the leaves it composes below it, in call order — a top-down narrative
- one export per file already holds (`rule.require.single-responsibility`), so the namesake is the
  file's sole export and its natural head

## .examples

### bad — leaves first, tree last (read bottom-up to find intent)

​```ts
const readConfigText = (...) => { ... };
const asReachesSharedClusterFromConfig = (...) => { ... };
const wakeSharedCluster = (...) => { ... };
// ...more leaves...
export const useInfraWake = async (...) => { /* the tree, at line 142 */ };
​```

### good — tree first, leaves below (read top-down)

​```ts
export const useInfraWake = async (...) => { /* the tree, up top */ };

const readConfigText = (...) => { ... };
const asReachesSharedClusterFromConfig = (...) => { ... };
const wakeSharedCluster = (...) => { ... };
​```

## .enforcement

- the file's namesake export declared below its leaf operations = nitpick (readability; declaration
  order carries no correctness weight, so per `rule.forbid.overzealous-blockers` this is a nitpick,
  never a blocker)

## .see also

- `rule.require.sync-filename-opname` — filename === the namesake operation (WHICH export)
- `rule.require.single-responsibility` — one export per file (so the namesake is the sole head)
- `philosophy.transformer-orchestrator-separation` — orchestrator (tree) composes leaves (vocabulary)
- `rule.require.narrative-flow` — read top-down as narrative
- `rule.forbid.overzealous-blockers` (bhrain/reviewer) — why this is a nitpick, not a blocker
```
