## .the ready-to-ship body

**title:** `🎙️ task - feat: coordinate dir-move + in-place rewrite of one file within a single apply`

---

## .what

when a single `declapract fix` (one `executeApply`) runs two fixes that both touch one file — a
**dir-move** bad-practice that relocates the file, and an **in-place rewrite** bad-practice that
edits it at its old path — the move unlinks the source and the rewrite then throws `ENOENT`
against the path that no longer exists.

declapract has no native coordination for this, so a consumer must hand-roll a **defer**: each
in-place rewriter gates its fix on a predicate that returns true while the file still sits under a
to-be-relocated dir, so the rewrite holds to the NEXT apply (a two-pass settle). the ask: let
declapract handle this upstream so a consumer does not carry apply-order knowledge in its own
practices.

## .the concrete case (declapract-typescript-ehmpathy)

two bad-practices legitimately target the same file in one apply:

- `directory-structure-src/old-*-dir` — RELOCATES `src/logic/foo.ts` → `src/domain.operations/foo.ts`
  (returns a new `relativeFilePath`, so declapract unlinks the source and writes the destination).
- `typescript-any/relative-imports` and `directory-structure-src/old-import-paths` — REWRITE
  imports in that same file at its OLD path.

apply both to one file in one pass → the move unlinks `src/logic/foo.ts`, then the rewrite
reads/writes `src/logic/foo.ts` → `ENOENT`.

## .the workaround we ship today

both in-place rewriters import ONE shared predicate and DEFER any file still under a deprecated
dir, so neither rewrites a file the same apply relocates. two passes settle it (pass 1 relocates,
pass 2 rewrites at the new path):

```ts
// defer a file still under a deprecated dir to its peer dir-move: the move
// relocates it this pass, then this rewrite fires at the new path next pass.
// the two never touch one file in one apply, so no relocate+rewrite ENOENT.
if (isDeferredToDeprecatedDirMove({ relativeFilePath: context?.relativeFilePath }))
  throw new Error('deferred to peer dir-move this pass');
```

(shared predicate = `src/utils/isDeferredToDeprecatedDirMove.ts`; one source for both declarers so
the guard cannot drift between them.)

## .why this belongs upstream

- it is **apply-engine order knowledge**, not practice knowledge. every consumer with both a
  dir-migration and an import-rewrite must re-derive the same defer coordination.
- it is fragile: two declarers must agree on the exact deprecated-dir set (we mitigate with a
  shared util, but that is a patch over an absent engine guarantee).
- it forces a consumer to author a fix that throws-to-skip on a file it genuinely wants to change —
  unexpected, and easy to get wrong.

## .possible upstream shapes

not prescriptive — any that removes the consumer-side defer:

1. **relocation-aware fix order.** within one apply, when a file is relocated, re-target any later
   in-place fix at the file's NEW path (apply to the moved contents, not the unlinked source).
2. **drive fixes to a fixed point automatically.** if apply already re-drives to convergence (see
   #104), a deferred rewrite lands on the engine's own next internal pass — no consumer defer guard
   needed.
3. **expose move intent in fix context.** give a fix's context a signal that this file is slated for
   relocation this pass, so a rewriter can react to the engine's plan instead of a repo-specific
   predicate.
