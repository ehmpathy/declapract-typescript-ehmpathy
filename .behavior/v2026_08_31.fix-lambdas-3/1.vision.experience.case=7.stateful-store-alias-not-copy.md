# case=7 — stateful-store-alias-not-copy

**actor** operator · **feel** SHARP · **care** critipath · the split-brain the design documents as forbidden

> the `[t1]`-`[t3]` CNAME/cutover demos are illustrative sketches of a human-gated LIVE migration —
> declapract declares the go-forward and forgets the old, but the live re-point is a runbook step,
> not code this repo runs.
> the alias-not-copy rule has **no machine-enforced structural guard**, by design. a service repo's
> `provision/aws/resources.ts` declares ZERO rds clusters (`getResources` returns only SSM params),
> so the template holds no cluster for a `fix` to duplicate — and a count guard on "two or more
> clusters" would only ever fire on a state a conformant consumer cannot reach (its premise, "one
> cluster per repo," is wrong: it is ZERO per service repo). the safety rests on two load-bearers
> below: the pit-of-success (a CNAME alias is easier than standing up a second cluster) plus the
> runbook for the human-gated CNAME cutover.

## why this is a critipath, not an alterpath (a self-review correction)

r2 (`has-experience-coverage`) caught this: the wish's decision point 3 —
*"stateless double-publishes; stateful ALIASES, never copies"* — is a **load-bearing safety
invariant**, and its failure mode is catastrophic (a write to `-dev` and a read from `-prep` on two
independent stores = silent data divergence). care = freq × cost: freq is low (once per service,
per env), but cost is a data-integrity break with no loud signal. a rare-but-catastrophic operator
path with a **forbidden cell** behind it owes a fail-safe demo, not a table row. promoted from
itemized (row 7) to demoed critipath.

## narrative

vlad migrates `svc-gateway`'s RDS toward the `-prep` name. the tempting move — the one dual-publish
makes look normal — is "publish the store under both names, like the lambdas." for a **lambda** that
is safe duplication. for a **database** it is a disaster: two independent RDS clusters means a write
that lands on `-dev` is invisible to a read from `-prep`. split-brain, silent.

the documented rule warns him. RDS is already reached by an **opaque, access-keyed config host**
(`config.database.tunnel.lambda.host` = `databaseClusterHost.prep`), so the `-prep` name is added as
a **Route53 CNAME → the one extant endpoint**, not a second cluster. one store, two pointers. zero
data moved. the `-dev` and `-prep` names are two doors into the same room.

the aha: **a lambda under two names is two copies of code; a database under two names must be one
store with two pointers.** the design names the distinction so the operator cannot reach for the
lambda pattern on a stateful store by reflex.

## bdd

```
given svc-gateway's RDS, reached by an access-keyed config host
  and `config/prep.json:31` keys the host by `databaseClusterHost.prep`                        # ✅ read
  and `getDatabaseConnection.ts:42-52` connects via that host, no stage token                  # ✅ read

when [t0] vlad reaches for the lambda pattern (publish the store under both names)
  then the template offers ZERO clusters to duplicate — a second cluster is his to hand-author, against the runbook
  and the documented rule names the exact hazard (write-dev/read-prep split-brain)

when [t1] vlad adds the `-prep` name as a Route53 CNAME → the extant RDS endpoint
  then `svc-x-dev.db...` and `svc-x-prep.db...` both point at ONE cluster
  and zero rows are copied or moved
  and a write via either name lands in the same store (no split-brain possible)

when [t2] the config host is re-pointed from the `-dev` DNS to the `-prep` CNAME
  then the app reads `-prep` and reaches the same data it always had
  and the cutover is a DNS change, not a data migration

when [t3] the transition ends and the `-dev` CNAME is dropped
  then only `-prep` remains, one store, one name
  and no data operation was ever required to retire the old name
```

## the fail-safe

the sharp edge — a stateful split-brain — is held off by two load-bearers, and by the absence of any
template cluster to duplicate. the template declares ZERO rds clusters, so `[t0]`'s tempting move
(publish the store under both names) has no cluster to copy — a second cluster is the operator's to
hand-author against the runbook, never a state the `fix` produces. `[t1]`: the only sanctioned move
(alias). the pit-of-success is the first load-bearer: the easy, correct path (a CNAME, zero data
risk) is easier than the dangerous one (stand up a second cluster, migrate data, court divergence),
so the operator falls into the safe move by default. the runbook for the human-gated CNAME cutover is
the second — declapract declares the go-forward and forgets the old, but the live re-point is a
runbook step (the vision does not over-claim a one-command stateful migration).

## the SSM sibling (row 12, still itemized)

the SSM credential-name migration (`.dev.` → `.prep.`) shares this shape but stays itemized, not
demoed: its move is a **decrypt-reseed** (the param is write-only, so declastruct cannot copy the
value — a human decrypts `.dev.` and writes `.prep.`, then re-points the 3-way byte-identical join:
config reader · OIDC IAM ARN · declared name). it is sharp and human-gated, but it is a variation on
this same alias-not-copy principle rather than a distinct encounter — so one demo (this file) carries
the pattern, and the SSM specifics are itemized with their caveat.
