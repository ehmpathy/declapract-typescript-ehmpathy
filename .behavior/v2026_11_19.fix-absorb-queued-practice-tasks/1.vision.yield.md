# vision — absorb the queued practice tasks #781–#811

## .what this builds
one practice release that removes every defect an upgrade trips on twice: a ci red no consumer can fix, a check that can never pass, a hook that fails open, an ignore that lets host-local files into jest or depcheck. each fix names its issue. each task not fixed carries a one-line reason on its issue.

## .the outcome world

### before
six upgrades in one day. each one:
- reads `test:unit` green with zero suites matched (nheuron, #811), or red from a plugin's tests and a trashed `.snap` (#783, #799, #809)
- waits 809 s on `test:lint` that then fails on a plugin import (#800)
- opens a pr that is 19 green, approved, and `BLOCKED`, since protection wants check names the workflow no longer reports (#781, #782)
- merges after a hand edit, then fails `github / apply` with `plan is stale` (#785)
- trusts commit hooks that pass on a git fault, a grep fault, or a hook dropped from the index (#789, #802, #808, #810)
- loses a shard to the slow-test report when every suite in it skipped (#788.1)

### after
the upgrade lands; the local run reads green and means it; the pr merges with no hand edit; main applies in one run; a hook that cannot verify says so and stops. each sender pulls its task from the radio and reads its status: `DELIVERED` with the version, `CLAIMED` with what shipped and why the rest waits, or `QUEUED` with the reason it stays open.

### the aha
protection stops to name inner jobs. one gate, `test-passed`, needs the suite; protection requires the gate. the inner names keep their place this release, so the first upgrade merges under the old protection, and the post-merge apply moves protection to the gate. after that, every rename (#791, #801) is free. a fix for one deadlock retires the class.

## .mental model
- to a friend: "the upgrade stops to bite back. tests read only our code, hooks never wave a fault through, and the pr merges by itself."
- analogy: a recall batch. each car owner filed a defect; the maker fixes the part once, ships one service bulletin, and tells each owner whether their defect is in it.
- adopter words vs ours: "my tests ran the trash" = jest haste map over `.agent/.cache`; "the pr won't merge" = a stale required context; "the hook said I changed it" = an unguarded `hash-object`.

## .evaluation
- goals: every task triaged (the three tables); upgrade-trip defects first (first table); each fix names its issue (`#N` in the pr and the commit), and its radio status moves to `DELIVERED` once the version ships, since the sender reads the radio, not the issue's open state; none narrows a practice (jest and depcheck now run MORE of a repo's own code; protection checks the same jobs through one gate); one pr, one version
- pros: one cure per class, not per symptom (the gate retires every future rename deadlock; one `.agent/` rule governs jest and depcheck); every sharp path fails loud with its owner named
- cons: protection reads one gate, so a red points at `test-passed` first; the gate names each failed suite job in its log and summary, so the reader is one click from the cause. adopters still on the pre-`suite /` names (from before #257, 2025-12) still pay one hand apply, and their stranded pr gives no loud signal
- edge cases kept in the pit of success:
  - a repo with no acceptance: a skipped inner job counts as pass in the gate; a cancel or failure fails it (the roll-up through the reusable call is `[research]` below)
  - a suite under `.agent/repo=.this/`: runs; under a vendored role: never
  - a lock sourced by `sh`: `set -eu` leaks into the hooks sourced after it, which already set the same flags, so no later hook changes behavior
  - a repo with no `patches/`: the cache key stays what it is today, so no adopter's cache busts for naught

## .open questions & assumptions

### [answered]
- does a plan in the apply's environment see that environment extant? yes: github creates an environment the moment a workflow names it (docs below)
- can the yalc hook split "found" from "broken" on exit code? no: `yalc check` exits 1 on found references (`yalc/src/check.js:65-67`, after `console.info('Yalc dependencies found:', …)`), and an uncaught throw also exits 1. the hook splits on that stdout line
- may #794's connect retry cover a timeout? no: the template lambda timeout is 60 s (`serverless/best-practice/serverless.yml:26`); a retried 35 s timeout spends 70 s. retry fast faults only
- does a 35 s connect plus a 30 s query fit 60 s? not in the worst case (65 s). the worst case needs a full resume and a near-limit query in one call; a cluster fresh from a resume rarely serves a 25 s+ query. accepted, and named in the bound's note
- is cross-repo testdb eviction a per-repo misconfig? no: the template `config/test.json` declares 7821 for every rds repo (`persist-with-rds/best-practice/config/test.json:32`)
- can an adopter add a job the gate's `needs` would miss? no: `test.yml` is checked `EQUALS` (`test.yml.declapract.ts`) and fixed whole
- does protection move with no extra step after merge? yes: `.declastruct.yml` applies on main by default (`allow-apply` default `github.ref == 'refs/heads/main'`, line 36)
- where does the sender look? the radio, which carries `QUEUED | CLAIMED | DELIVERED` (`rhx radio.task.push --help`); case=5
- can the scans rely on `set -o pipefail`? no: `pre-commit` is `#!/bin/sh` (dash on ubuntu), and an older dash lacks it. the scans read grep's own exit status (2 = fault)
- does F5's poll need a wider token grant? no: repeated `actions/cache/restore` steps with `lookup-only: true` need none; a cache-api loop would need `actions: read` at six reusable callers' top-level workflows (F5)

### [research] — in execution, before release
- does a reusable-workflow call job's `needs.<id>.result` read `failure` when an inner job fails? the github contexts doc lists `success | failure | cancelled | skipped` and is silent on the roll-up; this repo's three failed `publish` runs each failed in `publish` itself, so the record does not answer. the gate rests on it: a roll-up to `success` would make the gate fail open. prove it with a run whose inner job fails, or key the gate on each inner job by name
- aurora resume times: the 35 s bound rests on #794's reads (prep's 19–30 s record; aws's ≥ 30 s after 24 h); not re-measured here, since a measure needs prep access this route does not hold

## .groundwork

### external research
- github: a workflow that names an absent environment creates it, per the github actions docs on deployment environments (fetched this round) — https://docs.github.com/en/actions/managing-workflow-runs-and-deployments/managing-deployments/managing-environments-for-deployment. this is #785's mechanism
- jest 30.2.0: `@jest/core/build/index.js:459` compiles `new RegExp(testPathIgnorePatterns.join('|'))`, so a negative lookahead (`(?!repo=\.this/)`) holds; `:1085` feeds the same patterns to obsolete-snapshot cleanup, so under the ignore a trashed `.snap` no longer reads as obsolete
- yalc 1.0.0-pre.53: `src/check.js:65-67` — see open questions
- github contexts doc (fetched this round): `needs.<id>.result` takes `success | failure | cancelled | skipped`; silent on how a reusable call rolls up — https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/accessing-contextual-information-about-workflow-runs
- depcheck 1.4.3: the rc file's `ignorePatterns` is read as-is (`dist/cli.js:106`, `opt.ignorePatterns`) and fed to the `ignore` package (`dist/index.js:113`), which honors `!` negation

## .what is awkward
- one gate hides which check failed at the protection layer; the reader clicks through once. the trade buys freedom from every future rename deadlock
- the pre-`suite /` adopters still pay one hand apply; no workflow change can report a name it no longer runs
- #811 and #788 split: part fixed, part open. the issue stays open for the tail, which a sender must read to see its fix landed
- the hook harness exercises `sh`-sourced bash files; the test must invoke them the way husky does, or it proves a shell nobody runs
