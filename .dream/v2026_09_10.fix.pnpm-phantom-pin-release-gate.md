# 🌙 dream: run the pnpm phantom-pin registry check as a pre-release CI gate

- kind  = fix (enhancement) — this repo (declapract-typescript-ehmpathy)
- owner = declapract-typescript-ehmpathy
- caught = 2026-09-10

## .the cue that fired

i037 r007 (arch-hazards-behavior) blocker.1: `src/practices/pnpm/.declapract.integration.test.ts`
[case3] shelled `npm view` against the live npm registry every run, so the CI suite's green became a
function of registry availability (`rule.forbid.behavior-hazards`). the round's REPAIR split the
check by grain: the local semver-shape assertion runs every build; the registry round-trip runs
off-CI only (author-time, where a human bumps the pin and the network is present), like
`useInfraWake`'s `if (process.env.CI) return`.

## .the gap, precisely

the REPAIR relocates the phantom-pin guard to a dev machine at pin-bump time. that is reliable AND at
the change's origin — but it fires only if the author runs the suite locally. an author who bumps
`packageManager` and pushes without a local run gets no phantom-pin catch anywhere: CI runs the shape
check (which a phantom pin passes — `pnpm@10.31.7` is valid semver, just never published).

evidence: the REPAIR's own `if (process.env.CI) return` at
`src/practices/pnpm/.declapract.integration.test.ts` [case3] second `then`, and the harm it guards
against (#576: a phantom pin 404s corepack in every consumer).

## .the shape of the fix

add a dedicated pre-release CI step that runs the phantom-pin check exactly once, where a live
registry read IS a sanctioned dependency (a release job, network present, not a per-PR unit gate):

- a small `scripts/*` or a `cicd-common` workflow step that reads the shipped `packageManager` pin
  and puts it to `npm view`, then fails the release (not a PR) when the pin is unpublished.
- OR promote the check to a `*.real.integration.test.ts` grain (the pattern
  `rule.forbid.integration.mocks` sanctions) wired into the release workflow only.
- then [case3]'s off-CI `then` can drop entirely — the release gate owns the network half.

## .why it is not done in this round

DIRTY + low-marginal-value, re-examined 2026-09-13 with skepticism and confirmed a deferral:

- the CLEAN half is ALREADY shipped — `[case3]`'s registry read runs at local `npm run test`
  (the `if (process.env.CI) return` skips CI only, so a local full-suite run DOES catch a phantom
  template pin). the gap is narrow: only an author who pushes with NO local run misses it.
- the harm is LOUD-at-consumer, not silent — a phantom pin 404s corepack on the consumer's very
  first `pnpm install`. so the pre-ship gate only catches it one hop earlier, it does not turn a
  silent break loud.
- the correct home is NOT a `cicd-common` template (that propagates a pnpm-template-specific check
  to every consumer, most of whom do not ship the pnpm best-practice). it is THIS repo's own
  release config — a design fork (a new release-workflow step vs a `*.real.integration.test.ts`
  grain wired into release) whose live-CI behavior this practice-fix round cannot exercise or verify.

⇒ the fix is a release-pipeline placement decision + unverifiable-against-live-CI, against a
loud-at-consumer harm — a genuine deferral, kept for a release-pipeline round.
