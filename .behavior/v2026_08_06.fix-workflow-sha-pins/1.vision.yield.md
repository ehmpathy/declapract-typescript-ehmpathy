# 1.vision — the declared practice emits SHA-pinned action refs

> ground verified live on **2026-08-06**. every claim below marked ✅ was measured with a command
> quoted beside it; claims marked 🟡 are inferred and named as such.

## the outcome world

### the before

it is 2026-08-07. a repo in the ehmpathy org pushes a commit. nine seconds later every job is red:

```
The action actions/checkout@v4 is not allowed in ehmpathy/<repo>
because all actions must be pinned to a full-length commit SHA
```

not one test ran. ✅ the failure lands at **action lookup**, before any step executes — measured in
`ehmpathy/declastruct-github` run `31102465417`, where the log reads `Getting action download info`
and then the error **0.4s later**, with every downstream job
`skipped`. the error names all offenders in a job at once:
`The actions actions/checkout@v4, actions/cache/restore@v4, actions/setup-node@v4, and
pnpm/action-setup@v4 are not allowed …`. the developer
opens `.github/workflows/`, finds 47 tag refs, and starts a hand-edit — with no way to know what
SHA `@v4` should be, and no way for a reviewer to check the ones they type.

this is not hypothetical for **this** repo. ✅ `gh api orgs/ehmpathy/actions/permissions` returns
`{"enabled_repositories":"all","allowed_actions":"all","sha_pinning_required":true}` right now.
✅ `gh run list` shows this repo's last CI run at **2026-07-30** — before the control went live. its
next push is the first one that dies.

### the after

the same developer runs the upgrade. the template rewrites their workflows, and every third-party
ref comes back as:

```yaml
- name: checkout
  uses: actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4
```

CI starts. the `# v4` tail says which version that SHA is, so the next reader is not down a
research hole. a fresh scaffold ships this way on day one and never meets the red.

### the "aha"

the click is not "we pinned some SHAs." it is:

> **the template is the only place that has to be right.** every repo that consumes it inherits the
> pin instead of derive it.

⚠️ note the population carefully — i got this wrong once. the wish's audit counted **91 repos with
workflows**, all of which will hard-fail. it did **not** count how many of those consume this
template, and neither did i: ✅ `gh search code` for `declapract.use.yml` in the org returned 0 both
with and without a `filename:` qualifier — a null result from the search index, not a fact about the
org. so the leverage is "every consumer, from one edit" — a shape claim. **the 91 is the size of the
problem, not the size of this fix's reach.**

and the sharper half, which only shows once you try to derive a pin by hand:

> **a SHA you type is a claim you cannot check. a SHA the practice ships has already been checked —
> once, here, with a clamp that keeps it checked.**

the groundwork below proves that second half is not rhetoric: the obvious one-line way to resolve
`@v4` to a SHA produces a **wrong** value for 2 of the 12 actions this template uses. a
hand-editor would have shipped it, and the reviewer would have had no way to see it.

## user experience

### the usecases

| who | goal | what they do |
|---|---|---|
| a repo already on the template, undrifted | "my CI died today" | run the upgrade; template-owned workflows come back pinned |
| a repo already on the template, **drifted** | same | ⚠️ the upgrade brings the pin **and** every other drift with it — see "what is awkward" #3 |
| a fresh scaffold | "start a repo that works" | pins are already there; never meets the failure |
| a repo with its own custom workflow | "which of my files are still unsafe?" | ⚠️ **no in-repo signal exists.** github's CI error names the exact action and file, at the moment it dies |
| a maintainer of this repo | "bump checkout to v5" | edit the pin, the clamp confirms consistency, one PR reaches every consumer |

⚠️ **row 4 is the one that changed when move 3 was dropped, and i had it wrong.** i wrote that
`declapract check` would name a consumer's own unpinned workflows. it cannot. ✅ read in source —
`evaluateProjectAgainstFileCheckDeclaration.js` L41-47 globs **`check.pathGlob`**, the path derived
from the *declared* file. a consumer file that no practice declares is never enumerated, never read,
never evaluated. declapract is not a repo scanner; it is a per-declaration comparator.

that capability was **exactly** what the dropped move 3 would have added (a glob-scoped declaration
over `.github/workflows/**`), and when i dropped the move i left four of its promises standing. they
are corrected here, in the contract block, in the timeline, and in the edge-case table.

### the contract they leverage

no new contract. the extant declapract one, unchanged:

```sh
npx declapract plan   # previews; compares template-owned files only — it cannot see a consumer's own workflow
npx declapract apply  # template-owned workflows come back pinned
```

⚠️ **the verbs are `plan` and `apply`, and i had written `fix` and `check`.** ✅ read from the CLI
itself — `contract/cli/invoke.js` registers exactly four commands: `plan`, `apply`, `validate`,
`compile`. no `fix`, no `check`, no `upgrade`. the descriptions map them: `plan` = *"plan and display
what actions need to be taken"*, `apply` = *"apply fixes to all files which have failed to adhere"*.

this is worth a caution rather than a silent correction, because the error is **inherited from this
repo's own prose** — several briefs say "`declapract fix`" as shorthand for the fix *operation*, and
i read that as the command name. the briefs name the concept; the CLI names the verb. anywhere below
that this document says "`declapract fix`" as a **concept** (the fix half of a declaration) it is
correct; as a **command** it is not, and those are corrected.

inputs: none added. outputs: the same workflow files, with `@<tag>` swapped for `@<40-hex> # <tag>`.

**that no-new-contract property is deliberate.** a consumer whose CI is dead today should not have
to learn a flag to get it back.

## mental model

### how a user describes it to a friend

> "github stopped letting us say `checkout@v4`, because a tag can be re-pointed at anything. now
> you have to name the exact commit. our template does that for us, and leaves a comment that says
> which version it was."

### the analogy

a tag is a **name on a mailbox**; a SHA is the **street address**. anyone can repaint a mailbox
name. the pin says: deliver to this address, and here is the name it wore when we wrote it down.

closer to home, the repo already speaks this language:
`rule.require.pinned-versions` — *"always pin dependency versions exactly … eliminates surprise
changes if dependencies ignore semver."* a github action is a dependency that this rule never
reached, because it lives in yaml instead of `package.json`. this wish extends the extant rule to
the surface it always should have covered.

### their words vs ours

| they say | we say | why ours |
|---|---|---|
| "hash" / "hardcode the hash" | **pin** | matches `rule.require.pinned-versions`, already canon here |
| "version comment" | the **tag tail** | it is not a version; it is the tag the SHA wore at author time |
| "the template files" | **template** (a file copied to a consumer) | already a paved domain term with a paired opposite (`declaration`) |

⚠️ one term worth a flag: a reader will reach for "**version**" for the `# v4` tail. that is subtly
wrong and the wrongness matters — the tail records **which mutable tag this immutable SHA was
resolved from, on the day it was resolved**. it is provenance, not a version field. if the tag
later moves, the tail stays true about the past and turns false about the present. i will settle
whether that earns a glossary cluster at execution, not now.

## evaluation

### how well it serves the goals

| acceptance criterion | served by | confidence |
|---|---|---|
| a fresh scaffold's CI **starts** | templates ship pins; EQUALS check copies them verbatim | high — mechanism already proven for every other template |
| an upgrade pins template-owned refs, no hand-edit | `declapract apply` overwrites; ✅ verified **in declapract's source** for all 10 templates — see assumption 1 | high |
| the pin is **legible** | `@<sha> # <tag>` tail | high — this is github's own documented shape, and what declastruct-github shipped |
| the practice's own CI passes | this repo's 47 refs pinned too | high — and ⚠️ **not optional**, see below |
| coverage per grain | the templates are data, so the invariant is a **test**, not a code path | ⚠️ an **extension** of the rule, not a row in it — see below |

⚠️ **the fourth row is a delivery precondition, not a matter of principle.** ✅ this repo's
`publish.yml` declares `publish: needs: [test]`, and `test` is `./.github/workflows/.test.yml` —
which carries 24 unpinned refs. under the live control that workflow dies at action lookup, so
`publish` never runs and **the npm package cannot be released**.

so "the practice must not be exempt from the rule it teaches" is not the dogfood argument the wish
frames it as. it is the reason this fix can ship at all. that reorders the work: **this repo's own
47 refs must be pinned in the same change as the templates**, or the templates never reach a
consumer. (this reclassification **adds** a reason; it does not replace the wish's requirement.)

⚠️ **the last row is an extension of `rule.require.test-coverage-by-grain`, not an application of
it.** that rule's table has rows for transformer → unit, communicator → integration, orchestrator →
integration, contract → acceptance+snapshots. **a template is none of those grains** — it is inert
data, copied verbatim, with no call site to test. i had asserted "the invariant is a test" as though
the rule said so. it does not; it has no row for this. the extension i propose is: *data shipped to
consumers is covered by an invariant over the data.* i name it as an extension so a reviewer can
reject it as one.

### the shape i propose

three moves, smallest-first:

1. **pin the literals in the templates.** a template is copied to a consumer verbatim, so it cannot
   compute — the SHA has to be a literal in the file. ✅ **85 ref sites across 10 template
   workflows, 12 distinct action repos** — re-measured this round, per-file, and every figure holds
   exactly. ⚠️ but note the two file counts are different and both matter: **17** workflow templates
   exist; **10** of them carry a third-party ref (the other 7 are caller workflows with only local
   `./` refs). move 1 edits 10 files; move 2 walks all 17.
2. **clamp the invariant with a test, not a registry.** one test walks every
   `src/practices/**/.github/{workflows,actions}/**/*.yml` file and asserts:
   - every third-party `uses:` is a 40-hex SHA (not a tag, not a short SHA)
   - each carries a `# <tag>` tail
   - **any given action repo resolves to exactly one SHA across every template** — self-consistency,
     derived from the templates themselves

   ⚠️ that last assertion keys on the **repo** (`owner/repo`), not the full `uses:` path. ✅ measured
   this round: the 85 refs span **13 distinct `uses:` paths but only 12 distinct repos** —
   `actions/cache/restore` and `actions/cache/save` are two paths in **one** repo and must carry the
   same SHA. key it on the path and that pair passes trivially while a genuine drift between them
   goes unseen. one collapse out of thirteen is the entire margin the repo-key buys, and it is real.
   this catches the two regressions that actually happen: a new template lands with `@v4`, or two
   templates drift onto different SHAs of the same action.

   ⚠️ **one ref site already carries a comment, and the tail assertion must survive it.** ✅
   `.deploy-sls.yml:110` reads
   `uses: Entle/action-pagerduty-alert@0.2.0 # https://github.com/marketplace/actions/pagerduty-alert`
   — the only one of the 85 with a pre-extant trailing comment. a naive swap of `@0.2.0` for
   `@<sha> # 0.2.0` yields a line with **two** `#` marks. legal YAML, but the author must decide
   whether to keep the marketplace link, and the test's tail-parse must not read the URL as the tag.
   the pin's tail is a **prefix** of the comment, not the whole of it.

   ⚠️ **the `*.yml` bound is load-bearing, and i had it wrong.** my first phrasing walked
   `.../{workflows,actions}/**` — every file under those dirs. ✅ but that directory also holds
   `.declapract.ts` declarations, their `.declapract.test.ts` companions, and a `__snapshots__/`
   dir — and `__snapshots__/.test.yml.declapract.test.ts.snap` carries a literal
   `uses: actions/checkout@v4` at **L49 and L82** as synthetic fixture data. so the walk as first
   written would go **red on its own test fixtures**, on day one, before it ever caught a real
   defect. the hidden assumption was *"everything under `.github/workflows/` in a practice is a
   workflow template"* — false, and the `template` / `declaration` pair this repo already paved is
   exactly the distinction i failed to apply to my own test's scope.

   ✅ i also checked the inverse false-positive: **zero** `uses:` lines exist anywhere under a
   `bad-practices/` dir, so there is no legitimate-tag-ref exception to carve out beyond the
   fixtures.

   ⚠️ **this must be a static walk at unit grain, not an `executeApply` integration test.** ✅ the
   extant cross-practice test states its own cost: *"executeApply is slow (90+ seconds per
   invocation due to full practice evaluation)"* — and an invariant over 17 template files needs no
   pipeline at all. it reads files and asserts on strings.
3. **pin this repo's own 47 refs, in the same change.** not dogfood — a delivery precondition, per
   the note above: `publish` needs `test`, and `test` dies at action lookup until its refs are
   pinned. done as a targeted edit from the same SHA table, per F3.

**dropped: a detect-only bad-practice that chased tag refs in *consumer* workflows.** the wisher
settled the scope — this behavior fixes **this repo only**, and the other repos apply the practices
themselves. see F2 for the reasons. one of them should outlive the drop:

> ⚠️ ✅ **declapract source L52-54: a bad-practice declared with `FileCheckType.EXISTS` gets an
> implicit fix of `() => ({ contents: null })` — it DELETES the file.** that footgun is invisible
> from the declapract docs and would bite any future author who reaches for a "detect-only"
> bad-practice. out of scope now; it should not be un-learned.

**why no shared SHA registry constant.** the repo has a precedent for one —
`src/utils/defineExpectedGitignoreContents.ts`, imported by three declarers of one file. it does
not transfer. that util exists because three *declarations* (executable modules) must agree on a
computed result. here the artifacts are *templates* (copied files) which cannot import anything, so
a registry would be a **second** source of truth that restates what the templates already say, with
nothing to enforce the restatement but a test — and if a test can enforce agreement, it can enforce
agreement among the templates directly, and the registry buys nothing. `rule.prefer.wet-over-dry`
points the same way. i flag this as fulcrum F1, since a reader may expect the registry by analogy.

### pros

- **no new contract.** a consumer with dead CI runs the same upgrade they already run.
- **no codegen surface.** templates stay plain files; what you read is what a consumer receives.
- **the leverage is real.** one edit here reaches every consumer of the template. ⚠️ *how many* that
  is, i did not measure and do not need to — see the note under "the aha". the wish's 91 is the size
  of the org's problem, not a count of this fix's consumers.
- **provenance is checkable.** every SHA below is re-derivable with one documented command, and 5
  of them independently agree with what `declastruct-github` shipped — a cross-check neither of us
  could have faked.

### cons

- **it freezes consumers.** a hard pin defeats a malicious tag re-point and also stops an upstream
  CVE fix from ever reaching anyone. the wish records this and puts the automated-bump path out of
  scope; i concur and add a cost note under "open questions."
- **a bump is now 85 edits, not 10.** mitigated by `sedreplace` (one call per action) and by the
  self-consistency clamp, which goes red if a bump misses a site. still real friction.
- **the tag tail can go stale silently.** if `actions/checkout@v4` moves tomorrow, our `# v4` tail
  is still literally true (that is where the SHA came from) but no longer reads as "current".
  nothing in-repo can detect that without a network call.

### edge cases, and how the design keeps a user in the pit of success

| edge case | what keeps them safe |
|---|---|
| **an annotated tag** resolves to a tag-object SHA, not a commit — a silently broken pin | the resolution method must read `.object.type` and dereference; ✅ measured, 2 of 12 hit this |
| someone adds a new template workflow with `@v4` | the invariant test goes red on **shape**, before review |
| two templates drift onto different SHAs of one action | the self-consistency assertion goes red |
| a short SHA (7-hex) is typed | the 40-hex assertion goes red; 🟡 github likely rejects it too (the error text says *"full-length commit SHA"*) — inferred from the message, not measured |
| a consumer's **own** workflow still on tags | no silent rewrite — wish constraint 2 honored. ⚠️ and no in-repo warning either: ✅ declapract globs only declared paths (source, L41-47). github's CI error is their signal |
| local refs `./.github/workflows/*.yml` and `./.github/actions/*` | ✅ **exempt, proven directly** — see groundwork #5. the invariant test must not flag them |
| composite actions under `.github/actions/` | ✅ zero `uses:` today; the test scans them anyway so a future one cannot slip in |
| a ref line that **already** has a comment | ✅ exactly one exists (`.deploy-sls.yml:110`); the tail-parse must read the tag as the comment's **prefix**, not its whole |
| test fixtures that legitimately hold `@v4` | ✅ the `*.yml` walk bound excludes `__snapshots__/` and the `.declapract.*` companions beside them |

## open questions & assumptions

### assumptions made

1. **`declapract apply` on a workflow overwrites it wholesale.** ✅ **verified in declapract's own
   source**, not assumed — `node_modules/declapract/dist/domain.operations/declaration/
   readPracticeDeclarations/readPracticeDeclaration/getFileCheckDeclaration/
   getFileCheckDeclaration.js`:
   - L58-61 — no `.declapract.ts` companion + a template file present →
     `return FileCheckType.EQUALS; // default to "equals"`
   - L77-78 — `EQUALS` → check is `strictEqualsCheck`
   - L88-89 → L39-41 — `EQUALS` + `BEST_PRACTICE` → fix is `fixEqualsBySettingDeclaredContents`

   so all 10 templates land on strict-equality + whole-file overwrite: the 1 with an explicit
   companion by declaration, the 9 without by this default path. the pin propagates with **zero**
   new machinery.
2. **the org control does not reach local `./` refs.** ✅ **proven directly** — groundwork #5. this
   started as an inference from green CI and became a proof once i read the error text: the control
   named 1 of 3 refs in a job, and the same run shows it names *all* offenders it finds.
3. **`# <tag>` satisfies "legible"** — a reader can map SHA→version at a glance. matches github's
   own documented convention and what the wisher's cited exemplar shipped.

**3. the resolution method — and the trap it hides.** ⚠️ **this is the find that changes how
execution must work.**

the obvious one-liner is:

```sh
gh api -X GET repos/<owner>/<repo>/git/ref/tags/<tag> --jq .object.sha
```

it is **wrong for annotated tags**. for those, `.object.type` is `"tag"` and `.object.sha` is the
**tag object's** SHA — not a commit. measured:

```
gh api -X GET repos/pnpm/action-setup/git/ref/tags/v4 --jq .object
→ {"sha":"f40ffcd9367d9f12939873eb1018b921a783ffaa","type":"tag", ...}

gh api -X GET repos/pnpm/action-setup/commits/f40ffcd9367d9f12939873eb1018b921a783ffaa
→ 422 "No commit found for SHA: f40ffcd9..."      ← a pin that names nothing
```

the dereference gives the real commit:

```
gh api -X GET repos/pnpm/action-setup/git/tags/f40ffcd9... --jq .object
→ {"sha":"b906affcce14559ad1aafd4ab0e942779e9f58b1","type":"commit", ...}
```

**2 of 12** actions this template uses are annotated (`pnpm/action-setup@v4`,
`aws-actions/configure-aws-credentials@v4`) — a 17% wrong-answer rate for the naive method, and the
wrong answer is a plausible-looking 40-hex string that no reviewer could tell apart by eye.

so the method carries a mandatory second step: **read `.object.type`; if `tag`, dereference via
`git/tags/<sha>`.**

## what is awkward

**1. the deliverable is 85 near-identical string edits.** it does not feel like real work, and every
instinct says "extract it." the domain says no — a template is copied, not executed, so the literal
*is* the artifact. i am at peace with the conclusion and still find the shape uncomfortable, so i
name it rather than quietly reach for a generator.

**2. the tag tail is a comment, and comments do not have teeth.** the test can check the tail is
*present* and *self-consistent*, never that it is *true* about upstream. `# v4` beside a SHA that
`v4` no longer points at is a fully green, fully stale state. the honest bound: in-repo checks give
shape and consistency; only a network call gives truth, and a network call in CI trades one failure
mode for another (offline, rate limit). i propose we take the bound and record it.

**3. a security fix that would ship a security regression.** F3's discomfort is not the scope call —
it is that `declapract apply` has no grain finer than "the whole practice" (its `--practice` and
`--file` flags scope *which* declarations run, never *which part* of a declared file lands), so
"pin my refs", "adopt
test shards", and "drop `--ignore-scripts`" are the same command. my targeted-edit best-guess routes
around that rather than repairs it. the root cause is a declapract capability gap, which this wish
should not absorb, but a route-around does chafe against `rule.require.solve-at-cause`.

the sharper edge: **a repo cannot safely take a security fix from a practice it has drifted from.**
that is a property of the whole 91-repo fleet, not of this repo alone — and this wish's premise is
that those 91 repos will run exactly the upgrade i just declined to run here. i have no resolution
for that, and it is larger than this behavior. i would rather leave it named than tidy it away.

**4. we hand consumers a pin and no bump path.** the wish names this and scopes it out, and i agree
with the scope. it still means the honest sentence to a consumer is: *"your CI works again, and the
day one of these actions patches a CVE, nothing here will tell you."* the pin's hazard cures itself
as people touch repos; that one does not. it deserves to leave this behavior as a filed follow-on,
not just a paragraph.

**5. i reached past the wish's scope, and the wisher had to pull me back.** the wish said plainly
that the other repos are out of scope. i proposed move 3 anyway — a bad-practice whose entire job
was to chase refs in *other* repos' workflows — and rationalized it as "serves the wish's `.why` at
low cost." it was neither: it carried the sharpest hazard in the design (the implicit delete) for a
signal github already gives, better, at the moment of failure.

what makes this worth a note rather than a quiet edit: **it was the one move i invented rather than
derived.** moves 1 and 3-as-it-now-stands both fall out of the acceptance criteria. move 3 fell out
of my own sense that the outcome felt incomplete. the wisher's correction cost one sentence; the
tell was available to me a half-hour earlier, in a wish that already said it.
