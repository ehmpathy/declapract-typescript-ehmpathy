# case=1: the provision plan shows the review gate

feel: happy · care: critipath

## .narrative

a maintainer of `ehmpathy/sdk-aws-lambda` runs the fleet upgrade. `declapract apply` rewrites
`provision/github.repo/resources.ts` from the practice template, whole. the provision workflow's
plan job then reads that wish against github and prints one change on main's protection: the
review rule goes from absent to one approval. no other field moves. the commander reads the plan
and merges the upgrade pr; the provision workflow applies on push to main and sets it.

## .bdd sketch

```
given a repo whose main protection lacks a review rule (sdk-aws-lambda today)
  when [t0] `npx declapract apply` runs with the provision-github practice
    then resources.ts declares requiredPullRequestReviews.requiredApprovingReviewCount = 1
  when [t1] the upgrade pr's provision plan job runs (declastruct plan, production-on-else-plan)
    then the plan shows DeclaredGithubBranchProtection main: UPDATE
    then the only field diff is requiredPullRequestReviews: null → { count 1, dismissStale true, codeOwners false }
  when [t2] the commander merges the upgrade pr (out of this pr's scope)
    then provision.yml applies on push to main (production-on-main)
    then github's main protection requires one approval
    then the next pr into main is the first to wait for a review
```

## .proof

- `[t0]`: `src/practices/provision-github/main-review.declapract.integration.test.ts` runs the real
  `executeApply` against a demo repo that holds the prior template (review rule `null`): the block
  gains one approval, the variables stay filled, and a second apply is a fixed point. bites: the
  template's review block set back to `null` turns `[t1]` red
- `[t1]`–`[t2]` write to a real repo, which the wish bounds forbid; they rest on the clamp, github's
  documented branch protection, and the facebook/react control
