# fix-expo: give the `app-react-native-expo` usecase the global platform tools it lacks

## .what

the `app-react-native-expo` usecase in `src/useCases.yml` was hand-built as a flat practice
list with **no `extends`**, so it silently drops the cross-cutting "global platform tool"
practices that every other real dev repo gets via `typescript-project`. add the absent
global-platform practices to the expo usecase, and lift the pnpm-adoption lessons that
`ahbode/app-hometools-native` learned by hand up into the declapract templates, so future expo
repos get them for free.

## .why

- an expo repo is a first-class repo in our platform: it is MEANT to run the same tools as any
  other — rhachet agents, pnpm, the shared tool-scratch gitignores — even where a given repo has
  not adopted them yet (e.g. `app-protools-native` has no `.agent/` today, per the audit; this wish
  is what gives it the baseline, not a claim that expo repos already run it).
- `ahbode/app-hometools-native` proved the gap the hard way — it hand-wrote the entire pnpm
  migration (PR #55) because declapract's expo usecase never handed it those practices. the next
  expo repo (`ahbode/app-protools-native`) is about to pay the same tax unless we lift the
  lessons up now.
- a template lifted once serves every expo repo forever; a lesson left in one app's git history
  is re-derived by the next traveler (or drifts to a worse variant).

## .root cause

`app-react-native-expo` (src/useCases.yml:62-77) declares practices directly and does **not**
`extends: [typescript-project]`. so it inherits none of typescript-project's tool practices.
practices in `typescript-project` but absent from the expo usecase:

| practice | class | lift into expo? |
|----------|-------|-----------------|
| `rhachet` | global platform tool (agent roles, `.agent/.cache/` ignore) | ✅ yes — decided |
| `pnpm` | global platform tool (package manager) — **node-shaped** | ✅ yes, but as a `pnpm-expo` split (see below) |
| `cache` | global platform tool (generic `.cache/` tool-scratch ignore) | ✅ likely yes |
| `errors` | `helpful-errors` dep only (CONTAINS check) — **runtime-agnostic** | ✅ yes, as-is — zero toolchain conflict |
| `typescript` | node tsconfig + `tsc`/`tsc-alias` build — **node-shaped** | ⚠️ split needed — `typescript-expo` (see below) |
| `tests` | node `@swc/jest` config, `testEnvironment: node`, no jsx — **node-shaped** | ⚠️ split needed — `tests-expo` (see below) |
| `domain` | domain organization + `domain-objects`/`type-fns` deps — **runtime-agnostic** | ✅ yes, as-is — a domain choice, no build assumption |
| `directory-structure-src` | directional-deps architecture (`domain.objects`/`domain.operations`/`access`/`contract`) — **runtime-agnostic** | ✅ yes, as-is — a domain choice, no build assumption |
| `bottleneck` | runtime rate-limit lib | ❌ runtime lib, not a platform tool — exclude |

### the split axis: build/toolchain vs domain organization

evidence-backed 2026-08-06, sharpened. a practice needs a runtime variant ONLY when it encodes how
a repo **builds / bundles / runs** — because metro + EAS + jest-expo replace tsc + node-jest. a
practice that encodes how a repo **organizes its domain** is runtime-agnostic and drops into the
expo usecase as-is. the axis is build-vs-domain, NOT node-vs-expo broadly.

**runtime-agnostic → include as-is (NO variant):**
- **`errors`** — adds only the `helpful-errors` dep (`CONTAINS`); runs in rn / node / browser alike.
- **`domain`** — the `domain-objects` / `type-fns` deps + the domain-objects convention. a domain
  choice, not a build choice. an expo app has a domain like any app. include as-is.
- **`directory-structure-src`** — the directional-deps architecture
  (`domain.objects` ← `domain.operations` ← `access` ← `contract`). universal: `access` = the sdks
  it talks to, `domain.objects` = its domain, `contract` = its exposed interfaces. the `app/` +
  `components/` presentation layer sits ON TOP of this src/ logic; it does not replace it. as-is.

**build/toolchain-bound → MAY need a variant, but a variant is a LAST RESORT (see the fork rule):**
- **`pnpm`** — expo also needs the hoisted-linker `.npmrc` (flat `node_modules` for metro/native)
  atop the `packageManager` pin. FIRST try: one usecase-aware `pnpm` practice that adds the hoist
  patterns when the expo usecase is present. a fork is the fallback, not the plan.
- **`typescript`** — bundles a `tsc` + `tsc-alias` BUILD + a node16 tsconfig; an expo app extends
  `expo/tsconfig.base` and never builds with tsc (metro bundles, EAS builds native). FIRST try: one
  usecase-aware practice that swaps tsconfig/scripts by usecase. fork only if that proves untenable.
- **`tests`** — node `@swc/jest` config (`testEnvironment: node`, no jsx) vs the `jest-expo` preset.
  FIRST try: usecase-aware swap. fork only if untenable.

so the earlier "affirmed splits" are DOWNGRADED: none of pnpm/typescript/tests is a foregone fork.
each must first prove a single usecase-aware practice cannot serve both — per the rules below.

### the two fork rules — AUTHORED 2026-08-06

a fork raises two separate questions, so it is two briefs, NOT one (per
`rule.require.rule-directive-prefix` the directive fixes the severity, so a nitpick and a blocker
cannot share one file). both now live at `.agent/repo=.this/role=any/briefs/`:

- **`rule.avoid.runtime-forks`** (avoid → nitpick) — WHETHER to fork. default is one usecase-aware
  `<x>` practice (branch `contents`/`check` on `context.projectPractices`, as the `typescript`
  practice already does); a fork is the last resort. fires when a fork is proposed.
- **`rule.require.variant-family-triad`** (require → blocker) — HOW to name a JUSTIFIED fork: the
  `<x>-any` + `<x>-node` + `<x>-expo` triad, bare `<x>` retired. general to any split axis. fires on
  the artifact shape, only after the first rule settles toward a fork. rests on this repo's
  `sortable`/`ordered` "name the default" domain-terms lesson.

net: pnpm/typescript/tests are CANDIDATES to test against `rule.avoid.runtime-forks`, not confirmed
forks. the deliverable for each is a yes/no on "can one usecase-aware practice serve both?" — and
only a no triggers the triad.

## .the ask (bounded scope)

### 0. audit the WHOLE expo usecase — do not stop at the known gaps
the practices above surfaced from a `typescript-project` diff, but that diff only names what
node repos already have. an expo repo needs artifacts a node repo never does, and declapract may
declare NONE of them. before the wire-up, audit the full expo repo shape (use
`ahbode/app-hometools-native` + `app-protools-native` as the reference repos) and record what the
usecase should also cover:
- **expo toolchain configs** — `app.json` / `app.config.ts`, `metro.config.js`, `babel.config.js`,
  `eas.json`, `expo-env.d.ts`. are any of these worth a best-practice template?
- **expo lint/format** — is `lint-react` / `lint-react-native` current, and does it want
  `eslint-config-expo`?
- **expo test shape** — `jest-expo` preset, component tests, and any e2e (detox / maestro).
- **the `-expo` split family** — beyond `pnpm-expo`/`typescript-expo`/`tests-expo`, is there a
  `cicd-app-react-native-expo` gap (it holds only a `package.json` today — no `.deploy-expo.yml`,
  no `.npmrc`)?
- **what the current usecase gets WRONG**, not just what it lacks — e.g. does it pull a node-shaped
  practice that already fights expo today?

the deliverable of this step is a checklist appended to this wish: every artifact an expo repo
needs, mapped to include-as-is / `-expo`-split / net-new-practice / exclude. the wire-up (parts
1-3) then executes that checklist rather than only the practices named so far.

### 1. wire the absent global-platform practices into the expo usecase
- **include as-is** (runtime-agnostic — no fork): `rhachet`, `cache`, `errors`, `domain`,
  `directory-structure-src`. add each to `app-react-native-expo` in `src/useCases.yml`.
- **fork-candidates** (build-bound — test "can one usecase-aware practice serve both?" FIRST):
  `pnpm`, `typescript`, `tests`. only a proven-untenable one earns a `<x>-any`+`<x>-node`+`<x>-expo`
  triad; otherwise make the single practice usecase-aware. see the governing rule.
- confirm gitignore **convergence** still holds: `.gitignore` now has THREE declarers for an expo
  repo (`git`, `cicd-app-react-native-expo`, `rhachet` — the `cache` practice declares a package,
  NOT the gitignore; verified `src/practices/cache/best-practice/` holds only a `package.json`).
  all three route through the shared `src/utils/defineExpectedGitignoreContents.ts`, so they should
  converge — but this needs a cross-declarer clamp, not just a green per-declaration suite (per the
  #537 lesson).

### 2. lift the pnpm-for-expo lessons up into declapract (from ahbode/app-hometools-native PR #55)
the one artifact declapract does NOT yet have anywhere and is fully generalizable:
- **expo `.npmrc`** — a best-practice template that holds `node-linker=hoisted` +
  `public-hoist-pattern[]` for `*expo*`, `*react-native*`, `@react-native/*`, `metro*`,
  `*metro-*`. reason: react-native/expo/metro/EAS need a FLAT `node_modules`; pnpm's default
  symlinked store breaks native-module resolution. home for it: the
  `cicd-app-react-native-expo` practice (or a dedicated pnpm-expo practice).
- **`.deploy-expo.yml` pnpm setup** — the `cicd-app-react-native-expo/best-practice/` today
  holds only a `package.json`, no `.deploy-expo.yml`. the deploy-workflow pnpm setup
  (`pnpm/action-setup@v4`, `pnpm install --frozen-lockfile`, cache key on `pnpm-lock.yaml`) was
  NOT template-covered and is liftable — add it as a best-practice template and/or a bad-practice
  check for `npm ci` / `package-lock.json` cache keys in the expo deploy workflow.
- **`packageManager` pin gotcha** — `pnpm/action-setup@v4` fails "No pnpm version is specified"
  without `packageManager: pnpm@x` in package.json. the `pnpm` practice already pins this
  (`src/practices/pnpm/best-practice/package.json`); a `pnpm` add to the usecase covers it.
  confirm the check is `minVersion`, not exact (declapract pins 10.24.0; app used 10.32.1).
- **hoisted-linker transitive skew** — the flat layout lets mismatched transitive versions hoist
  over intended ones (e.g. `@commitlint/format` "is not a function", `type-fns` "Class extends
  value undefined", both pulled by `whodis-react`). the specific `overrides`/`resolutions` pins
  are repo-specific and NOT liftable as versions — but the *pattern* (hoisted linker exposes
  transitive skew; fix via `overrides`) deserves a documented gotcha brief in the expo practice.

### 3. transfer the lessons downstream to `ahbode/app-protools-native`
- **the transfer mechanism IS `declapract apply`.** once the lessons live in the practice,
  `app-protools-native` pulls them in through a normal apply of the `app-react-native-expo`
  usecase — no hand-diff, no manual migration. this is the whole point of the lift: the app
  repos stay thin and the practice carries the knowledge.
- what apply delivers to it automatically: the expo `.npmrc` hoist template, the `.deploy-expo.yml`
  pnpm setup, the `packageManager` pin (via the `pnpm` practice), the `package-lock.json`
  bad-practice removal, and the rhachet/cache gitignore lines — all as `declapract fix` output.
- so the success test for this wish is exactly: `app-protools-native` runs `declapract fix` and
  lands the full pnpm-for-expo shape with zero hand edits. the lift into declapract is the work;
  the downstream adoption is free.
- **the fixes must migrate GRACEFULLY, not clobber.** `app-protools-native` already has extant
  files (its own tsconfig, jest config, `.gitignore`, maybe an npm lockfile, maybe deprecated
  dirs). a practice that overwrites them with an EQUALS template destroys the repo's own work. so
  each fix is a bad-practice migration in the graceful mold: findsert/union (gitignore, `.npmrc`),
  forget-not-destroy (a stray `package-lock.json` removed only after `pnpm-lock.yaml` is in place),
  dir-rename (deprecated dirs moved, not deleted). every fix owes an idempotency + integration test
  (`rule.require.idempotent-fixes`, `rule.require.declapract-integration-tests`) proven against a
  clone of `app-protools-native`'s actual layout. the audit is DONE — the per-file migration-risk
  map is the appendix at the foot of this wish.

## .out of scope

  `directory-structure-src` are NO LONGER here — they are in as-is; see `.resolved`.)
- the repo-specific `overrides`/`resolutions` version pins from `app-hometools-native` (driven by
  its own dep tree, not generalizable).

## .resolved
- **`errors`?** (2026-08-06) — in as-is. runtime-agnostic dep, zero toolchain conflict.
- **`domain` / `directory-structure-src`?** (2026-08-06) — in **as-is**, NO fork. domain
  organization is universal, not a build choice: `access` = the sdks it talks to, `domain.objects`
  = its domain, `contract` = its exposed interfaces. the `app/`+`components/` layer sits on top of
  src/ logic, does not replace it. (corrected — an earlier draft wrongly called these service-only.)
- **a runtime fork is a LAST RESORT** (2026-08-06) — prefer one usecase-aware `<x>` practice
  (conditional on `context.projectPractices`) over a fork. see "the governing rule" above.
- **`<x>-any` vs `<x>` for the common half?** — `-any`, but ONLY inside a forced triad
  (`<x>-any` + `<x>-node` + `<x>-expo`); the bare `<x>` is retired there. a practice with no
  variants stays a bare `<x>`.
- **`typescript` / `tests` / `pnpm`?** — DOWNGRADED from "affirmed split" to "fork candidate." each
  must first fail the "can one usecase-aware practice serve both?" test before it earns a triad.
- **scope?** (2026-08-06) — **carry EVERYTHING in one pass.** this wish covers: the as-is includes
  (`rhachet`/`cache`/`errors`/`domain`/`directory-structure`), the fork-candidate evaluations
  (`pnpm`/`typescript`/`tests`, each driven to a verdict + whatever practice it earns), the lift of
  the pnpm-for-expo lessons, AND the graceful `app-protools-native` migrations proven end-to-end.
  no follow-on split. (part 0's audit may still surface more candidates — those ride along too.)

## .appendix — `app-protools-native` audit (2026-08-06, reference repo)

read-only audit of the live repo. it is the graceful-migration test case, and its state doubles as
the acceptance target for the whole wish.

**stance:** already on the target usecase (`declapract.use.yml` → `usecase: app-react-native-expo`),
but pinned to OLD practices (`declapract-typescript-ehmpathy: 0.36.1`, `declapract: 0.12.0`) — so a
declapract upgrade precedes any apply. still on **npm** (`package-lock.json`, no `packageManager`,
plain `.npmrc`). rhachet absent (`.agent/` does not exist). src/ on the DEPRECATED layer names
`src/logic/` (55 files) + `src/data/` (17, incl. `src/data/domain/`).

**already-correct — must NOT be clobbered (a naive EQUALS template would destroy real work):**
- `tsconfig.json` — already `extends: expo/tsconfig.base` with custom `@src`/`@assets` paths + a
  rheuse include. THIS is the proof that a node-shaped `typescript` practice clobbers a good expo
  tsconfig → merge/contains only, never EQUALS.
- `app.config.ts`, `metro.config.js`, `babel.config.js`, `eas.json`, `react-native.config.js` —
  expo-correct; leave as-is.

**per-file migration-risk map:**

| file | current | practice wants | risk | graceful shape |
|------|---------|----------------|------|----------------|
| `package.json` | npm scripts, `overrides`+`resolutions`, inline `jest` block | `packageManager: pnpm@x`, pnpm scripts, `pnpm.overrides` | clobber if EQUALS | contains-merge: add pin, `overrides`→`pnpm.overrides`, rewrite only npm→pnpm in scripts, keep expo/eas scripts |
| `package-lock.json` | present (npm) | absent; `pnpm-lock.yaml` instead | collide | forget-not-destroy: delete only after `pnpm-lock.yaml` exists |
| `.npmrc` | `save-exact` + `message` | + `node-linker=hoisted` + expo `public-hoist-pattern[]` | clobber if EQUALS | union: append hoist lines, keep extant two |
| `tsconfig.json` | expo base + custom paths | expo base | clobber if EQUALS | contains-only; treat extant as good |
| `jest.config.js` + `jest.unit.config.js` + inline `jest` block | jsdom config file + `jest-expo` preset inline — DUAL source | one home | collide | reconcile to one home, migrate settings, drop the redundant one |
| `.gitignore` | 41 lines, dupes, no rhachet `.agent/.cache/` line | 3-declarer converged shape (git/cicd-expo/rhachet) | collide | shared-algorithm merge (dedupe, add lines, keep expo entries) |
| `.husky/check.lockfile.sh` | greps `package-lock.json` | `pnpm-lock.yaml` | collide | string swap |
| `.github/workflows/.install.yml`, `.deploy-expo.yml` | `npm ci`, cache on `package-lock.json` | `pnpm install`, cache on `pnpm-lock.yaml` | clobber (safe target) | template swap, synced with lockfile move |
| `src/logic/**` (55) | deprecated layer | `src/domain.operations/` | collide | dir-rename move + import-path rewrite |
| `src/data/**` (17, incl `data/domain/`) | deprecated layer | `src/access/` + `src/domain.objects/` | collide | dir-rename/split move + import rewrite |
| `.agent/` + keyrack | absent | rhachet set up | clean | net-new drop |
| `expo-env.d.ts` | absent | present | clean | net-new / expo-generated |
| `declapract.use.yml` | already `app-react-native-expo` | same | clean | no change |

**the two heaviest surfaces:** (1) the npm→pnpm switch touches package.json + lockfile + `.npmrc` +
5 workflows + the husky lockfile check; (2) the `logic/`+`data/` → directional-layers move is
72 files with import rewrites. both are the exact migrations `howto.craft-practice-migrations` +
`rule.require.idempotent-fixes` exist for.
