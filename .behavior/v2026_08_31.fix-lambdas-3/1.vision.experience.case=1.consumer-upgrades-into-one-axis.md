## narrative

kai maintains `svc-home-services`, on the `lambda-service-with-rds` practice. today the upgrade
hands them a `serverless.yml` that remaps `accessByStage: { dev: prep }`, an `environment.ts` with a
dead `serviceClientStage`, and blackbox tests that call a `-prep-` fleet the deploy named `-dev-`.
they burned two days on it (PR #30).

after this wish, kai runs the same upgrade. the dead `serviceClientStage` is gone. the
`accessByStage` map now dual-publishes (`dev: prep`, `prep: prep`), so a cross-service call reaches a
peer under EITHER slug — no 404 while the org migrates. the new `sdkAwsLambdaEnvAccess{Ancient|Contemp}`
helper says exactly which slug a cross-call targets, and `grep AccessAncient` is the migration
ledger. in `environment.ts`, `stage` is gone entirely — the export is `access`, so app code cannot
name a slug that diverges from access. `stage` survives only inside the serverless adapter, pinned to
access. kai reads the diff and the divergence that cost two days is closed; the one-word serverless
DELETION is the flagged endpoint move, still ahead.

the aha: the silent divergence is closed by construction (dual-publish + an access-only app export),
and the ledger names every step left to the one-axis endpoint — kai is never stuck between names.

## the fail-safe

not a sharp case — the safety here is by construction, not a guard: the dual-publish remap makes a
cross-call reach a peer under either slug (no 404 between names), and the app export is `access` only,
so app code cannot name a divergent value. the divergent-stage GUARD that would forbid a re-split at
the serverless adapter is the endpoint move, council-gated — until it lands, the re-split defense is
the access-only export + the ledger, not an enforced blocker. stated plainly so a reader does not take
the endpoint guard as already-shipped.
