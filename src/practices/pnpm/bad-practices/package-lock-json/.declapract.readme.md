# bad-practice: package-lock-json

## .what

a `package-lock.json` (the npm lockfile) in a repo that has migrated to pnpm.

## .why it is bad

pnpm reads `pnpm-lock.yaml`, not `package-lock.json`. a stale npm lockfile left beside the pnpm one
is a dual source of truth for the dependency graph, and CI lockfile checks that grep the wrong file
pass or fail for the wrong reason.

## .the fix — forget-not-destroy

the fix removes `package-lock.json`, but ONLY once a `pnpm-lock.yaml` sits beside it. the delete is
gated on the pnpm lockfile's presence (read from the project root via
`context.getProjectRootDirectory()`), so a fix that runs on a repo that has not yet run
`pnpm install` is a no-op rather than a destructive strip that leaves the repo lockfile-less. this
is the wish's stated safety bar: *"package-lock.json is removed ONLY after pnpm-lock.yaml exists, so
a fix interrupted midway never leaves the repo lockfile-less."*

a bare `FileCheckType.EXISTS` would delegate to declapract's default fix, which deletes the file
UNCONDITIONALLY — so this practice declares its own gated `check`/`fix` instead.
