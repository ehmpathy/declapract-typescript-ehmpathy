# 1.vision: main requires one review approval

## .the change, in one line

the provision-github practice declares main's protection with
`requiredPullRequestReviews: null`. it will declare one approval instead:

```ts
requiredPullRequestReviews: {
  requiredApprovingReviewCount: 1, // a green pr still waits for one human approval
  dismissStaleReviews: true, // a push after approval drops it, so no commit merges unread
  requireCodeOwnerReviews: false, // the fleet carries no CODEOWNERS
},
```

that one field is the root cause of sdk-aws-lambda#79. every adopter inherits the protection
declaration whole (no `.declapract.ts` beside `resources.ts`, so the default EQUALS check holds).

## .the outcome world

**before.** seaturtle[bot] opens a pr, nine checks go green, and the bot merges it. no human
read it. sdk-aws-lambda#79 shipped this way: authored by `ehm-seaturtle`, merged by
`ehm-seaturtle`, zero reviews.

**after.** the same pr goes green and waits: `reviewDecision = REVIEW_REQUIRED`. github refuses
the merge, by hand or by automerge. a human reads the diff and approves; then it merges. the release pr waits the same way, so the prod gate
(`production-on-main`: "PR merge is the gate") gains a human.

**the aha.** the fleet already has a gate at merge (status checks) and calls the merge its prod
gate. a gate with no reader proves the code builds, not that anyone looked. one field turns
"green" into "green and read".

**how it lands.** this pr changes the practice only. a merge of it sets naught: this repo
provisions from its own `provision/github/declastruct.resources.ts`, not the template. once
released, an adopter's next `declapract apply` rewrites `provision/github.repo/resources.ts`; the
upgrade pr's provision plan job shows one field diff on main's protection. the shipped
`provision.yml` applies on push to main (`production-on-main`, no reviewer), so **the merge of
each adopter's upgrade pr is the act that sets the rule**. that merge is the commander's call, per
repo.

## .mental model

- a maintainer tells a friend: "main needs one approval now, even when ci is green."
- analogy: a second signature on a cheque. the bank (ci) checks the funds; a second person
  checks the payee.
- their words: "review required", "approve". ours: `requiredPullRequestReviews`,
  `reviewDecision`. the pr body uses theirs.

| goal | met? |

pros:
- one field, inherited fleet-wide by the extant upgrade path; no new practice, no new variable
- the plan diff is one field, so a commander reads exactly what changes

cons:
- every release pauses for an approval (F1)
- a pr open across a main merge needs a re-approval: strict forces the update, the update drops the approval (F2)
- a solo owner cannot merge a pr they authored by hand (case=5)

pit of success:
- `enforceAdmins: true` already holds, so no admin silently merges past the rule
- the census says `unknown`, never a guess, where no pr decides it

## .open questions & assumptions

### for the commander

- **[wisher] F1: exempt release-please prs?** lean: **no.** the release pr merge is the prod gate, and the
  review is cheap (a version bump and a changelog of reviewed commits). an exemption is not
  expressible today: declastruct-github 1.4.0 has no `bypass_pull_request_allowances` and no
  ruleset `pull_request` rule, and `enforceAdmins: true` closes the admin path. if you want it,
  the reseed dream names the upstream change first.
- **[wisher] F2: dismiss stale approvals?** lean: **yes.** the bot often pushes after an approval (nit
  fixes); with `false` that commit merges unread, the harm the wish targets. the cost is a
  re-approval when a pr outlives a main merge. `false` is a one-line rework.
- **[wisher] F5: must the approval come from a human?** lean: **not in this pr.** `ehm-seaturtle` holds
  write, so its approval counts. it cannot approve its own prs, but it could approve a rhelease
  release pr. only a CODEOWNERS file plus code owner review restricts who may approve; that adds a
  file and a human team per org, a wider change than the wish.
- **[wisher] which repos count as "released into"?** taken: every non-archived, non-fork repo of
  the four owners (195). the table marks `release workflow`, so the narrower set (123) is one filter away
- fulcrum inventory: `.fulcrums/inventory.of=fulcrums._.md`

### answered now

- **[answered] can an exemption be declared today?** no. declastruct-github 1.4.0 has no bypass
  field and no ruleset `pull_request` rule (`DeclaredGithubBranchProtection.d.ts:59-80`)
- **[answered] does `git.release --watch` name a review wait?** no. it polls `await automerge` to
  a 15-minute `⏰ timeout` (rhachet-roles-ehmpathy 1.42.0, `emit_transport_watch.sh` ~229). the
  gate holds; the mechanic reads a timeout. upstream fix caught as a reseed dream; land it before
  a fleet-wide apply
- **[answered] what sets the rule in an adopter?** the merge of its upgrade pr: `provision.yml`
  applies on push to main
- **[answered] does a merge of this pr change any protection?** no: this repo provisions from its
  own `provision/github/declastruct.resources.ts`
- **[answered] does declastruct-github send the review fields?** yes: `setBranchProtection.js:50-53`
- **[answered] how many approvals, code owners?** one, off (F3; no CODEOWNERS in the fleet)
- **[answered] can a push token read the rule?** yes, via `reviewDecision` + rulesets (F4,
  proven against two controls)

### research, later

- **[research] does github dismiss an approval on an update-branch merge that leaves the pr diff
  unchanged?** the docs name update branch as a dismissal trigger; observe it on the first
  adopter after the merge, to size F2's friction

### assumptions

- adopters receive `resources.ts` whole on apply (default EQUALS check), so no migration code is owed
- `reviewDecision` reflects current rules (see the skill's `.note` for the bound)

## .groundwork

### external research
- github branch protection docs (docs.github.com, about-protected-branches): update branch
  dismisses a stale approval; bypass lists exist only in orgs; "do not allow bypass" holds admins
- github docs (approving-a-pull-request-with-required-reviews): "pull request authors cannot
  approve their own pull requests" (grounds case=5)
- github rest: `/branches/main/protection` returns 404 to a push token (checked on
  ehmpathy/sdk-aws-lambda as `ehm-seaturtle`); `/rules/branches/main` and graphql
  `reviewDecision` are readable with push

  (ungated) reads empty on #764 and APPROVED on #761

## .what is awkward

- the release pr pause lands on every release, fleet-wide, for a review that is mostly a glance
- the census reads a proxy (recent prs), not the protection itself, for want of an admin token
- `dismissStaleReviews: true` with `strict: true` means a re-approval each time a pr outlives a
  main merge. in a busy repo that is several clicks a day. `false` would remove the friction and
  reopen the unread-push gap; neither side is clean
