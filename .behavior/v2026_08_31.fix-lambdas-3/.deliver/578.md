# deliver: #578 — workflow env gates stop spraying timeline Deployments

## what shipped

every job-level `environment:` gate in this repo's workflow TEMPLATES now uses the block
no-deployment form:

```yaml
environment:
  name: <x>
  deployment: false
```

`deployment: false` (github, march-2026) keeps the built-in gate — required reviewers, wait
timer, tag/branch policy, OIDC env-scoped role claim — but suppresses the side-effect Deployment
object, so a run posts no "deployed to <env>" status onto the PR/commit timeline. it fixes the
noise on BOTH plan gates and apply gates, which is the user's actual pain: a plan-against-prod
gate was accreting timeline noise for a job that deploys no resource at all.

## the clamp — `src/workflowEnvDeploymentFalse.declapract.integration.test.ts`

walks every workflow template under `src/practices/**/.github/workflows/*.yml` (skips
`.test`/`__snapshots__`/`node_modules`) and asserts:

- the walk reaches real templates (guards against a vacuous pass)
- the total gate count equals the known 11
- NO template uses the flat inline form (offenders == [])
- every block opener carries a `deployment: false` key (per-file blockOpeners === deploymentFalseKeys)

integration-classified: it crosses the filesystem boundary (`readFileSync` over every template),
same rule as `actionPins` — the boundary alone puts it in the integration suite, no credential,
no network.

## ⚠️ two GitHub-side confirms this template shape depends on

neither is readable from the repo tree, so each is a documented bound — recorded in the clamp's
doc header, not asserted by a test:

1. **empty-name in block form** — a caller that omits the env input (e.g. prep on `.deploy-sls`,
   which passes no `github-environment-apply`) must, in the block form, mean "no environment" as
   it does in the flat form. the block form's `name` is the same field, so this holds by github's
   own desugaring — but it is unverified from here. **fail-loud + one-line revert if wrong.**
2. **custom deployment-protection-rule App** — `deployment: false` is INCOMPATIBLE with a custom
   deployment-protection-rule GitHub App on the environment: the job fails loud. built-in rules
   (reviewers, wait timer, tag/branch policy) are fine. a consumer whose prod environment carries
   a custom App rule must drop `deployment: false` there — a one-line, fail-loud revert, never a
   silent break.
