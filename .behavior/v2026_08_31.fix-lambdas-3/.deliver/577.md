## the fix — finish the prep-over-dev migration via a dual-publish of both fleets

`deploy:release` resolved `SLS_STAGE prep → dev`, so the stack + every lambda deployed under the
`-dev-` slug while all a human reads says `prep` — the divergence the north star exists to kill, and
the direct cause of the deployed-acceptance break (a suite that invokes `svc-x-prep-*` against a
fleet named `svc-x-dev-*`).

the fix implements the vision's dual-publish mechanism in `serverless/best-practice/package.json`:
- **`deploy:release:ancient`** — `SLS_STAGE = ($ACCESS == prep ? dev : $ACCESS)`, then
  `sls deploy --stage $SLS_STAGE`. emits the legacy `-dev-` fleet an ancient peer still addresses.
- **`deploy:release:contemp`** — `sls deploy --stage prep`. emits the go-forward `-prep-` fleet.
- **`deploy:release`** — runs BOTH (`ancient && contemp`), so a fresh deploy lands under both
  slugs and no cross-service call 404s while the org migrates peer-by-peer.
- **`deploy:prune`** — prunes the ancient fleet always AND the contemp (`-prep-`) fleet when
  `ACCESS=prep`.
- **`deploy:prod`** — runs `deploy:release:ancient` only (prod: access == stage, one fleet).

pairs with the D27 dual-grant already in `serverless.yml` (the ancient stack deploys `--stage dev`
but runs `ACCESS=prep`, so the cache + glue-db IAM carry BOTH the stage-keyed and access-keyed
names). this is the deploy half of the north-star `stage`→`access` collapse; at the endpoint
(`grep AccessAncient → 0` org-wide) the `:ancient` half, the `-dev-` fleet, and the divergent
`stage` retire together.
