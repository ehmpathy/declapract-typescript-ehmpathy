# 1.vision.experience.case=4 — an upgrade meets old text

inventory rows 23, 24. actor: upgrader. feel: happy, then sharp. care: critipath.
the densest walk: it crosses the practice upgrade, the lock, text committed before the upgrade, and the halt.

## .narrative

a consumer maintainer runs `npx declapract apply --practice husky`. the apply writes the new
`check.timestamps.sh` and a lock re-stamped with the new hook's blob id, together, so the lock never
halts on the upgrade itself. the next commit touches only clean files and lands, silent.

a week later a dev edits an old runbook that has said "deploy window opens at `hhmm UTC`" since
before the upgrade. the hook scans the whole staged blob, not the diff, so the old line halts the
commit, though the dev did not write it. the error names `runbook.md:<line>:<the line>`. the dev
masks it, and the leak that sat in the repo for months stops at the next touch.

this is the intended feel: the hook scrubs on contact. it never rescans the tree, so a repo is not
flooded with halts on the day of the upgrade.

## .bdd sketch

```
given a consumer repo on the prior hook, with runbook.md that holds `hhmm UTC`
  when [t0] the maintainer runs `npx declapract apply --practice husky`
    then .husky/check.timestamps.sh and .husky/check.timestamps.lock.sh both change
  when [t1] a dev commits an unrelated clean file
    then pre-commit exits 0 (the lock matches the new hook)
  when [t2] a dev stages an edit to runbook.md that leaves the old line in place
    then pre-commit exits 2 and names `runbook.md:<line>:`
  when [t3] the dev masks the clock and restages
    then pre-commit exits 0
```

## .the test shape

the lock stamp is already held by `check.timestamps.lock.play.declapract.integration.test.ts` and
`self-application.declapract.integration.test.ts`; this pr re-stamps the root copy with
`rhx husky.lock.restamp` and reruns both. the halt on old text is the same halt as case=1: the hook
scans whole blobs, which `[case13]` rows already exercise.
