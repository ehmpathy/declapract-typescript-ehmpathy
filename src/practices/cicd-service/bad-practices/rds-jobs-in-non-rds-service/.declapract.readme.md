# rds-jobs-in-non-rds-service

## .what

detects a non-rds service whose `.github/workflows/provision.yml` still carries the 4 rds-coupled
jobs (`sql-schema-{prep,prod}`, `aws-{prep,prod}-declastruct`), and strips them.

## .why

the best-practice `provision.yml` gate omits those 4 jobs for a non-rds usecase — but it is a
`CONTAINS` check, so it is fix-forward for **fresh** scaffolds only. a superset satisfies `CONTAINS`,
so a non-rds repo stamped **before** the gate keeps the full superset, no best-practice fix fires,
and its provision workflow fails: the 4 rds jobs reference `persist-with-rds` files (the schema +
daos `.sql-schema-control.yml` callee, the `provision/aws/resources.ts` declastruct callee) that a
non-rds service does not ship.

this bad-practice is the retroactive half of that gate — it repairs a pre-stamped consumer without a
hand edit.

## .the check

- **detected** (return) when `persist-with-rds` is NOT in `context.projectPractices` AND the file
  still holds the rds-jobs tail.
- **not detected** (throw) when the repo IS an rds service (it legitimately keeps those jobs), or the
  rds tail is already gone.

## .the fix

reuses the best-practice's own `withoutRdsJobs` + `RDS_JOBS_ANCHOR`, so the truncation boundary lives
in one place and cannot drift between the fresh-scaffold gate and this retroactive strip. on an
anchor miss the helper throws loud rather than truncate to the whole superset — a silent re-ship of
all 4 rds jobs is the exact break this strip exists to close.

## .idempotency

the fix strips the rds tail; a second pass finds the tail gone, so `check` throws (skip) and the fix
never re-fires. a direct second `fix` call throws loud (the anchor is absent) — check gates fix, so
the pipeline re-run is a clean no-op.
