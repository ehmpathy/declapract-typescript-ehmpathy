## the defect — the template lacks a body-max-line-length override

`test:commits` lints from the last tag through HEAD. on a release PR, github squash-merge
collapses a PR's sub-commit headers into `* ` body bullets, so a header near the 140-char
header-max-length becomes a body line over config-conventional's default `body-max-line-length`
of error-level 100 — and the release-branch lint fails even though every source header was valid.

## the ground read — #570 fixed the REPO ROOT, not the template

⚠️ verified against the current tree: commit `b0802fd` (#570) added
`body-max-line-length: [1, 'always', 140]` to this repo's OWN root `commitlint.config.js` (+5
lines), but did NOT touch the practice template at
`src/practices/conventional-commits/best-practice/commitlint.config.js`. so the fix reached one
consumer (this repo) and no other — the exact symptom-vs-source split this wish exists to correct.
it also left a template↔repo drift: the root carries the override, the template does not.

## the fix — align the template with #570's chosen remedy

added to `best-practice/commitlint.config.js`, byte-identical to what #570 put in the repo root:

```js
// match the header allowance: a squash-merge turns each commit header
// into a `* ` body bullet, so a 140-char header becomes a ~142-char body
// line. keep body lines aligned with the 140-char header cap so a long
// header can never fail the release-branch commit lint.
'body-max-line-length': [1, 'always', 140],
```

this resolves #554's problem AND closes the drift #570 introduced. the file is checked with
`EQUALS` (no `.declapract.ts` companion), so consumers get the exact line on next upgrade.

## why #570's `[1, 140]` over #554's proposed `[0, 100]`

#554 proposed the rule off (`[0, always, 100]`). #570's warn-level-140 is strictly better: it
keeps enforcement (subject length is still bounded via header-max-length, and body lines are still
flagged past 140), aligned with the header cap, so a squashed header-turned-bullet never errors
while genuine over-long body lines still warn. adopted #570's form since it is the more considered
remedy AND the one already live in this repo's root — so template and repo now agree.

## the clamp — commitlint-body-max-line.declapract.test.ts (practice root, 2 tests)

reads the shipped template and asserts a `body-max-line-length` line is declared, is warn-level
(`[1, `), and is aligned to `140]`. teeth confirmed: delete the line from the template and both
assertions go RED (2 failed — config-conventional's error-level-100 default reasserts). restored →
2 GREEN. the clamp sits at the practice ROOT, so declapract never emits it.

## bounds

- header-max-length stays warn-level 140 (unchanged); subject length enforcement is untouched.
- this repo's root `commitlint.config.js` was already correct (via #570); no root edit was needed
  — only the template, so every consumer inherits the fix.
