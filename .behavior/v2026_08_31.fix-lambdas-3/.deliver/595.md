delivered on branch vlad/fix-lambdas-3.

the sharded PR acceptance job now defaults to IN-PROCESS (`LOCALLY=true`), so a fleetless
service — one that publishes only its dev/prep fleet and has no deployed `test` fleet —
inherits a green PR gate instead of an all-404 cloud-invoke run.

## the shape — LOCALLY=true on every acceptance shard step

`src/practices/cicd-common/best-practice/.github/workflows/.test.yml` — every
`test:acceptance` shard command (the explicit path + both dynamic-shard branches) carries
`LOCALLY=true THOROUGH=true npm run test:acceptance`. in-process runs the handler directly,
so a service with no deployed `test` fleet still exercises its acceptance suite. the deployed
-fleet run stays a POST-deploy grain (the assure job, against the contemp fleet) — the PR gate
is deliberately fleetless.

## why this is the wish's meta-lesson (case=6, silent-check class)

a bare cloud-invoke shard against a fleetless service is an all-404 run that reads as a real
failure — a silent gate defect on arrival, kin to #564 / #586's suite-on-arrival family. the
in-process default removes the arrival break: the gate speaks about the code, not about an
absent fleet.

## clamp

`src/practices/cicd-common/.declapract.integration.test.ts` (28 tests, GREEN) — the #595 case
asserts BOTH acceptance shard steps (explicit + dynamic) carry `LOCALLY=true` and NO bare
cloud-invoke step survives. teeth: revert any shard to the cloud-invoke default (drop
`LOCALLY=true`) and the matched case reddens. the shipped `.test.yml` is snapshotted, so a
reword vibechecks in review.

## bounds / not-done

- the POST-deploy acceptance run against the deployed contemp fleet is unchanged — it stays a
  real cloud invoke in the assure job, where a deployed fleet exists by construction. the
  fleetless default is scoped to the PR gate only.
