# 🌙 dream: decide the config-host tier-migration strategy

kind = fix
owner = whoever next touches `src/utils/migrateDevConfigToPrep.ts` or `persist-with-rds`'s config templates
caught 2026-09-10

## .the cue that fired

i034 r008.b3 (behavior-intent-coverage) flagged that `migrateDevConfigToPrep` rewrites the `access`
key but leaves the `database.tunnel.lambda.host` value untouched — so a consumer whose config still
carries a `dev`-named host keeps pointing at a `dev`-slug resource after the migration, a
silent-wrong-tier window the north star exists to kill.

## .the gap, precisely

- **evidence**: `src/utils/migrateDevConfigToPrep.ts` rewrites only
  `contents.replace(/"access":\s*"dev"/g, '"access": "prep"')` — every host byte is preserved.
- so a config with `"host": "svc-x-dev-...."` still names a `-dev-` resource after `access` flips to
  `prep`. the `access` axis is corrected; the host slug is not.
- the north star (decision 3) says the RDS host is an opaque `access`-keyed value the CNAME alias
  re-points, so a byte-preserve is CORRECT under that plan. but a consumer who has NOT set up the
  alias inherits a still-live `dev`-named host that now disagrees with the `prep` access — the exact
  two-word divergence, one layer down.

## .why it is a REFUTE, not a repair — the three grounds a host rewrite fails

the reviewer asked the migrator to also rewrite the host. it must not, and the code already codifies
why (`migrateDevConfigToPrep.ts` jsdoc):

1. **structural ambiguity** — a `.dev` label is axis-ambiguous WHEREVER it sits: a `.dev` gTLD, a
   foreign mid-dotted host, and an internal tier token all read alike to a regex. a blind
   `dev → prep` host rewrite corrupts the first two to fix the third.
2. **the per-consumer prep host is unknowable** — the template cannot know a given consumer's actual
   prep cluster host. to emit one is the meta-lesson's forbidden value-guess (*a practice that emits
   a value cannot verify its own output*).
3. **JSON admits no marker + the gate is EXISTS** — there is no place to leave a `@declapract:review`
   marker in a JSON value that a plan would surface, and the config gate is EXISTS (never reads
   content), so a spliced host rewrite reads CLEAN in plan even when wrong. any host rewrite
   reintroduces a silent break to close one.

⇒ so the byte-preserve is the correct behavior, the residual window is conceded, and the reviewer's
point is answered by the fulcrum below rather than a code change.

## .the shape of the fix

there is no clean code fix — the strategy is a wisher call. the two candidate paths:

- **byte-preserve + CNAME alias** (north-star decision 3) — the migrator never touches the host; the
  `-dev-`-named host is re-pointed at the one prep cluster by a Route53 CNAME, zero data moved. the
  window closes when the alias lands, human-gated per env.
- **structural token-swap** (wish row 4) — the migrator rewrites the tier token in the host. requires
  a marker convention the JSON+EXISTS gate cannot carry, and a per-consumer prep host the template
  cannot know — so it fights grounds 2 + 3 above.

## .the fulcrum this raises

`inventory.of=fulcrums.case=F-config-host-tier-strategy` — **byte-preserve+CNAME-alias vs
structural-token-swap**. decision 3 already picks byte-preserve; this records that the choice leaves a
silent-wrong-tier window open until the alias lands, and that the alternative (token-swap) is refused
on the three grounds above. the wisher must ratify that the CNAME path is the sanctioned close, and
that the residual window is acceptable for the transition.
