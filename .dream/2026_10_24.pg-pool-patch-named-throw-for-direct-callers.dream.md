# 🌙 dream: the pg-pool patch names itself when a direct caller passes no Client

- kind: followup
- owner: declapract-typescript-ehmpathy, practice persist-with-rds
- caught 2026-10-24

## .the cue that fired

a peer review (enroll-impl-behavior-intent, i003) noted the error a direct `new Pool()` caller meets is
`this.Client is not a constructor`, which names neither pg-pool's patch nor the remedy. the clamp now asserts that
exact message across every release in `^3.2.1`.

## .the gap, precisely

the patch header names the remedy `{ Client: require('pg').Client }`, but a caller reads the header only if they
think to open the patch. the error at first connect points at pg-pool internals.

## .the shape of the fix

replace the fallback with a getter-free stub that throws a named error, with no `require('pg')`, so dpdm still sees
no edge:

```js
this.Client = this.options.Client || Client || class {
  constructor() {
    throw new Error("pg-pool: no Client passed, and patches/pg-pool.patch removed the require('pg') fallback; pass { Client: require('pg').Client }")
  }
}
```

then flip the clamp's `withoutClient` and `withoutClientConnect` assertions to the named message.

## .why it is not done in this round

it changes runtime behavior beyond the wish (a cycle fix): every direct caller's failure mode changes shape, and the
hunk grows, which widens its fit risk across releases that this round just narrowed. safe to defer; the current
failure is loud and the header + readme name the remedy.
