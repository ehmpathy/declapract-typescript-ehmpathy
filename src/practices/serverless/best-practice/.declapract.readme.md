# serverless

the serverless-framework deploy config for a lambda service.

## dual-publish, across the ancient→contemp transition

`custom.accessByStage` maps the deploy slug (`stage`) to the access (`ACCESS`):

```yaml
accessByStage:
  dev: prep # stage=dev deploys $service-dev (ancient slug), runs ACCESS=prep
  prep: prep # stage=prep deploys $service-prep (contemp slug), also ACCESS=prep
  prod: prod
```

so a single `prep`-access service dual-publishes BOTH fleets from one artifact:
`deploy:release` runs `deploy:release:ancient` (`--stage dev`) then `deploy:release:contemp`
(`--stage prep`). `deploy:prune` prunes the ancient fleet always and the contemp (`-prep-`) fleet
when `ACCESS=prep`, so neither accumulates unpruned versions. `deploy:prod` publishes the ancient
(`prod`) fleet only — prod is `prod` on both axes, so it has no divergent slug.

### why prod does NOT dual-publish (the contemp→prod edge)

the dual-publish exists to bridge ONE divergence: below prod, `access=prep` deploys under a `-dev-`
slug (ancient) while migrated callers address the `-prep-` slug (contemp). prod has no such
divergence — `access=prod ⟺ stage=prod` — so there is one `-prod-` fleet and no second slug to
publish.

a contemp→prod 404 is therefore unreachable, because the `sdkAwsLambdaEnvAccess{Ancient|Contemp}`
target helper resolves against the CALLER's OWN `access`, not a fixed `-prep-` string. a prod-access
caller resolves BOTH `Ancient` and `Contemp` to `prod` (there is no dev/prep split at prod), so it
always addresses the published `-prod-` fleet. the `-prep-` slug is only ever emitted by a
`prep`-access caller, which addresses `prep`-tier peers — never a prod service. a `prep`-access
caller that reaches a prod service is a cross-tier call, which is not a supported pattern and is not
what dual-publish covers. so prod's ancient-only publish leaves no cross-service call uncovered.

the north-star of the fix-lambdas wish is to retire the `stage` axis entirely; this dual-publish is
the transition scaffold, built to be torn down once every peer addresses self by `access`. see
`.behavior/v2026_08_31.fix-lambdas-3/1.vision.yield.md`.

### the transition cost — watch the Lambda code-storage cap

dual-publish doubles a service's deployed function count AND its code-storage footprint in the
test/prep account, for the life of the transition. AWS Lambda's per-region **code storage is a
75 GB soft cap**. before a fleet-wide dual-publish, confirm `usage × 2 < 75 GB` via
`aws lambda get-account-settings` (the `AccountLimit.TotalCodeSize` vs `AccountUsage.TotalCodeSize`
fields). the cap is soft (raisable by a support request), the 2× is transition-only, and it drops
back to 1× at the north-star endpoint when the `-dev-` publish retires. function count has no hard
cap, and concurrency is unaffected (the `-dev-` fleet takes ~no traffic).

### this practice ships the ADD half only; the REMOVE half waits on an opt-in marker

this practice adds the `accessByStage` insert + the dual IAM grants. it ships no paired remove.

the remove half waits on an explicit opt-in marker that a consumer has completed its migration —
the marker cannot be inferred from the filesystem, because a fresh scaffold and a fully-migrated
consumer both hold zero `AccessAncient` imports, so any auto-strip re-adds and re-strips on each
`declapract fix`. the marker also authorizes case=1's one-axis deletion.

the transform that adds the scaffold is labeled in `serverless.yml.declapract.ts`. the full
rationale is in the vision's settled design §2.

## the deployment bucket is account-scoped, not just stage-scoped (#596)

`custom.deploymentBucketByStage` keys the serverless deployment bucket by stage, the same shape as
`accessByStage`:

```yaml
deploymentBucketByStage:
  dev: serverless-deployment-<ns>-dev   # prep-account bucket (ancient slug)
  prep: serverless-deployment-<ns>-dev  # prep-account bucket, shared with dev
  prod: serverless-deployment-<ns>-prod # prod-account bucket
```

the deployment bucket is not merely service-scoped — it is **account-scoped**: it must live in the
same account the deploy role assumes. a prod deploy assumes the prod-account oidc role
(`ahbode-prod-oidc-for-apply`), which has no cross-account grant to the prep-account `-dev` bucket, so
a single hardcoded `-dev` bucket fails a prod deploy at bucket lookup
(`s3:GetBucketLocation ... not authorized`). the map keeps ancient (`dev`) + contemp (`prep`) on the
one shared prep-account `-dev` bucket, and points `prod` at a prod-account `-prod` bucket, so every
deploy's bucket sits in the account of its role.

the -prod bucket must be provisioned in the prod account (e.g. via the terraform under
`provision/aws/environments/prod/`), or the fix trades a cross-account-deny for an absent-bucket
error. this is the deploy-bucket facet of the same prep→dev account divergence the `accessByStage` +
dual-IAM sections above address; it collapses with the rest at the north-star `stage`→`access`
endpoint.

## the domain-driven-cache IAM — the middle segment is name-globbed, not templated (D27, #597)

the `iamRoleStatements` grant for the global cache table globs the middle name segment, rather than
template it on `provider.stage` or `custom.access`:

```yaml
Resource:
  - arn:aws:dynamodb:...:table/infrastructure-*-table-domain-driven-cache
```

the cache is one SHARED dynamodb table addressed by a single name (below prod that name is `-dev-`),
while a dual-publish service runs two fleets whose roles key on different slugs (ancient `dev`,
contemp `prep`). a slug-templated grant covers only the deployed fleet's own slug — so the contemp
`-prep-` fleet's `-dev-` cache read AccessDenies, and a with-simple-cache read-back throws a 500
instead of a null. this was a real break on svc-gateway `prep / assure`: 3 chat endpoints 500'd on
the contemp fleet only, and cloudwatch named the AccessDeny on
`infrastructure-dev-table-domain-driven-cache` (#597).

the glob covers `-dev-`, `-prep-`, and `-prod-` in one line. it stays least-privilege:
account-scoped (`${aws:accountId}`) and name-scoped to the one cache family — it widens only across
the middle segment, the axis the fleets differ on. the glob already covers every slug, so it needs
no change at the north-star `stage`→`access` endpoint. tracked in the wish roster (D27,
north-star tier-C).
