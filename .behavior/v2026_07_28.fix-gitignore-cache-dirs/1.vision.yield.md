# 1.vision — gitignore the two cache dirs, so `git tree del` can fell a worktree

## .tldr

the wish asks us to findsert `.cache/` and `.agent/.cache/` into the declapract-managed
gitignore template. **both lines are already there** — `.cache/` landed in #435, `.agent/.cache/`
in #477. the wish's premise ("neither dir is tracked nor gitignored today") is stale.

so the vision is not "add two lines." it is **close the gap between what the template declares
and what the acceptance can prove**:

| acceptance criterion | today | gap |
|---|---|---|
| template carries both lines | ✅ already true | none |
| upgrade adds an absent line | ✅ the `fix` does this | **unproven for these two lines** |
| a repo that carries a line stays byte-identical (*prove it, do not assert it*) | 🔴 **false as written** — see below | prove the **fixed point** instead; no idempotency test extant, and neither cache line is named by any assertion |
| a fresh worktree shows clean `git status` after a role boot | ✅ attainable | this repo's own `.gitignore` drifted — add the one line (the `?? .behavior/` in `git status` is **not** a gap; `.behavior/` is tracked work product, just uncommitted here) |

so the deliverable re-shapes rather than grows: **leave the `git` template alone**, **self-apply one
line**, **clamp it** — plus one addition the wisher folded in mid-drive: **give the `rhachet`
practice its own gitignore declaration**, so the practice that *creates* `.agent/.cache/` also
*declares* its ignore.

### ➕ the rhachet fold-in (added 2026-07-28, wisher-directed)

> "are they both applied by the rhachet practice though? we'd like that practice alone to also
> findsert those gitignore rows" — the wisher, then: **"fold into this"**

today the answer is **no**. `src/practices/rhachet/` declares three files —
`package.json`, `package.json.declapract.ts`, `.agent/keyrack.yml.declapract.ts` — and **no
`.gitignore`**. every cache line a rhachet consumer gets arrives from the **`git`** practice.

that is an ownership seam, not a bug: the practice that boots roles into `.agent/.cache/` does not
declare the ignore for the dir it writes. a repo that took `rhachet` **without** `git` would get
the cache dir and no ignore for it. today no use-case does that (`src/useCases.yml` puts both in
`typescript-project`), so the gap is **latent** — the same shape of latency the wisher already
ruled on for `.agent/.cache/` itself.

the cost is real and must be stated: it makes `rhachet` a **second declarer of the repo-root
`.gitignore`**, which is exactly the shape edgecase 7 flags as a suspected oscillation. so this
fold-in **promotes q15 from `[research]` to a prerequisite** — the integration test must first
settle what declapract does when two practices declare one file. see move 4 and edgecase 9.

**the wisher has ruled (2026-07-28): ship as proof-and-clamp, do not close as done.** and the
reason `.agent/.cache/` is not merely redundant is sharper than the one this vision first gave —
today's agent-cache coverage is **implicit**, a side-effect of `.cache/`'s pattern shape, and **no
consumer repo carries the explicit line yet** (sampled `type-fns`). so a single future edit to that
one line would un-ignore agent caches **fleet-wide, silently**:

> a latent path is one refactor away from live. — the wisher

so the clamp must prove **both paths stay ignored**, not merely that both lines exist.

### ⚠️ the third criterion needs a correction before it can be met

*"a repo that already carries a line stays byte-identical"* is **not true**, and we should not
chase it. `defineExpectedContents` **always sorts** and **always relocates** the `node_modules`
negations to the end. so this repo — which carries `.cache/` — would still be rewritten:

```
# a .gitignore that "already carries a line"      # what fix() emits
node_modules                                       *.log
.cache/                              ──fix()──▶    .agent/.cache/
*.log                                              .artifact
                                                   .cache/
                                                   … (+ the rest, sorted)
                                                   node_modules
                                                   !.test*/**/node_modules
                                                   !.test*/**/node_modules/**
```

two different claims sit inside that one sentence:

| | claim | true? |
|---|---|---|
| **A** | carries the line ⇒ untouched — `fix(x) == x` | **false** |
| **B** | the fixed point — `fix(fix(x)) == fix(x)` | **true**, and provable |

**only B is idempotency**, and B is what the parenthetical *"(idempotent — …)"* names. we prove
**B**. claim A is recorded as a defect in how the wish is worded, flagged to the wisher as **f5**.

this matters: had we chased A, the clamp would assert `fix(x) == x`, watch it fail on every
realistic input, and get weakened until it passed — a hollow clamp born from a false spec.

## the outcome world

### day-in-the-life

a beaver finishes a dispatched task in a worktree. a rhachet role booted at session start and
wrote scratch into `.agent/.cache/`. the beaver runs the teardown — and it just works. no
hand-clean, no `rm -rf .cache`, no "hmm, whose dir is this?" pause. the tree falls on the first
ask, every time.

> **note on `git tree del`:** the wish names this teardown command, but `git-tree` is **not on
> this host** (`which git-tree` → not found) — it lives in the beaver's dispatch loop, outside
> this repo. so this vision does **not** quote its stdout; inventing one would be fiction. the
> observable we *can* verify from here is the precondition `git tree del` refuses on: whether
> `git status` reports untracked cruft. that is the signal used throughout below.

### before / after

| | before (2026-07, the incident window) | after |
|---|---|---|
| teardown | `git tree del` refuses — untracked `.cache/` present | fells clean |
| beaver's move | hand-clean, then retry the fell | none — just fell it |
| scratch files | trackable, so `git add .` sweeps them in | invisible to git |
| `FIREWORKS_API_KEY` in a debug file | commitable → **was committed and pushed** (per #514's account, corroborating the wish) | unstageable by default |
| a fresh role boot | re-creates the cruft, snag returns next teardown | stays invisible forever |

### the aha moment

the value clicks the moment someone runs `git status` in a freshly-booted worktree and sees:

```
$ git status --short
$
```

empty. the roles have been writing cache all session, and git has no word on it.
**the scratch state became genuinely invisible, not merely tolerated.**

the *second* aha is sharper, and it is the one that actually motivates this wish: a beaver types
`git add .` in a hurry, and the api key that lived in `.cache/debug.json` **does not go with it**.
the gitignore line is not a tidiness nicety — it is the constraint that makes the careless move
safe (`rule.prefer.prevent-over-correct`).

## user experience

### who, and what goal

| user | goal | the contract they touch |
|---|---|---|
| beaver in a dispatched worktree | fell the tree on the first ask | `git tree del` — succeeds instead of refusing |
| beaver mid-task | `git add .` without a secret leak | `git status` / `git add` — cache never appears |
| repo maintainer | inherit the ignore, author nothing | `declapract fix` — the line arrives |
| this repo (self-application) | stay conformant to its own declaration | `declapract check` — passes on its own `.gitignore` |
| a repo that takes `rhachet` | get the ignore for the dir rhachet writes, from rhachet | `declapract fix` — the `rhachet` practice findserts `.agent/.cache/` on its own (move 4) |

### the contract, in and out

the contract is the declapract file-fix pair in
`src/practices/git/best-practice/.gitignore.declapract.ts`:

```ts
export const check: FileCheckFunction = (contents) =>
  expect(contents).toEqual(defineExpectedContents(contents)); // throw = violated

export const fix: FileFixFunction = (contents) =>
  ({ contents: defineExpectedContents(contents) });           // union, sort, emit
```

| in | out |
|---|---|
| `null` (no `.gitignore` yet) | the full declared set, sorted, `node_modules` negations last |
| a repo's extant `.gitignore` | **union** of its lines with the declared set — custom lines preserved |
| a `.gitignore` that already conforms | **byte-identical output** (the idempotency claim) |

the shape is already a findsert by construction: `dedupe([...fromFile, ...declared]).sort()`.
a line present once stays present once. this is why the wish's "no duplicate line" ask needs no
new mechanism — only a **proof**.

### the timeline a consumer walks

```
[t0]  repo has .gitignore without .cache/
[t1]  `npx declapract fix`
        └─ check throws (contents ≠ expected)
        └─ fix unions the declared lines in, sorts, writes
[t2]  .gitignore now carries .cache/ and .agent/.cache/
[t3]  `npx declapract fix` again
        └─ check passes → NO write. file byte-identical.   ← the proof we owe
[t4]  a role boots, writes .agent/.cache/roles.json
[t5]  `git status --short` → empty
[t6]  `git tree del` → fells clean
```

step **[t3]** is the whole deliverable. it is believed true and never demonstrated.

## mental model

### how a user describes it to a friend

> "the repo template knows which folders are scratch. you upgrade, and git stops seeing them.
> your worktrees tear down clean and you can't accidentally commit a debug file with a key in it."

nobody says "findsert." they say **"the ignore just shows up when i upgrade."**

### the analogy

the gitignore template is a **shared do-not-pack list** for a house move. every repo inherits the
list; each may add its own items; no item on the list is ever packed twice, and a re-read of the
list never adds a duplicate. `declapract fix` is the packer who reconciles your list against the
shared one — and a second pass finds no work left.

### their words vs ours

| they say | we say | why ours |
|---|---|---|
| "the ignore shows up" | findsert | states the idempotency in the verb |
| "run it twice, no change" | idempotent | `rule.require.idempotent-fixes` |
| "the shared list" | the declapract-managed template / best-practice | names the mechanism |
| "cache folder" | `.cache/` — a **gitignore directory pattern**, not a path | pattern semantics are load-bearing (see below) |

that last row is the one place their word and ours must diverge, and it is the crux of the
sharpest finding in this vision.

### pros

- **zero new mechanism for moves 1–3.** the extant sort+dedupe union already IS a findsert. we add proof, not machinery (`rule.prefer.wet-over-dry`).
- **the fix is a fixed point by construction.** `defineExpectedContents` is idempotent because its output, re-parsed, yields the same set. the clamp will show this rather than argue it.
- **inherited, not authored.** a repo gets the ignore from an upgrade; no maintainer writes a line.
- **custom lines survive.** the union preserves `.idea`, `*.pyc`, whatever a repo added.
- **the fold-in aligns ownership with authorship.** after move 4, the practice that boots roles into `.agent/.cache/` is the practice that declares its ignore — so the ignore travels with the cause, not with a neighbor.

### cons

- **the wish's premise was stale**, so the visible deliverable is far smaller than the wish implies. a reader who expects a two-line diff gets a test file instead. that mismatch needs said out loud, not hidden.
- **`.agent/.cache/` has no matching effect today** (see edgecase 1). we keep it as insurance against silent fleet-wide breakage, but it changes what git does for no repo right now.
- **the deliverable is proof-shaped, not feature-shaped** — a test file plus one line. that reads thin next to the wish's framing, and the temptation to pad it into something that looks bigger must be resisted.
- **the fold-in duplicates `ignoresOrdered` across two practices** (edgecase 9). assertion (e) guards the seam, but the true fix is a shared constant, and that is deferred to a follow-on task. a reader who meets the duplicated block without the cross-reference comment would rightly try to delete it.
- **the fold-in is gated, not free.** it cannot ship until q15 is observed, so it puts a real prerequisite in front of a move the wisher already approved. if q15 answers "dedupe to one", move 4 must be re-shaped rather than written as specified.

### edgecases, and how the contract keeps a user in the pit of success

**1. `.cache/` already matches `.agent/.cache/` — verified, not assumed.**

```
$ git check-ignore -v .agent/.cache/foo .cache/foo
.gitignore:6:.cache/	.agent/.cache/foo
.gitignore:6:.cache/	.cache/foo
```

a gitignore pattern with no **interior** separator matches at **any depth** — the trailing slash
constrains it to directories, not to the root. so `.cache/` alone already ignores
`.agent/.cache/`. the `.agent/.cache/` line is a no-op for matching.

**but "redundant" is the wrong read.** coverage today is real but **implicit**: it is a side-effect
of `.cache/`'s pattern *shape*, not an explicit declaration.

> **a latent path is one refactor away from live.** — the wisher

**a correction to the mechanism, which strengthens rather than weakens the point.** the wisher
attributed the risk to #514, as an owner that might re-scope `.cache/`. #514's text says the
opposite — its gitignore ask is *"add `.cache/` to the declapract-managed `.gitignore` template"*,
already satisfied by #435; only its husky secret-scan half is live. **#514 is not a re-scope
threat.**

the fragility is **structural**, and needs no named threat:

1. agent-cache coverage is **implicit** — `git check-ignore` shows `.cache/` as the rule that matches
2. implicit coverage breaks **silently** on any future edit to that line, by anyone, for any reason
3. **no consumer repo carries the explicit line** (sampled `type-fns`, byte-identical to ours) — so
   one edit un-ignores agent caches **fleet-wide, at once**

the explicit `.agent/.cache/` line is therefore **insurance against silent fleet-wide breakage**,
not documentation. a deliberate exception to `rule.prefer.wet-over-dry`: the duplication buys
independence from a line whose behavior many things quietly depend on.

**this changes what the clamp must assert.** line-presence and path-coverage are different claims:

| claim | assertion | catches a `/.cache/` narrowing? |
|---|---|---|
| the lines are declared | `contents` contains `.cache/` and `.agent/.cache/` | ❌ no |
| **both paths stay ignored** | `.cache/x` **and** `.agent/.cache/x` each match a rule | ✅ **yes** |

the wisher asked for the second. the clamp proves **coverage of both paths**, so a re-scope of
`.cache/` by #514 goes red here instead of silently un-ignoring the agent cache.

**2. a repo that already carries a line — idempotency has *two* halves, not one.**

`rule.require.idempotent-fixes` demands both, and a fix can satisfy the first while it fails the
second:

| half | assertion | what breaks without it |
|---|---|---|
| the fix reaches a fixed point | `fix(fix(x)) == fix(x)` | the file churns on every upgrade |
| **the check agrees it is done** | `check(fix(x))` does **not** throw | **`declapract fix` loops — re-flags the file forever** |

the second is the one i nearly dropped. the loop is governed by `check`, not by `fix`, so a
perfect fixed point still re-flags on every pass if `check` keeps throwing on it. the rule names
this a blocker outright: *"a `check` that still flags fixed output → `declapract fix` loops /
reflags forever."* the clamp asserts both.

**6. the self-referential-fixture trap — the clamp's own failure mode.**

this one surfaced in self-review r1 and it changes what the clamp must look like.

the extant `check` test asserts `contents` against `defineExpectedContents(contents)`. both sides
derive from the same `ignoresSortable` array. so if someone deletes `.cache/` from that array:

| | expected side | fixture side | result |
|---|---|---|---|
| today | includes `.cache/` | includes `.cache/` | pass |
| after a delete | **shrinks** — no `.cache/` of its own | still lists `.cache/`… | …but that fixture line is unioned back into the expectation from the file contents → **still pass** |

the fixture cannot detect the removal, because the fixture's own lines feed the expectation. a
test that passes whether or not the defect is present proves only that it does not exercise the
defect — `rule.require.clamp-edge-cases` calls this **a clamp with no teeth**.

so the clamp must assert the constant **directly**, never through the derived expectation:

```ts
// bites: names the declared set, independent of any fixture
const { contents } = await fix(null, {} as any);
expect(contents!.split('\n')).toContain('.cache/');
expect(contents!.split('\n')).toContain('.agent/.cache/');
```

`fix(null, …)` emits the declared set with no file contents to union in — so the assertion reads
`ignoresSortable` alone. delete a line from that array and this goes red. that is the teeth test,
and it must be **shown** to bite (delete → red, restore → green), never assumed to.

**3. a repo with a comment line in its `.gitignore`.** comments (`# custom ignores`) are treated
as sortable lines and get sorted into the list — they survive, but they migrate away from the
lines they annotate. prior behavior, unchanged by this wish. worth a note, not a fix here.

**4. a repo that has not upgraded since #477.** it gets both lines on its next upgrade. no action
needed; the template is the single source.

**5. the ordered negations.** `node_modules` and its `!.test*/**` negations must stay last —
gitignore negation requires the negated pattern to follow its target. the code holds them out of
the sort deliberately. any clamp we write must not disturb that invariant.

**7. there are TWO gitignore declarations that appear to conflict — a hypothesis, not a proven defect.**

⚠️ **evidence grade first**, so this is not read as stronger than it is:

| verified (read/ran) | **not** verified |
|---|---|
| two declarations target the repo-root `.gitignore` (both files read) | that a real `executeApply` actually oscillates — **needs a run, not a read** |
| both practices sit in `app-react-native-expo` (`src/useCases.yml`) | |
| their sort rules are incompatible (both sources read) | |
| declapract has no conflict/duplicate detection (grep of `node_modules/declapract/dist`) | |
| `npm run test:validate` is green today with both present | |

so **rejection at validate-time is ruled out**, but whether declapract applies both (→ oscillation)
or dedupes to one (→ no defect) is **inferred, not observed**. the integration test that step 3
already requires is the instrument that would settle it.

what follows is the hypothesis:

the wish says "the template". there are two, both targeting the repo-root `.gitignore`:

| declaration | behavior |
|---|---|
| `src/practices/git/best-practice/.gitignore.declapract.ts` | sorts, **holds 3 lines out** of the sort (negations last) |
| `src/practices/cicd-app-react-native-expo/best-practice/.gitignore.declapract.ts` | sorts **all** lines, no ordered section |

`src/useCases.yml` puts **both** in `app-react-native-expo`. so for those repos:

- `git` fix puts the negations last → `expo` check throws
- `expo` fix sorts all lines; `!` sorts before alphanumerics → negations hoist to the **top** → `git` check throws
- → **endless oscillation. neither is a fixed point once both apply.**

worse than churn: a hoisted `!.test*/**/node_modules` sits **above** `node_modules`, so the
negation turns **inert** — the exact invariant the `git` practice keeps a comment to protect.

**out of scope here** (the wisher ruled stay-narrow; this is a different practice) — propose a
radio task alongside the f4 sweep. but it is a live counterexample to a single-file idempotency
proof: **both practices pass a per-file `fix(fix(x)) == fix(x)` test individually.** the defect is
in their interaction, which is why edgecase 8 matters.

**8. a unit clamp cannot see the pipeline.** `rule.require.declapract-integration-tests`: a fix that
*"transforms blocks (structured text)"* **requires** an `.declapract.integration.test.ts`, and its
absence is a **blocker** — *"a unit test of the exported `fix`/`check` alone is necessary but NOT
sufficient."* the gitignore fix unions, sorts, and relocates. edgecase 7 is the proof rather than
merely the letter: only a real `executeApply` sees two practices contend for one file.

**9. the rhachet fold-in makes a SECOND declaration on purpose — the same shape edgecase 7 warns
about. it is safe only under one condition.**

edgecase 7 warns about two declarers of one file. the fold-in adds a third declarer deliberately.
the distinction that makes it safe is **not** "ours is smaller" — it is **sort compatibility**:

| declarer | what its `fix` emits |
|---|---|
| `git` | `sorted(file ∪ git17) ++ ordered` |
| `expo` (the cautionary one) | `sorted(file ∪ {android/, ios/})` — **no ordered tail** |
| `rhachet` (proposed) | `sorted(file ∪ {.agent/.cache/}) ++ ordered` ← **must replicate `ordered`** |

both `git` and `rhachet` **union the file's extant lines**, so once either has run, the file already
holds the other's lines. run `git` then `rhachet`: `rhachet` finds `.agent/.cache/` present, unions
its own set (a no-op), sorts, appends the same ordered tail → **byte-identical**. `rhachet`'s check
then passes on `git`'s output and vice-versa. **the two converge; they do not oscillate.**

`expo` is the counter-example that shows the condition carries real weight: it omits the ordered
tail, so its output can never satisfy `git`'s check, and `git`'s output can never satisfy its own.

**so the rhachet declaration MUST replicate `ignoresOrdered` verbatim.** that duplication is a
maintenance hazard in its own right — two copies of the negation invariant, either of which can
drift. the mitigation is a cross-reference comment in both files that names the other, so whoever
edits one is told the other exists. (a shared exported constant is the cleaner fix and is **out of
scope** here — it would move code out of `best-practice/`, whose files are templates, not a module
tree.)

**the condition above is verified by read, not by run.** whether declapract even *applies* both
declarations — or dedupes to one, in which case one practice silently wins and the other's rows
vanish — is q15, and it is **unobserved**. that is why the fold-in promotes q15 to a prerequisite:
the integration test settles it before the second declaration ships.

## what is awkward?

### 1. the wish argues for work already done — and that is the honest headline

the wish's `.why` is written in the present tense: *"neither dir is tracked nor gitignored today."*
that was true when the pain was felt across the 2026-07 teardowns; it stopped being true when
#477 merged. the whole rhetorical weight of the wish — the secret leak, the stalled fells — is
real history that has **already been addressed**.

the awkwardness is that a faithful read of the wish produces a no-op diff, and a *useful* read
produces something the wish never asked for (tests). we choose the useful read, and we say so
plainly rather than quietly shipping tests under a "findsert two lines" banner.

### 2. `.agent/.cache/` is a line that does nought

it is dominated by `.cache/` at every depth. we keep it on a documentation-and-future-proofing
argument, which is a **weaker** justification than "it makes git behave differently." a reviewer
who applies `rule.prefer.wet-over-dry` strictly could reasonably call it dead weight. this is a
genuine tradeoff, not a settled point — hence fulcrum **f2**.

### 3. ~~the fourth acceptance criterion is unattainable~~ — retracted, i had it backwards

**an earlier draft of this vision claimed** that `?? .behavior/…` in `git status` made the
criterion *"a fresh worktree shows a clean `git status` after a role boot"* impossible to satisfy.
that was wrong, and the correction belongs on the record.

`.behavior/` is **tracked**:

```
$ git ls-files .behavior | head -3
.behavior/v2025_11_09.cicd.postgres.dataApi/0.[wish].cicd.md
.behavior/v2025_11_22.cicd.github.tfstate/0.wish.md
.behavior/v2025_12_14.absolute-paths/1.blueprint.md
```

it holds committed work product — wishes, blueprints, yields — across many prior behaviors. the
`??` is simply **this behavior's own artifacts, not yet committed**, exactly as every prior
behavior looked before its commit.

so the criterion is **fully attainable**, and there is no residue to flag. more importantly: the
earlier draft's implicit remedy — gitignore `.behavior/` — would have **hidden the repo's own
wishes and blueprints from git**, the precise inverse of the wish's intent, shipped under its
banner. one `git ls-files` was the difference.

### 4. proof-only deliverables feel thin, and are not

the diff will be a test file and one `.gitignore` line. that reads as small. but the acceptance
says **"idempotent — prove it, do not assert it,"** and an unproven idempotency claim is exactly
the class of bug that hides until a second `declapract fix` run corrupts a consumer's file. the
clamp is the deliverable. we should resist the pull to pad it into something that looks bigger.
