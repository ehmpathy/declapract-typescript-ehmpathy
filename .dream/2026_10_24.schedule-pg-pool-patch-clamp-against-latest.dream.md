# 🌙 dream: run the pg-pool patch clamp on a schedule, against the latest pg-pool

- kind: followup
- owner: declapract-typescript-ehmpathy, cicd of this repo
- caught 2026-10-24

## .the cue that fired

a peer review (enroll-impl-arch-defects, i003) noted the vision's claim that a moved line "goes red here before any
adopter re-locks" holds only when this repo's ci runs. its one scheduled workflow is `bump-action-pins`, weekly.

## .the gap, precisely

`src/practices/persist-with-rds/pg-pool-patch.declapract.integration.test.ts` pins its releases (`PG_POOL_RELEASES_IN_RANGE`).
a new pg-pool release that moves the fallback line reaches adopters on their next re-lock; this repo learns of it only
on its next pr. an adopter then meets a pnpm warn and a red `test:lint:cycles`.

## .the shape of the fix

- add `latest` to the clamp's release list (or a `[case2.latest]` that reads `npm view pg-pool version`)
- a scheduled workflow (daily) that runs `npm run test:integration -- pg-pool-patch`, and opens an issue on red
- or fold it into a broader "floor + latest" nightly for every shipped patch
- build `PG_POOL_RELEASES_IN_RANGE` from `npm view pg-pool versions` (every stable release in the range the shipped
  pg floor asks for), so the matrix extends itself and the early signal and the matrix are one mechanism

## .why it is not done in this round

it is a cicd change in a separate practice surface (a new workflow, its permissions, its issue route), outside a
pg-pool cycle fix. safe, but not clean: it ripples into cicd.
