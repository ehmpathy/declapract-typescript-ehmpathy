dream = collapse the CI schema-provision steps in the cicd-service best-practice
`.sql-schema-control.yml` down to a single ghlitch `rhx provision.database` call,
so "everything is via ghlitch" (one skill owns tunnel + grant + plan/apply).

## .what

today the best-practice `.sql-schema-control.yml` runs schema provision as three
explicit steps per job:

```yaml
# plan job (has job-level `env: GRANT: plan`)
- run: npm run prepare:rhachet --if-present
- run: npx rhx use.vpc.tunnel --env ${{ inputs.stage }}
- run: |
    set -o pipefail
    ACCESS=${{ inputs.stage }} npm run provision:schema:plan | tee ./plan.log
# apply job (no GRANT → defaults to apply)
- run: ACCESS=${{ inputs.stage }} npm run provision:schema:apply
```

the ghlitch `provision.database` skill does all three (tunnel + grant +
plan/apply) in one call, so the dream end-state is:

```yaml
- run: rhx provision.database --which livedb --env ${{ inputs.stage }} --mode plan
# and, in the apply job:
- run: rhx provision.database --which livedb --env ${{ inputs.stage }} --mode apply
```

file: `src/practices/cicd-service/best-practice/.github/workflows/.sql-schema-control.yml`

## .status (reassessed 2026-07-20 against ghlitch 0.2.7)

started with 4 blockers; **0.2.7 fixed the two correctness-critical ones. two
remain, both on the prod-apply path.** the reusable workflow is ONE template
driving both prep and prod via the `stage` input, so we can't adopt it for
prep-only — it's all-or-nothing until both remaining gaps land.

| # | blocker | status in 0.2.7 |
|---|---------|-----------------|
| 1 | GRANT-per-mode | ✅ FIXED — `provision.database.sh:196-201` sets `GRANT=plan`/`GRANT=apply` per mode |
| 2 | CI/OIDC auth (no SSO profile) | ✅ FIXED — `use.vpc.tunnel.sh:185` skips keyrack/SSO when `AWS_ACCESS_KEY_ID` already set; uses static creds only, never `AWS_PROFILE`. `use.rds.capacity.sh` no longer does its own cred export (delegates to the tunnel). |
| 3 | "changes planned?" signal | ❌ still absent (behavioral) |
| 4 | prod-apply gate fits CI | ❌ still blocking |

### ✅ blocker 1 — GRANT-per-mode (FIXED in 0.2.7)
`provision.database.sh:196-201`:
```bash
if [[ "$MODE" == "plan" ]]; then
  GRANT=plan npm run provision:schema:plan
elif [[ "$MODE" == "apply" ]]; then
  GRANT=apply npm run provision:schema:apply
fi
```
matches our getConfig contract. plan takes the reader grant, apply the writer.

### ✅ blocker 2 — CI/OIDC auth (FIXED in 0.2.7)
`use.vpc.tunnel.sh:184-194` now short-circuits the local SSO path:
```bash
# skipped when AWS creds are already set (e.g., CI static creds).
if [[ -z "${AWS_ACCESS_KEY_ID:-}" ]]; then
  rhx keyrack unlock --owner ehmpath --env "$ENV"
  AWS_PROFILE=$(rhx keyrack get ... --key AWS_PROFILE --value)
  eval "$(aws configure export-credentials --profile "$AWS_PROFILE" --format env)"
  unset AWS_PROFILE
fi
```
so `configure-aws-credentials` OIDC (which exports `AWS_ACCESS_KEY_ID` etc. with
no profile) is honored as-is. `use.rds.capacity.sh` delegates all cred-sourcing to
the tunnel (its lines 93-96 note), so no SSO assumption remains in the chain.

### ❌ blocker 3 — no "changes planned?" signal (behavioral)
our plan job gates apply on plan output: it `tee`s `./plan.log` and greps for
`"Everything is up to date"` (no changes → skip apply) and `"connect ETIMEDOUT"`
(tunnel failure → fail). `provision.database --mode plan` runs
`npm run provision:schema:plan` with NO logfile passthrough and NO machine-readable
result. adopting it as-is loses the "no-op plan → skip the gated apply" behavior
(the prod approval gate would fire even for an empty plan).
→ ghlitch ask: a `--tee <path>` passthrough, a stdout marker
  (`has-changes-planned=true|false`), or a dedicated exit code for "no changes".

### ❌ blocker 4 — prod-apply gate is local-human-only, dead in CI (BLOCKING)
`provision.database --env prod --mode apply` calls
`uses._.check.sh --meter provision.uses --env prod` (`provision.database.sh:159-162`).
that meter (`uses._.check.sh:47-108`) is a LOCAL human-approval quota: prod needs
an `allowed:local:*` grant a human sets via `rhx provision.uses set --quant 1 --env
prod`. in CI there is no local grant → `blocked:unset` → **exit 2 → prod apply
always blocked.** there is no CI/OIDC bypass.

that meter is correct for local human runs, but in CI the prod-apply authorization
is meant to be the GitHub environment approval + `v*`-tag ruleset (declared in
`provision/github.repo/resources.ts` + `ahbode/infrastructure` OIDC trust), NOT the
local meter.
→ ghlitch ask: a CI-aware path — under CI/OIDC, defer to the github-env gate and
  skip/satisfy the local `provision.uses` meter. make it explicit/opt-in (e.g.
  `--gate ci` / `PROVISION_GATE=ci`), NOT a silent `CI=true` bypass, so a local
  shell can't accidentally skip the meter.

note: prep is ALREADY fine — `uses._.check.sh:48` returns exit 0 for any non-prod
env. a prep-only consolidation would work on 0.2.7 today; the shared template is
the only reason we wait for prod.
