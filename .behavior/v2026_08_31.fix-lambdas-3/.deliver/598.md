## the fix — wake the shared prep cluster whenever a service REACHES it, not only when it OWNS the db

the cicd-common test workflow already runs `npm run start:livedb:prep --if-present` in both the
integration + acceptance shards. but the command lived ONLY in `persist-with-rds` — so a
gateway/fan-out service (owns no db, but invokes peers that query the shared prep aurora-serverless
cluster) never got it, the `--if-present` step no-op'd, and the min-capacity-0 prep cluster stayed
paused. its first query cold-started past the 90s jest timeout and flaked the suite (#598). the same
gap exists at dev-laptop grain: no wake ran before an integration/acceptance run locally.

the discriminant is the same for both halves: a `database.tunnel` block in the consumer's own
`config/prep.json`. that tunnel IS the signal a service reaches the shared cluster — it is declared
whether the service owns the db (persist-with-rds) OR is a gateway that invokes db-querying peers. it
is NOT a `projectPractices` signal (a gateway declares its tunnel in config, not via a db-ownership
practice).

**move 1 — lift the CI wake command to the common denominator (`tests-service`).**
`tests-service` is the lambda-service-only usecase, so it covers gateways AND rds services — the
common home for the wake. added a `start:livedb:prep` = `rhx use.rds.capacity --env prep` entry to its
`best-practice/package.json`, and a tunnel-gated `package.json.declapract.ts` (`FileCheckType.CONTAINS`
contents-fn) that reads the CONSUMER's `config/prep.json` via `getProjectRootDirectory()` and STRIPS
the command when no tunnel is declared. so:
- a tunnel consumer (gateway or rds) gets the wake → the inert `--if-present` step fires.
- a no-tunnel pure-compute lambda has it stripped → the step stays a no-op, never fires
  `rhx use.rds.capacity` against a cluster it does not use (the step has no swallow — a fire against an
  unused cluster could FAIL the job).
persist-with-rds ALSO declares this exact line; both emit the IDENTICAL entry, so an rds service
converges on one entry (the multi-declarer convergence pattern). additive by design — this does not
touch persist-with-rds. and because the command lands in `tests-service`, the extant `.test.yml`
step picks it up with ZERO workflow/snapshot churn.

**move 2 — a local jest globalSetup wake, best-effort, self-gated the same way.**
added `useInfraWake.ts` (a `best-practice/` template emitted at the consumer's repo root, beside the
jest configs it serves — test-scoped, never under `src/**`, per `rule.forbid.test-assets-in-src`):
it returns early on `CI` (the CI half is move 1's job), on `prod`, on an absent `config/prep.json`, and
on a config with no `database.tunnel`; otherwise it runs `rhx use.rds.capacity --env prep` and SWALLOWS
any error (the db may already be warm, or the skill may be unavailable on a given laptop — a wake is a
latency nicety, never a correctness gate).

jest allows exactly ONE `globalSetup`, and both suites already point it at test-fns's autoprune setup.
so the wake must COMPOSE, never REPLACE (the trap the downstream svc-gateway hand-fix fell into — it
set `globalSetup` to a wake-only file and silently dropped autoprune). added
`jest.integration.globalSetup.ts` + `jest.acceptance.globalSetup.ts` composites that
`await useInfraWake({ env: 'prep' })` FIRST, then `await autopruneSetup(globalConfig)` — forwarding the
REQUIRED `globalConfig` arg (autoprune falls back to `false` = falsely accuses a correctly-wired
consumer of the #590 half-wired state if the arg is dropped). the two `jest.*.config.ts` files repoint
`globalSetup` from the direct autoprune subpath to the composite. `globalTeardown` is unchanged. the
composite imports useInfraWake by RELATIVE path (`./useInfraWake`), never `@src` — a
globalSetup loads before jest's moduleNameMapper.

## bounds / not-done

- **the wake is best-effort by design, both halves.** locally it swallows every error; in CI the
  `--if-present` step runs only where the tunnel gate emits the command. a false-negative (a warm-db
  assumption that turns out cold) costs one flaky retry, never a wrong result — so a soft read of the
  neighbor config is safe.
- **no persist-with-rds change.** both practices emit the identical `start:livedb:prep` line; an rds
  service converges. the move is purely additive.
- **`config/dev.json` not handled.** the wake keys on `prep` (the only min-capacity-0 shared cluster in
  play). a `test` tier is local/ephemeral; `prod` is explicitly excluded.
