## scope note

(#551/#552/#553) as an in-scope deliverable. it is NOT a stage/access row — it is a distinct silent

## narrative

the node major that **builds** a serverless artifact and the major that **serves** it can drift.
`build:artifact` traces real `require` chains and copies third-party files into the zip verbatim — it
never transpiles a dependency down to the deploy runtime's syntax level; only the repo's own `src/`
goes through tsc. so a dep can emit syntax the build node accepts, every gate accepts, and the deploy
accepts — yet the lambda cannot parse. the lambda is the sole place the older node ever runs, so
every gate stays green and prod alone breaks.

the incident is real: `aether-auctions/app-employee-web`, 2026-08-03. a pnpm migration moved `.nvmrc`
to `v22`; `serverless.yml` stayed `nodejs14.x` and drifted for months with no symptom. a lockfile
change pulled in `uuid@11` (emits `??=`, needs node 15+). every gate ran on node 22 and passed; the
lambda ran node 14 and threw `SyntaxError: Unexpected token '??='`. the only gate that caught it was
the post-deploy `assure` — after prod already served blank pages.

after this wish, two guards close the gap. first (#552) the practice **derives**
`serverless.yml`'s `provider.runtime` from `.nvmrc`, so the two majors cannot drift — one source, not
two a test compares. second (#553) the acceptance suite serves the built artifact on the **deploy**
major in docker and drives a real request at it, so a dep that skews the syntax floor fails a gate,
not prod.

the aha: **a parity check on two config values is a claim; running the artifact on the node that
serves it is proof.** the fault is silent only because no gate ran the artifact where it lives — so
the cure is to run it there.

## bdd

```
given a repo whose .nvmrc is node 22 and whose serverless.yml runtime is nodejs14.x
  and a prod dependency that emits es2021 syntax (needs node 15+)                              # the app-employee-web chain

when [t0] every default gate runs (unit, integration, local acceptance — all on .nvmrc node 22)
  then all pass                                                                                # today — silent
  and the lambda (node 14) throws `SyntaxError` only after deploy, mid-request

when [t1] the post-wish parity practice runs (#552, runtime derived from .nvmrc)
  then serverless.yml states `nodejs22.x`, derived — not a second value to drift
  and a hand-edit back to nodejs14.x is rewritten by fix (or fails a check), never silently kept

when [t2] the post-wish acceptance suite runs the artifact on the DEPLOY node (#553)
  then it serves `.artifact/contents` under `node:<deploy-major>` in docker
  and it fetches `/` and asserts a 200 AND a rendered document                                 # a require alone misses the mid-request throw
  and the syntax-floor break fails HERE, before deploy — loud, named, pre-prod

when [t3] the deploy workflow gates on the runtime job
  then a red runtime gate stops the deploy before `sls deploy` runs
  and the prior last-line-of-defense (post-deploy assure) is no longer the first to see the break
```

## the fail-safe

this is a fail-safe by **running the truth**, not by inspection of a proxy. the sharp edge — a lambda
that cannot parse its own artifact — was silent for one reason: no gate executed the artifact on the
node that serves it. the two guards remove that reason: `[t1]` makes the two majors one derived value
(they cannot drift), and `[t2]` runs the real artifact on the real deploy major with a real request
(the break cannot hide behind a load-only check or a right-artifact/wrong-node pass). the
pit-of-success: the correct gate is the default gate — `start:prod:server` **is** the deploy-node
launcher, so there is no second command that serves prod on the build node to be taken by accident.

> **two traps the incident taught, both worth encoded guards** (from #551/#553):
> - **a handler `require` is not a request.** the framework pulls page code per request, so the throw
>   lands after a `200` is already sent. a load-only check reports a false pass — only a real fetch of
>   `/` reaches the code that throws.
> - **the port is not the server.** a boot-wait that polls the url and reads "the port answers" as
>   "our server is up" can drive a stray container on that port and prove no claim about the artifact.
>   the practice must refuse to start when the port is already held, and preflight `docker info` so an
>   absent daemon names its own cause rather than reads as an app fault.

## the honest cost

`npm test` inherits a docker dependency, because the acceptance suite does — the price of one gate
rather than two. the alternative (fall back to the build node when no daemon is present) is exactly
the failure this practice removes: a suite that reports green while it proves something weaker than it
claims. fail loud instead. repo-specific values (the expected title asserted on `/`, the localhost
domain + port, `DEPLOYMENT_STAGE`) come from declapract variables, not hardcodes.
