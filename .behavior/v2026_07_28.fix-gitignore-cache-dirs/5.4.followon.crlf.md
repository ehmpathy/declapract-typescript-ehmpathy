# follow-on: the line model is thinner than the file format it parses

three gaps, one root. `defineExpectedGitignoreContents`
(`src/utils/defineExpectedGitignoreContents.ts`) treats a `.gitignore` as **a list of pattern
strings**. a real `.gitignore` is more than that — it has line endings, comments, and a tail whose
order carries load. each gap below is a place where that thinner model diverges from the format.

all three are **pre-extant** — `git show main:src/practices/git/best-practice/.gitignore.declapract.ts`
carries the identical parse — and all three sit outside #535's scope fence (*gitignore template
only, cache-dir lines*), per the wisher's f4 "stay narrow" verdict. filed together because a fix
that addresses one in isolation would likely have to be redone for the next.

| # | gap | severity | grade |
|---|---|---|---|
| 1 | CRLF input duplicates the tail and hoists a negation | **inert negation** — same class as #537 | blocker-shaped, out of scope |
| 2 | a comment sorts away from the lines it describes | surprise, per `rule.forbid.surprises` | nitpick |
| 3 | the emitted tail carries no signal that its order carries load — ⚠️ **maintainer half already fixed**, consumer half open | invites the edit that causes gap 1's failure mode | nitpick |

---

## gap 1 — CRLF splits into lines the ordered test cannot match

the tail is held out of the sort by **exact string match**:

```ts
const ignoresFromFile = input.contents ? input.contents.split('\n') : [];
const orderedPatterns = new Set(ignoresOrderedForGitignore);
const ignoresFromFileSortable = ignoresFromFile.filter(
  (line) => !!line && !orderedPatterns.has(line),
);
```

a consumer `.gitignore` with **CRLF** endings splits into lines that each end with a carriage
return, so the ordered-pattern test misses every one of them.

### the defect, traced rather than guessed

| step | CRLF input |
|---|---|
| split on the newline | each line keeps a carriage return at its end |
| the ordered-pattern test | **false** — the set holds the bare `node_modules` |
| so the line is | kept as **sortable**, sorted in among the alphabetical lines |
| and the tail is | still appended after |

result: a carriage-returned `node_modules` sorted into the middle **and** a second, bare
`node_modules` + negations block at the end. the hoisted copy sits **above** its negations, which is
the inert-negation state — the exact defect the ordered class exists to prevent.

an inert negation silently re-ignores every test-fixture `node_modules` the tail protects, and the
file still **reads** as correct. same failure mode as #537, reached by a different route.

### coverage today

**none.** 13 review rounds, the vision's 9 edgecases, and both new suites all miss it.

### the fix, and the clamp it owes

likely a cast of the parsed lines that drops a terminal carriage return before the ordered-pattern
test — but the emitted file's own line endings must be decided too, not merely the parse.

per `rule.require.clamp-edge-cases` the fix owes a clamp **shown** to bite: a CRLF fixture that goes
red before and green after, at both the unit and integration grain. and per
`rule.require.idempotent-fixes`, twice-applied on CRLF input must be a fixed point.

### credit

found by the `enroll-impl-behavior-intent` peer reviewer on #535's l3 round — explicitly graded a
nitpick, not a blocker, with a follow-on recommended rather than a scope expansion.

## gap 2 — a comment sorts away from the lines it describes

same filter, different gap. a comment line is **neither ordered nor empty**, so `!!line &&
!orderedPatterns.has(line)` keeps it, and it is sorted like a pattern.

in ascii `#`(35) < `*`(42) < `.`(46), so a comment sorts to the **top of the file** — above every
pattern, detached from the lines it was written to annotate:

```
# custom project ignores      ← the human wrote this above .idea
.idea
*.pyc
```

becomes

```
# custom project ignores      ← now at the top, annotates the whole file
*.pyc
*.bak.*
…
.idea                         ← the line it described, 8 rows down
```

**`rule.forbid.surprises`**: the annotation still exists, and it now annotates the wrong region.

### coverage today

**none.** `should preserve custom ignores and append required patterns`
(`src/practices/git/best-practice/.gitignore.declapract.test.ts:80`) feeds exactly this fixture — a
`# custom project ignores` comment above `.idea`, `*.pyc`, `__pycache__` — and asserts all three
patterns survive. it makes **no assertion whatsoever** about where the comment landed. the comment
is in the fixture and absent from every expectation, so the behavior is unobserved rather than
blessed.

### the fix, and why it is not a one-liner

a comment is not a pattern; it belongs **with the line beneath it**. so the real fix teaches the
algorithm a third line class — ordered-with-successor — alongside `sortable` and `ordered`. that is
a change to the model of what a line IS, which is why it earns a wish rather than a patch.

the clamp it owes: a fixture whose comment sits above a specific pattern, asserted to still sit
above that same pattern after the fix, **shown** to go red without it.

## gap 3 — the emitted tail carries no signal that its order carries load

the file this code writes ends:

```
node_modules
!.test*/**/node_modules
!.test*/**/node_modules/**
```

to a human who sees an otherwise perfectly alphabetized file, those three read as an oversight. the
obvious tidy-up is to sort them in — which hoists `!.test*/**/node_modules` **above**
`node_modules` and turns the negation inert. that is gap 1's failure mode, reached by a well-meant
human edit rather than by a parse bug.

**`rule.prefer.prevent-over-correct`** puts "make it hard" above "report it well". the emitted file
currently does neither: no constraint, no signal.

### ⚠️ correction — this gap has TWO audiences, and one half is already closed

an earlier draft of this file said flatly that *"gap 3 cannot be fixed until gap 2 is."* **that was
too broad.** it conflated two different humans who reach the tail by different routes:

| audience | reaches the tail via | blocked on gap 2? |
|---|---|---|
| **a maintainer** who edits `ignoresOrderedForGitignore` or the declaration in THIS repo | `src/practices/git/best-practice/.declapract.readme.md` | ❌ **no** — the readme is not parsed, not sorted, not subject to gap 2 at all |
| **a consumer** who opens their own emitted `.gitignore` and sees three unsorted lines | the emitted file itself | ✅ yes — the only in-file channel is a `#` comment, and comments sort |

**the maintainer half is fixed.** `src/practices/git/best-practice/.declapract.readme.md` gained
§*"the emitted tail looks unsorted. it is not. do not tidy it."*, which states the hoist mechanic,
names the clamp that catches it, and — the part the readme did not previously carry — distinguishes
**two causes with one symptom**:

- a *second declarer* with a divergent tail (the convergence section already covered this), and
- a *single well-meant tidy-up* by one person, with no drift and no second practice involved

only the first was documented. the second needs no divergence at all, which makes it the likelier
of the two, and it was unnamed.

`.declapract.readme.md` is a **declaration**-side doc, never copied into a consumer repo — verified:
all 116 copies live under `src/practices/` or `dist/practices/`, and this repo, which consumes its
own practices, has none at its root. so it reaches exactly the maintainer audience and no other.

**the consumer half stands, and stays blocked on gap 2.** a consumer repo never sees that readme.
the only surface that reaches them is their own `.gitignore`, and the only channel in it is a
comment — which gap 2 would sort to the top of the file, far from the tail it describes. so the
remedy would be both useless and an instance of the very defect it warns about.

that residual dependency is still the argument for one wish over three.
