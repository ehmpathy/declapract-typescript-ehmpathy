## provision.yml is usecase-aware — the rds jobs gate on persist-with-rds (D28)

`provision.yml` carries 4 rds-coupled jobs (`sql-schema-{prep,prod}`,
`aws-{prep,prod}-declastruct`) whose callees — `.sql-schema-control.yml` and the
`provision/aws/resources.ts` wish — are shipped by `persist-with-rds`, not by this practice. so
`provision.yml.declapract.ts` emits those 4 jobs **only** when `persist-with-rds` is in the resolved
practice set; a service without rds (`lambda-service`, `lambda-service-with-dynamodb`) gets the
generic jobs (terraform ×3, github) alone. this is the D28/#573 gate: a caller that names a callee
another practice supplies must be reconciled against that practice's presence. it uses `CONTAINS`
(not `EQUALS`) so a narrow `declapract fix --practice cicd-service` never strips an rds repo's jobs.
the persist-with-rds side documents the same gate from the callee's view.

### the gate is fix-forward for fresh scaffolds

a `CONTAINS` check passes when the file holds the declared narrowed content, so a pre-extant non-rds
repo that already carries the full superset keeps its rds jobs — the gate emits the narrowed workflow
for a fresh scaffold, and an extant non-rds repo is a one-time hand-strip of the 4 rds jobs.
