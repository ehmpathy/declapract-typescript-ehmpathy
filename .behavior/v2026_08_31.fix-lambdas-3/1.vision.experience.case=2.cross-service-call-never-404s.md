# case=2 — cross-service-call-never-404s

**actor** consumer-dev · **feel** happy · **care** critipath · the transition's core promise

> ⚠️ `[tn]` demos are illustrative sketches — no code exists yet.

## narrative

`svc-gateway` calls `svc-jobs` to fetch a job. today, in prep, gateway asks for
`svc-jobs-prep-getJob` while jobs published `svc-jobs-dev-getJob` — a `ResourceNotFoundException`
that reads like a deploy fault (H22/D31). the two services would have to cut over in lockstep to
agree, and a lockstep across a fleet is a flag-day gamble.

after this wish, both services dual-publish through the transition. gateway addresses jobs with the
helper: while jobs is still `Ancient` (published `-dev-` only), gateway uses
`sdkAwsLambdaEnvAccessAncient` → `dev`, and the call lands. when jobs finishes its own migration and
publishes `-prep-`, gateway flips that one call site `Ancient → Contemp`. no call 404s in between,
and neither service waited on the other.

the aha: `grep AccessAncient` in gateway is the exact list of peers gateway still owes a migration —
the code IS the ledger.

## bdd

```
given svc-gateway calls svc-jobs, both mid-transition, tier=prep
  and svc-jobs is still Ancient (publishes svc-jobs-dev-* only)

when [t0] gateway addresses jobs with `sdkAwsLambdaEnvAccessAncient`
  then the invoke targets `svc-jobs-dev-getJob`
  and the call lands (the -dev- fleet is live)

when [t1] svc-jobs dual-publishes and becomes Contemp (svc-jobs-prep-* now live)
  then BOTH `svc-jobs-dev-getJob` and `svc-jobs-prep-getJob` answer                           # dual-publish window
  and no gateway call has 404'd across the flip

when [t2] gateway flips the one call site `Ancient → Contemp`
  then the invoke targets `svc-jobs-prep-getJob`
  and `grep AccessAncient` in gateway no longer lists svc-jobs                                # ledger decrements

when [t3] a reviewer audits gateway's outbound migration debt
  then `grep AccessAncient src/` lists every call site still on an Ancient peer   # import-presence, the reliable signal
  and zero hits = zero unmigrated peers = gateway's outbound migration complete   # the exit is presence→absence, not an exact count
```

> the ledger is read as **import-presence, not occurrence-count**: a caller that aliases or wraps the
> helper still imports it, so the hit-count need not be 1:1 with peers. any hit = debt remains; zero
> imports = the exit. (this matches the yield's ledger correction — a reliable presence signal, an
> approximate per-peer count.)

## the fail-safe

not sharp, but the pit-of-success is the **no-lockstep** property: a service that has not migrated
yet is addressed correctly by `Ancient`, so a slow peer never breaks a fast caller. the only way to
404 is to flip a call site to `Contemp` before the peer publishes `-prep-` — which the ledger
discipline (flip only after the peer dual-publishes) prevents.

## where the client lives (inventory row 19, #532)

the call site above is not a hand-maintained `data/clients/svc*.ts`. #532 establishes `access/svcs/*`
as a **generated** sdk location — codegen from live lambda contract introspection
(`npx sdk-aws-lambda gen --for <svc> --into src/access/svcs/ --env prep`, sdk-aws-lambda@0.3.0) — and
deprecates the hand-transcribed pattern. the generated `<svc>.mechanisms.ts` wraps `askLambdaEndpoint`
with the target function name, which is exactly the `dev`-vs-`prep` slug the
`sdkAwsLambdaEnvAccess{Ancient|Contemp}` helper resolves. so the generated client is the natural home
for the target-resolution, and `grep AccessAncient` reads across `access/svcs/` as the same ledger.

a hand-maintained client is itself an instance of the wish's meta-lesson: it **emits a contract-shape
value** (the transcribed request/response types) that no gate verifies against the upstream, so it
drifts silently. the codegen makes drift a reviewable diff (re-gen) rather than a runtime bug.
