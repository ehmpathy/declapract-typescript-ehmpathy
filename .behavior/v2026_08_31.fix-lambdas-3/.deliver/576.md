## the defect — the blessed pnpm pin was a PHANTOM version (10.31.7), never published

the pnpm practice pinned `packageManager: pnpm@10.31.7` in its best-practice `package.json`. that
version was never published to the npm registry. corepack reads `packageManager` and, on the FIRST
pm command in a consumer, tries to fetch that exact version — a 404 on an unpublished pin bricks
EVERY `pnpm`/`npm`/`corepack` invocation in the repo, not a lint nit but a repo-wide outage. every
consumer that took this practice inherited a pin corepack could not fetch.

## the fix — bump to the real latest-10.x (10.33.4), across every declarer + fixture

sedreplaced `10.31.7` → `10.33.4` in the 8 files that carried it:
- `pnpm/best-practice/package.json` — the pin itself
- `pnpm/best-practice/package.json.declapract.ts` — the CONTAINS check's expected pin
- `pnpm/best-practice/.declapract.readme.md` — the doc
- `pnpm/best-practice/__snapshots__/.declapract.integration.test.ts.snap` — the pipeline snapshot
- `pnpm/.test/assets/repo-npm-to-pnpm/package.json` — the migration fixture's seed
- `pnpm/.declapract.integration.test.ts` — the pinned assertions
- `cicd-app-react-native-expo/.declapract.integration.test.ts` — the expo migration's pinned pin
- `cicd-app-react-native-expo/__snapshots__/.declapract.integration.test.ts.snap` — its snapshot

## the durable guard — a registry-existence clamp so a future phantom pin reddens in CI, not a consumer

added `[case3]` to `src/practices/pnpm/.declapract.integration.test.ts`: read the pin the
best-practice SHIPS, extract the version after the `@`, and put the question to the npm registry
itself via `npm view pnpm@<version> version`. a pin that 404s (unpublished) throws in the harness
here, so the next bump to a phantom version reddens THIS suite rather than a bricked consumer's
corepack.

this is the ticket's durable ask: the check reads the shipped pin, not a hardcoded expectation, so
it stays correct across every future bump.

## the [case2] reframe — the convergence direction flipped

`[case2]` seeded the pin OFF the blessed version to prove the convergence rewrite. it was written
as `10.32.1` "AHEAD" of a `10.31.7` blessed pin — a DOWNGRADE. with the blessed pin now `10.33.4`,
`10.32.1` sits BELOW it, so "ahead"/"downgrade"/"DOWN" are all false. reframed to
`[case2] a repo OFF the blessed pnpm pin (10.32.1)` proving the convergence rewrite `10.32.1 →
10.33.4` in either direction — the org-standardization intent, unchanged in mechanism.

## the test-fns ride-along resnap

the test-fns floor bump (this repo's own dep + the practice floor already at 1.17.0) converges the
expo migration fixture's settled `package.json` to `test-fns: 1.17.0`. the `[t6]` before+settled
snapshot in `cicd-app-react-native-expo/.declapract.integration.test.ts` was resnapped to accept
that one-line diff (`1.15.8` → `1.17.0`) — a benign downstream effect of the floor bump, not a
regression.

## verification

- pnpm integration: 16/16 green — including `[case3]`, which made a REAL `npm view pnpm@10.33.4
  version` call and confirmed the pin is published.
- cicd-expo integration: 53/53 green after resnap, stable on a re-run without `--resnap`.

## clamp teeth

`[case3]` bites by construction: revert the pin to a phantom version (e.g. `10.31.7`) and the
`npm view` call errors (non-zero exit, execFileSync throws) or prints empty — the assertion
`expect(published).toContain(pinnedVersion)` goes RED. the real published `10.33.4` makes it GREEN.

## bounds

- the registry check is an INTEGRATION test, not a unit — `npm view` crosses the network (a remote
  boundary forbidden in unit tests per `rule.forbid.unit.remote-boundaries`).
- `10.33.4` is the latest 10.x at delivery; a future bump is safe as long as the target is
  published — which is exactly what `[case3]` now enforces.
