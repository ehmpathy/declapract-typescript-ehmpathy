provisions github repository settings and environments via declastruct-github-sdk.

## main requires one review approval

- main's protection requires its status checks and one approval before a merge. a green pr still
  waits for a human read
- a push after approval drops the approval (`dismissStaleReviews`), so no commit merges unread.
  with `strict` checks, an update from main drops it too: a pr open across a main merge needs a
  re-approval
- `enforceAdmins` holds admins to the rule; an exception is a deliberate settings change
- the release pr (rhelease app) waits for an approval like any other. its merge is the prod gate
- github forbids an author's approval of their own pr: a repo with one human with write merges
  prs the bot authors, never prs that human authors
- no CODEOWNERS is declared, so github requests no reviewer on its own: a pr waits until someone
  asks for a review
- a green pr with automerge on waits for its approval, then merges; a release watch that ends
  before the approval reads a timeout, not a failure
- the release pr is rewritten on each push to main, and a rewrite drops its approval
  (`dismissStaleReviews`). approve it after the last merge you mean to ship
- the provision workflow applies on push to main, so the merge of the upgrade pr that brings this
  file sets the rule

## repo visibility fails closed

- the repo provisions **private** unless `package.json` declares `"private": false`. an absent key,
  a `null`, a string, or any other value provisions it private
- `package.json` always declares `private` as an explicit boolean. where it is absent or not a
  boolean, the `implicit-package-privacy` fix backfills `"private": true`. an explicit `true` or
  `false` is never touched
- a repo meant to be public declares `"private": false`, by hand, when its owner is ready to
  publish that domain. no practice sets it on the owner's behalf
- `"private": true` also makes `npm publish` refuse. a package published to npm declares
  `"private": false`
