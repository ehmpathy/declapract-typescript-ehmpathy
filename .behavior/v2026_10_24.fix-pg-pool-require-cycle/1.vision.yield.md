# 1.vision: the pg <-> pg-pool require cycle no longer fails the cycle check

## the outcome world

an rds adopter runs `declapract apply`, then `pnpm install`, then `npm run test:lint:cycles`. it reports no pg <-> pg-pool cycle. no repo
carries a patch of its own; the practice that ships `pg` also ships the patch for the cycle `pg` drags in.

| | before | after |
|---|---|---|
| fresh rds adopter | cycle check red: `pg/lib/index.js -> pg-pool/index.js -> pg/lib/index.js` | no pg-pool cycle, with no per-repo edit |
| svc-service-providers | carries `patches/pg-pool@3.14.0.patch` by hand | its patch is redundant; the practice patch covers every pg-pool version |
| next pg-pool bump | the hand patch goes stale; `stale-patched-dependency` drops it; the cycle returns | the bare-name key is never stale; the patch holds |

aha: the patch lands once, in `persist-with-rds`, and every repo that adopts it inherits a cycle check free of the pg-pool cycle.

## the patch

pg-pool's `index.js` holds `this.Client = this.options.Client || Client || require('pg').Client`. pg passes its own
`Client` into the pool, so the fallback never runs under pg. dpdm reads it statically and reports a cycle.

`persist-with-rds` ships:

- `patches/pg-pool.patch` — drops `|| require('pg').Client` (the same hunk svc-service-providers proved). a text
  header above the first `diff --git` line names why it exists, the fix if it ever stops to apply (upgrade
  declapract-typescript-ehmpathy, then re-apply), and the fix for a direct `pg-pool` caller
  (`{ Client: require('pg').Client }`). pnpm's patch-failure warn names this file, so the file teaches the fix
- `package.json` → `pnpm.patchedDependencies: { "pg-pool": "patches/pg-pool.patch" }` — a **bare-name** key, so it
  covers every pg-pool version, and `stale-patched-dependency` never judges it stale

the shipped `.dpdmrc.yaml` keeps `exclude: []`. the policy stands; the cycle is gone, not hidden.

## evaluation

| option | verdict |
|---|---|
| exclusion in `.dpdmrc.yaml` | rejected. pg is a prod dep; `rule.forbid.dpdm-exclude-change` makes it a blocker, and the check already rejects `node_modules` entries |
| version pin | rejected. the fallback is in every pg-pool release read: 2.0.0, 3.6.0, 3.14.0 |
| shipped patch, exact key `pg-pool@3.14.0` | rejected. stale on the next bump; our own `stale-patched-dependency` then deletes it |
| **shipped patch, bare-name key** | **chosen.** one file, survives bumps, owned by the practice that ships pg |

pros: policy intact; no per-repo work; prior hand patches still hold (exact key outranks bare name).
cons: a patch on a third-party package is upkeep we own. if pg-pool moves the line, the hunk no longer applies.

edgecases:

- pg-pool moves or drops the line → the patch fails to apply. the pnpm practice ships `pnpm.ignorePatchFailures:
  true` (#680), so the install only warns and pg-pool lands unpatched. the cycle check is the signal: it goes red with
  pg <-> pg-pool, in this repo's usecase walk on its next ci run, and in an adopter's lint if they re-lock first.
  case 3.
- repo imports `pg-pool` directly and calls `new Pool()` with no `Client` → the patch removed the fallback, so
  `this.Client` is undefined and the first connect throws. every persist-with-rds template uses `pg`'s `Client` and
  never imports `pg-pool`, and `pg.Pool` always passes `Client`. the throw is loud and points at the pool. a human who
  calls it direct passes `{ Client: require('pg').Client }`. named here, since the patch changes runtime behavior for that caller.
- repo has no pg → `persist-with-rds` is not in its usecase; no patch ships. impossible cell.
- repo already holds `pnpm.patchedDependencies` → the CONTAINS check deep-merges; its other keys survive.

## open questions & assumptions

- [research] does pnpm 10.34.5 (the pinned `packageManager`) honor a bare-name `patchedDependencies` key? pnpm docs
  state keys may be "an exact version, a version range, or just the name", but name no version that added it. the
  real install in the `[t3]` walk answers it; a range key `pg-pool@^3` is the fallback.
- [research] does the hunk fit an older in-range pg-pool (e.g. 3.6.0), where line 92 differs? one `pnpm patch`
  dry install against 3.6.0 in execution answers it (inventory rows #4–#6, #32; case=4).
- [research] does pnpm's patch parser accept a text header above the first `diff --git` line? one install answers it;
  if not, the header moves to a `persist-with-rds` readme line, and the warn still names the file.
- [research] is the cycle red without the patch here, as downstream reported? the `[t3]` step, run before the patch
  lands, answers it — owed first in execution.
- [answered] does a patch that fails to apply halt the install? no — `pnpm/best-practice/package.json.declapract.ts`
  ships `pnpm.ignorePatchFailures` + `pnpm.allowUnusedPatches`. the cycle check, not the install, is the signal.
- [answered] do an adopter's other `pnpm.*` keys survive the apply? yes — the CONTAINS fix deep-merges (same file's
  `.why`). the walk's convergence step confirms a nested `patchedDependencies` with a string value stays converged.
- [answered] should a bad practice retire an adopter's own `pg-pool@<version>` hand patch? no — it goes stale on the
  next bump and `stale-patched-dependency` retires it.
- [answered] does the wisher need to pick the patch? no — the wish named a shipped patch among the allowed fixes, and
  the other two fail on evidence (policy blocker; fallback in every release).

- pg@8.23.1 depends on `pg-pool: ^3.14.0`

## what is awkward?

- we patch a package we do not own, for a cycle that never runs. the alternative is to break our own policy.
- the patch lives in `persist-with-rds`, while the symptom shows in `lint`. ownership follows the cause: the practice
  that ships pg owns what pg brings.
- the test vehicle is the slowest suite in the repo. it is also the only one that walks the adopter's real path.
