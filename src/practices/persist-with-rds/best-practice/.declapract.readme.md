| variable | description | default |
|----------|-------------|---------|

## the pg-pool patch

pg-pool's pool falls back to `require('pg').Client` when no `Client` is passed. dpdm reads that
require statically, so every repo with pg + pg-pool fails `test:lint:cycles` on `pg <-> pg-pool`
(the check reads node_modules too, by policy). this practice ships
`patches/pg-pool.patch`, which drops the fallback, under the bare-name key
`pnpm.patchedDependencies["pg-pool"]`:

- the bare name never goes stale, so the stale-patch check never retires it; the hunk fits every
  stable pg-pool release in `^3.2.1`, which `pg@8.3.0` asks for
- a repo's own exact-version key (`pg-pool@<version>`) outranks it at install, and both survive the apply.
  a hand patch of the same line may be deleted, key and file
- after an apply, run `pnpm install` and commit the lockfile: it records the patch hash, so a ci
  `--frozen-lockfile` install fails until it does
- pg passes its own `Client` into every pool it builds, so code that goes through `pg` sees no change.
  code that calls `new Pool()` from pg-pool directly must pass `{ Client: require('pg').Client }`
- if pnpm warns that the patch failed to apply, pg-pool moved the line: upgrade
  declapract-typescript-ehmpathy and re-apply. if no fix has shipped yet, pin your own
  `pg-pool@<version>` patch; its exact key outranks the bare one
- to recut the hunk, keep one context line on each side of the changed line. wider context misfits
  older releases in `^3.2.1` (3.2.1–3.4.1), and pnpm then installs pg-pool unpatched

## ssm parameters

the provision wish (`provision/aws/resources.parameters.ts`) declares the db credentials at the
names sdk-config derives for a bare `$.at(aws::param)`:

| parameter name | description | environments |
|----------------|-------------|--------------|
| `/{org}/{project}/{config}/database.role.cicd.for-plan.password` | password for the cicd plan user | prep, prod |
| `/{org}/{project}/{config}/database.role.cicd.for-apply.password` | password for the cicd apply user | prep, prod |
| `/{org}/{project}/{config}/database.role.crud.password` | password for the crud user | prep, prod |

a repo whose values sit at a prior name (or under `role.admin` / `role.service`) copies them to
these names before its first provision apply — the map is in `provision/aws/readme.md`.

prep users are created with the `__CHANG3_ME__` password by `provision/schema/deploy.database.sh`,
so `config/prep.json` accepts either `__CHANG3_ME__` or `$.at(aws::param)` at each password.

## config grants

`src/utils/config/config.schema.ts` exports one schema per oidc grant:

- `apply` (the default: the apply job, the cloud runtime, local dev, tests) requires every secret,
  so `Config` carries no `| undefined` and consumers need no guards
- `plan` marks `role.cicd.for-apply.password` and `role.crud.password` optional. the prod plan
  job's oidc role may read only the for-plan credential, and sdk-config substitutes `undefined`
  for each param a role is denied
- `for-plan` and `for-apply` each carry a username, since a plan job may map to a readonly db user

the grant is an argument, never read inside the schema; `getConfig` picks the schema at call time
(see the `config` practice readme).

## a stateful store gets an alias, never a copy, across the dual-publish transition

the `serverless` + `environments` practices dual-publish each lambda fleet under both slugs
(`-dev-` ancient, `-prep-` contemp) through the `-dev-`→`-prep-` slug transition. a stateless lambda
is safe under two names. a stateful store is not.

this RDS cluster (and its SSM credential params, its S3 buckets, its SQS queues) stays one store
reached by two pointers — a Route53 CNAME, an SSM pointer, or an ARN — never two clusters.

a second `-prep-` RDS cluster is never stood up to satisfy dual-publish. two independent clusters
form a write-`-dev-`/read-`-prep-` split: the ancient fleet writes one, the contemp fleet reads the
other, and the divergence stays silent until data is absent. the alias points at the one cluster.

no data migration is needed: the runtime DB path resolves `config.database.tunnel.lambda.host` (see
`src/utils/database/getOneDatabaseConnection.ts`), an access-keyed config value
(`databaseClusterHost.{prep,prod}`) with no deploy-slug token, so a CNAME re-points the one live
cluster with zero data moved. which alias mechanism to use is unsettled; the invariant "one store, two
pointers" holds regardless.

## the provision workflow's rds jobs are gated behind this practice (D28)

`cicd-service`'s `provision.yml` carries 4 rds-coupled jobs — `sql-schema-{prep,prod}` (the
`.sql-schema-control.yml` callee, driven by this practice's schema + daos) and
`aws-{prep,prod}-declastruct` (the `provision/aws/resources.ts` wish this practice ships). the gate
lives in `cicd-service/best-practice/.github/workflows/provision.yml.declapract.ts`: a usecase-aware
`contents` fn emits those 4 jobs **only** when `persist-with-rds` is in the resolved practice set, so
a service **without** rds (`lambda-service`, `lambda-service-with-dynamodb`) does not inherit a
`provision` workflow that references files it lacks. it uses `CONTAINS`, not `EQUALS`, so a narrow
`declapract apply --practice cicd-service` cannot strip an rds repo's own jobs (the additive-delta
EQUALS hazard). if you add a new rds-coupled provision job, add it to that gate the same way — a
caller that names a callee this practice supplies must be reconciled against this practice's presence.
