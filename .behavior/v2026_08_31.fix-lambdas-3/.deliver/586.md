## the shape — the org `useKeyrack` convention, at the tests-node practice

`src/practices/tests-node/best-practice/useKeyrack.ts` — the org one-line `useKeyrack` orchestrator
(the svc-jobs / svc-notifications convention) over three pure, boundary-injected leaves. both jest
envs call it in ONE line — `useKeyrack({ env: 'test' })` (integration), `useKeyrack({ env, mode:
'strict' })` (acceptance) — rather than re-derive the keyrack.source → set-ACCESS → v2-export
sequence inline.

- `useKeyrack` — the entrypoint: skip in CI, skip when the consumer declares no `.agent/keyrack.yml`,
  `keyrack.source` the tier, set `ACCESS` when the tier is not `test`, and — only for an aws consumer
  (`declapract.use.yml` names `awsAccountId`) — export the sso profile's static creds via the leaves
  below. it composes the injectable leaves, so this repo's test-coverage standard holds (the org's
  verbatim inline version is untestable at the boundary).
- `exportAwsCredentialsFromSsoProfile` — shells to `aws configure export-credentials --format env`
  (profile passed as an argv element, never a shell string — no injection), parses the
  `export KEY=VALUE` lines, throws a `ConstraintError` (exit 2) that NAMES the fix on a failed export.
- `spliceAwsStaticCredsIntoEnv` — splices ONLY `AWS_`-prefixed creds into the injected `env`, then
  `delete env.AWS_PROFILE`. the removal is DELIBERATE and must persist the suite lifetime: aws-sdk v2
  prefers `AWS_PROFILE` over static creds when both are set, so a "restore" would reintroduce the
  exact auth-against-no-target defect this guard closes.
- `getOneAwsSsoProfileFromEnv` — reads `env.AWS_PROFILE` or throws a `ConstraintError` that names the
  `.agent/keyrack.yml` key to declare (the #564 kin: the practice cannot ship a consumer's
  gitignored keyrack, so it tells the consumer exactly what to add).

the util is test-scoped beside the jest configs it serves, never under `best-practice/src/**` (the
consumer's prod tree) — the placement `rule.forbid.test-assets-in-src` mandates.

## why this is the wish's meta-lesson (case=6, suite-on-arrival class)

keyrack.source sets only `AWS_PROFILE`, and v2 cannot derive an sso profile from it — so the suite
auths against no target and dies on arrival, kin to #564's AWS_PROFILE gap. the fix is a single
practice-owned guard for that v2 boundary: every repo that invokes lambdas in tests inherits it
rather than rediscovers it after an opaque credential failure. the boundary is INJECTED (`exec`,
`env`, `exportCreds`), so both the failure path and the all-clear path are pure and clamped.
