# 1.vision.experience.dimensions

two actors meet this behavior, in two spaces that do not share a repo shape. the actor picks the space; it is not an
axis crossed with the others.

- **adopter** — a repo owner who applies the practice to a repo with its own history and code
- **maintainer** — this repo's ci, which applies each usecase to a fresh clone of `src/.test/assets/typecheck-templates/repo-bare`

## the adopter space

| axis | values | orthogonal because |
|---|---|---|
| A1 repo pg state | `rds` (persist-with-rds adopted, pg installed) · `no-pg` | set by the usecase the repo declares; no other axis moves it |
| A2 patch map before apply | `empty` · `other` (keys for other packages only) · `own` (its own `pg-pool@<version>` key + file only) · `own+other` (both) | the four values partition the map: each repo holds exactly one. set by the repo's own history; independent of which pg-pool release the lockfile pins, and of how code calls the pool |
| A3 pinned pg-pool release vs shipped hunk | `fits` (the line sits where the hunk says) · `offset` (same line, other line number — an older in-range release) · `moved` (upstream changed or dropped the line) | a property of the release the lockfile pins; independent of the repo's patch map and its call style |
| A4 pool caller | `via-pg` (`pg.Pool`, or `pg.Client` alone) · `direct` (imports `pg-pool`, `new Pool()` with no `Client`) | a property of the repo's own code; the patch map and the release do not decide it |

`age` and `fit` were two faces of one axis (an older release is what makes the hunk land at an offset), so they are one
axis, A3.

product: A1=`rds`: A2 × A3 × A4 = 4 × 3 × 2 = 24 cells. A1=`no-pg`: no pg-pool is installed and no patch ships, so
A3 and A4 hold no value; A2 alone varies = 4 cells. 28 cells.

## the maintainer space

| axis | values | orthogonal because |
|---|---|---|
| W1 usecase pg state | `rds` (`lambda-service-with-rds`) · `no-pg` (every other usecase) | set by which usecase the walk applies; the walk applies each one |
| A3 pg-pool release vs shipped hunk | `fits` · `offset` · `moved` | set by the registry's latest in-range release at run time |

the repo shape is fixed by construction: the walk clones a bare repo that holds no patch map and no code beyond what
the usecase emits. so A2 is always `empty` and A4 always `via-pg` here — not a correlation between axes, but a
constant of the space. each excluded cross still gets its own `impossible` row in the inventory.

A3 holds no value on W1=`no-pg` (no pg-pool is installed), the same rule as the adopter's no-pg branch.

product: W1=`rds` × A3 = 3 cells, W1=`no-pg` = 1 cell, plus 4 `impossible` rows for the constant crosses
(A2=`other`, `own`, `own+other`; A4=`direct`).

## held to one value, by the toolchain pin

- pnpm version: the pnpm practice pins `packageManager: pnpm@10.34.5` for every adopter. whether that pnpm honors a
  bare-name `patchedDependencies` key is one fact for all cells, not an axis; it is a precondition the `[t3]` walk
  verifies. if false, every rds cell falls to the `moved` outcome, and the fallback is a range key `pg-pool@^3`.
- patch failure mode: the pnpm practice ships `pnpm.ignorePatchFailures: true`, so a hunk that does not fit warns and
  never halts, in every cell.

total: 28 adopter + 8 maintainer = 36 rows, each verdicted in `1.vision.experience.case=_.md`.
