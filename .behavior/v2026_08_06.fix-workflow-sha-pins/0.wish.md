# wish: fix(workflows) — the declared practice must emit SHA-pinned action refs

> the ground is `ehmpathy/declastruct-github` at **v1.8.0**, released 2026-08-06. read its
> `provision/github.org/resources.ts` and its `.github/workflows/*`. that repo declared the org
> posture AND conformed itself to it, so it is both the cause of this wish and its worked example.

## .what

a repo scaffolded or upgraded from this template emits workflows whose every third-party action
ref is pinned to a **full-length commit SHA**, never a tag.

## .why

**this is live and it is already breaking repos.** on 2026-08-06 the ehmpathy org set
`sha_pinning_required: true`. that control is not advisory:

> GitHub fails when it looks the action up — **before any step executes**. a repo whose refs are
> not pinned does not fail a test. its CI never starts.

measured, not guessed. `declastruct-github`'s `suite / install / pnpm` job hard-failed at **9
seconds** with:

```
The action actions/checkout@v4 is not allowed in ehmpathy/declastruct-github
because all actions must be pinned to a full-length commit SHA
```

after its 48 refs were pinned, the same job passes at **58 seconds**.

**the blast radius is the org.** the audit taken before the control went live counted **91 repos
with workflows, 1,626 third-party action refs pinned by tag, and 0 pinned by SHA.** every one of
those repos will hard-fail its next CI run until it is pinned.

this template is the leverage point. the human's stated call was *"folks will update their repos
as they continue"* — which only works if the practice they upgrade to already emits pins.
otherwise each repo pays the cost by hand, 90 times, and a fresh scaffold ships broken on day
one.

## .acceptance — what proves it done

- a repo scaffolded from this template has CI that **starts** under the live org control
- a repo that runs the upgrade against this template comes away with its template-owned refs
  pinned, without a hand-edit
- the pin is legible: a reader can tell WHICH version each SHA corresponds to, so a later bump is
  not archaeology
- the practice's own CI passes under the control it declares — the template must not be exempt
  from the rule it teaches
- coverage per grain, per `rule.require.test-coverage-by-grain`

## .the constraints that genuinely bind

1. **a SHA is only as good as its provenance.** a pin invented from memory is worse than a tag —
   it is an unverifiable claim about upstream. every SHA must be derived from the upstream repo
   at author time, and be checkable by whoever reviews it.
2. **the template's reach ends at the refs it owns.** a consumer repo may carry workflows this
   template never wrote. do not silently rewrite what the practice does not own; the boundary
   between template-owned and consumer-owned refs is part of the outcome, not an afterthought.
3. **the control is already live.** you cannot ship this behind a flag and enable it later — the
   org enforces today, so a partial conformance still leaves consumers dead before their first
   step runs.

## .the tradeoff to RECORD, not to solve here

a hard SHA pin trades one hazard for another: it defeats a malicious upstream tag re-point, and
it freezes consumers on whatever commit was current, so a later upstream CVE fix does not reach
them. the party who found this named it plainly:

> *"a hard cut without automated pin bumps trades 'malicious update' for 'unpatched CVE'"*

— and unlike the pin itself, that second hazard does not cure itself as people touch repos.

**it is out of scope for this wish.** if an automated-bump path (renovate, dependabot, or
whatever the repo prefers) is genuinely cheap to land alongside, say so in your yield and let the
human decide. do NOT expand into it unasked.

## .out of scope

- the other 90 repos. this wish fixes the **practice**; conformance of consumers is downstream of
  it and is a separate dispatch.
- any change to `declastruct-github` or to the org posture itself. the control is settled.

## .the HOW is yours — advisory only

per `rule.require.wish-outcome-over-proposal`, `.what` / `.why` / `.acceptance` above are
authoritative. all else is ground, not instruction.

`declastruct-github@v1.8.0` pinned 48 refs and its CI now passes — that is **evidence the outcome
is reachable**, and a repo whose shape you may study. it is NOT a spec to transcribe, and its
approach was chosen for a single repo rather than for a template that many repos inherit. those
are different problems, and the second is yours to settle in-repo.

if you deliver the acceptance criteria with a shape neither i nor that repo imagined, that is a
success. say why in your yield.
