dream =

# swap jest for a more modern test runner — one that makes expo a MINOR DEVIATION, not a fork

## .what

move the whole test-practice family off jest onto a more modern runner (e.g. vitest), for BOTH
runtimes — the `-node` config AND the `-expo` config — together. the north star: pick a runner whose
react-native/expo story is good enough that expo becomes a **minor usecase-aware deviation of one
shared config, NOT a separate forked practice**. the `-any` common half (deps +
`test:unit`/`test:integration`/`test:acceptance` commands) migrates with them.

## .why

- jest's config surface is heavy, and the toolchain around it (babel, `@swc/jest`, jest-expo preset)
  is what forces the runtime fork today. a runner with native esbuild/swc-class transforms + native
  TS + esm could shrink or reshape that delta.
- **the real prize is fork elimination.** under jest the split is a JUSTIFIED fork; the dream is a
  runner where it is NOT — where node and expo share one config and expo only appends a small
  react-native environment/resolution branch, gated on `context.projectPractices` per
  `rule.avoid.runtime-forks`. that collapses the `tests-node`/`tests-expo` fork back to a single
  usecase-aware `tests` practice (retiring the triad, or shrinking it to `tests-any` + one aware
  config).
- faster cold start + watch on the pure-logic (`domain.operations`/`domain.objects`) glob, where the
  node repos spend most test time.

## .the catch — why this is a dream, not a task

the `2026-08-11` design round settled that under jest the `tests-node`/`tests-expo` split is a
JUSTIFIED fork: it is forced by `jest-expo` as a whole PRESET (babel-preset-expo transform + RN
module resolution + RN test env + the `.pnpm/`-nested ESM `transformIgnorePatterns`), NOT by the
transformer choice. swc alone cannot load a test that reaches the expo/react-native boundary.

so the load-bearing question a modern runner must answer FIRST — and the one that decides whether the
"minor deviation, not a fork" dream is reachable:
- does vitest (or the chosen runner) have a first-class react-native / expo story? jest-expo is the
  paved path today; a runner without an equivalent RN preset would REGRESS expo component tests, and
  the fork stays.
- if the runner needs no babel-preset-expo equivalent, does the node↔expo delta shrink to only the RN
  environment + module-resolution (platform suffixes, haste)? if yes, that is small enough to be one
  usecase-aware config branch — the dream's whole point. if no, the fork is still justified and the
  dream does not wake yet.
- migration cost: every `*.test.ts` assertion api (jest globals, `toMatchSnapshot`, `test-fns`
  wrappers) + every `.snap` format would need to survive or convert. the `test-fns` bdd utils
  (`given`/`when`/`then`/`useThen`) must have a runner-agnostic or ported form.

## .scope when it wakes

- the three practices: `tests-any` (deps + commands), `tests-node` (transform/env), `tests-expo`
  (preset/env). the aspiration is to end with `tests-any` + ONE usecase-aware `tests` config, not a
  three-way fork.
- the node consumers AND the expo consumers (`app-hometools-native`, `app-protools-native`) inherit
  via `declapract fix`, so the migration must be a graceful bad-practice (findsert/convert the config,
  forget the old jest config only once the new one lands) with idempotency + integration tests, same
  discipline the fix-expo migration used.
- verify the RN story before committing — it is the load-bearing unknown that gates the fork-vs-aware
  outcome.
