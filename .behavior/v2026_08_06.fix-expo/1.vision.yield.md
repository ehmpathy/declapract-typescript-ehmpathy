# vision — fix-expo

illustrates the world implied by `.behavior/v2026_08_06.fix-expo/0.wish.md`.

---

## the outcome world

### day-in-the-life

**before.** a fresh expo app repo wants pnpm. an engineer opens `app-hometools-native`'s git
history, finds PR #55, and hand-copies it piece by piece: the `.npmrc` hoist block, the
`packageManager` pin, the `.deploy-expo.yml` pnpm steps, the `package-lock.json` deletion — then
chases the transitive version skew the flat linker exposes. repo by repo, and the lesson survives
only in that one repo's history. the next expo repo pays the tax again.

**after.** the same engineer runs `declapract fix`. the `app-react-native-expo` usecase already
carries `pnpm-expo`, `rhachet`, `cache`, `errors`, `domain`, and `directory-structure-src`. one fix
lands the whole shape — the hoist `.npmrc`, the `packageManager` pin, the pnpm workflows, the
rhachet `.agent/`, a converged `.gitignore`, the `domain-objects` deps — and migrates the repo's
extant files gracefully: it renames `src/logic/` → `src/domain.operations/`, forgets
`package-lock.json` only once `pnpm-lock.yaml` is in place, and merges into the repo's own expo
`tsconfig.json` rather than clobber it. zero hand edits.

### before / after contrast

| dimension | before | after |
|-----------|--------|-------|
| expo repo baseline | a thin hand-built usecase that dropped rhachet/pnpm/cache/errors/domain | parity with node repos, shaped for metro where it must be |
| a new pnpm adoption | hand-port of PR #55, file by file, per repo | `declapract fix`, one command, every repo |
| where the lesson lives | one repo's git history | the practice, inherited by every consumer |
| runtime variance | ad-hoc, re-derived each time | one usecase-aware practice, or (last resort) an `-any`/`-node`/`-expo` triad |

### the aha

the value clicks when `app-protools-native` runs `declapract fix` and its whole pnpm-for-expo shape
appears — the exact shape `app-hometools-native` hand-wrote commit by commit in PR #55 — with no
engineer ever reading that PR. the app repos stay thin; the practice carries the knowledge. and the design
discipline (the build-vs-domain axis, the fork-as-last-resort rule) means the practice library does
NOT drown in `-node`/`-expo` copies: most practices stay single and usecase-aware.

## user experience

### who, and what goal

- **the consumer** — an expo app repo (`app-hometools-native`, `app-protools-native`). goal: "give
  my repo the org platform baseline with one command, without a break to metro."
- **the maintainer** — us, in this declapract repo. goal: "encode a runtime difference once, at the
  least surface (usecase-aware over a fork)."

### the contract they leverage

- **input** — `declapract.use.yml` declares `usecase: app-react-native-expo` + the repo's variables.
- **process** — `declapract fix` reads the usecase, composes its practices, runs each practice's
  `check` (gate) and `fix` (migration).
- **output** — the repo's files converge to the practice shape, gracefully migrated (findsert,
  forget-not-destroy, dir-rename), never clobbered.

### what it looks like to leverage

- consumer: `declapract fix` in plan mode → review the diff → apply → commit → CI green.
- maintainer: author a practice with a usecase-aware `contents` fn keyed on
  `context.projectPractices`; only when that is untenable, author the `<x>-any` + `<x>-node` +
  `<x>-expo` triad (`rule.avoid.runtime-forks`, `rule.require.variant-family-triad`).

### timelines

- **consumer**: upgrade the `declapract-typescript-ehmpathy` dep → `declapract fix` (plan) → review →
  apply → commit → watch CI.
- **maintainer**: audit the runtime delta → decide the axis (usecase-aware vs fork) → author the
  practice + its idempotency and integration tests → release → consumers inherit on next fix.

## mental model

- **how a user describes it to a friend**: "it's the org's repo baseline, but shaped for a mobile
  app instead of a backend service — one command sets up pnpm, the agent tools, the lint, the
  domain conventions."
- **analogy**: a usecase is a recipe; practices are ingredients; `-any`/`-node`/`-expo` are the same
  ingredient in different cuts. you reach for a different cut only when the dish demands it.
- **the load-bearing distinction**: how a repo **builds / bundles / runs** differs by runtime (metro
  and EAS replace tsc and node-jest); how a repo **organizes its domain** does not (`domain.objects`
  ← `domain.operations` ← `access` ← `contract` holds for any app with logic).
- **terms we use vs they use**: we say *practice*, *usecase*, *declarer*, *convergence*, *fork*,
  *triad*, *usecase-aware*. they say "the pnpm setup", "the tsconfig", "the expo template".

net: the load-bearing requirements HOLD; three are genuinely OPEN for the wisher (fork verdicts,
`EXISTS` severity, auto-migration), and one requirement (the hoist) is held on a to-verify assumption.

### how well it solves the goals

(this is a vision of the built state, not a delivered one — the verbs below are the intended
outcome, not a claim of done.)

- **parity** — WOULD be met: the expo usecase gains the platform practices node repos already have.
- **knowledge-in-practice** — WOULD be met: PR #55's lesson becomes a template, not tribal history.
- **graceful migration** — the plan MANDATES it: every fix must be findsert / forget-not-destroy /
  dir-rename, each with an idempotency + integration test against a real clone (required, NOT yet
  built).
- **fork discipline** — backed by the two authored rules (`rule.avoid.runtime-forks`,
  `rule.require.variant-family-triad`, written this round): a fork is the earned exception, and a
  forced fork takes one canonical shape.

**a requirement still open, NOT a solved goal:** the fork-candidate carry
(`pnpm`/`typescript`/`tests`) is a CANDIDATE set, not a settled one — each still owes a "can one
usecase-aware practice serve both?" spike, and that verdict is the wisher's to confirm, not a
vision's to decide. likewise the `domain` / `directory-structure-src` `EXISTS` mandates: the
conventions hold (wisher-endorsed), but their SEVERITY for the expo usecase (blocker vs advisory) is
unsettled. the vision does not claim these as met — it names them in "questions for the wisher"
below so the open requirement is visible rather than silently resolved.

### pros

- app repos stay thin; one source of truth for the platform.
- minimal fork surface — the default is one usecase-aware practice.
- the `-any`/`-node`/`-expo` triad forecloses the unmarked-default drift the domain-terms lesson
  warns of.

### cons

- **migration weight** — `app-protools-native` has 72 files under the deprecated `src/logic/` +
  `src/data/` layers; an auto-migration that renames them and rewrites imports is powerful but has a
  real blast radius.
- **a prerequisite step (owned by the app team, per wisher 2026-08-06)** — `app-protools-native` is
  pinned to old declapract (`0.36.1`); the "one fix" story has a declapract upgrade in front of it.
  the wisher scoped that upgrade OUT of this wish — the app team runs it on their schedule — so it is
  no longer this wish's critical-path con, only a note on the downstream adoption sequence.
- **jest dual-source** — its jest lives in two places at once (a `jest-expo` preset inline in
  package.json AND a jsdom `jest.unit.config.js`); a `tests` practice must reconcile, not overwrite.
- **the axis is a judgment call** — `typescript` straddles it (typecheck is domain-agnostic, the
  `tsc` build is runtime-bound), so the split runs THROUGH a practice, not cleanly between practices.

### edge cases + the pit of success

- **clobber of a good file** — the expo `tsconfig.json` is already correct and customized; the pit
  of success is a CONTAINS/merge check, never EQUALS, so a fix cannot destroy the repo's own work.
- **a half-done lockfile swap** — forget-not-destroy: `package-lock.json` is removed ONLY after
  `pnpm-lock.yaml` exists, so a fix interrupted midway never leaves the repo lockfile-less.
- **gitignore drift** — with `rhachet` in, the expo `.gitignore` becomes a 3-declarer file (`git`,
  `cicd-app-react-native-expo`, `rhachet`; the `cache` practice declares a package, NOT the
  gitignore — verified: `src/practices/cache/best-practice/` holds only a `package.json`). they
  route through the one shared algorithm, so they SHOULD converge — but a cross-declarer clamp for
  this 3-declarer case is UNconfirmed (see the open questions + the #537 lesson).
- **a greenfield expo app** — an app with no domain yet meets `domain`'s `EXISTS` mandate; the pit of
  success is to relax that check for the expo usecase rather than block a fix on an unearned file.

## open questions & assumptions

### assumptions made

1. **pnpm's hoisted linker is REQUIRED for expo/metro native module lookup.** evidence is
   second-hand: `app-hometools-native` PR #55 shipped `node-linker=hoisted` + the
   expo/metro/react-native `public-hoist-pattern[]`, with commit rationale that the default
   symlinked store breaks native-module lookup. a real repo proved it in prod — but it is NOT yet
   checked against the official expo/pnpm docs. flagged for a doc check before build.
   **this is the load-bearing requirement — the FIRST thing the build spike must verify, ahead of any
   practice code.** every downstream deliverable (the `.npmrc` lift, the `pnpm-expo` split, the whole
   "one fix delivers the pnpm shape" story) is built ON this assumption. if a newer pnpm/metro
   resolves native lookup without the hoist, the headline `.npmrc` template is unneeded. so the doc
   check is not a nicety at the tail — it gates the design and runs first.
2. **every `app-react-native-expo` consumer wants the domain + directory-structure conventions.**
   true for a repo with logic; an app that is pure UI could find the `EXISTS` mandates premature.
3. **declapract's CONTAINS / EXISTS semantics on glob declarations behave as described** — validated
   against extant practice code, but the glob+EXISTS case deserves a direct pipeline test.
4. **the two reference-repo facts are agent-gathered, not read first-hand.** the
   `app-hometools-native` PR #55 specifics and the whole `app-protools-native` audit came from
   sub-agent `git.repo.get` / `gh` runs, not from the author's own read of those repos. the agents
   read the live repos, so the evidence is real — but re-verify the load-bearing items (the pnpm
   requirement, the 72-file dir layout, the declapract `0.36.1` pin) directly at build, since they
   gate the migration design.

### open questions — triaged

each question tagged `[answered]` (settled now via logic/code), `[research]` (settled by a build
spike or doc check), or `[wisher]` (only the wisher can decide).

- **[answered — wisher, 2026-08-06]** do we upgrade `app-protools-native`'s declapract pin as part of
  this wish? — NO. the app team handles their own upgrade. the declapract-pin bump is a prerequisite
  the app repo OWNS, OUT of this wish's scope. this wish delivers the practices; the app team runs
  the upgrade + `declapract fix` on their schedule. (removes the "hidden first step" con from this
  wish's critical path — it is the app team's step, not ours.)
- **[answered — wisher, 2026-08-06]** the 72-file `logic/`+`data/` migration — auto-fix or guided
  manual? — AUTO-FIX. always autofix. the `directory-structure-src` fix renames `logic/` ->
  `domain.operations/` + `data/` -> `access/`/`domain.objects/` and rewrites imports, driven by the
  practice. the blast radius is real, so the guardrails carry the weight: each migration is an
  idempotent + integration-tested fix (`rule.require.idempotent-fixes`,
  `rule.require.declapract-integration-tests`) proven against a clone of the app's actual layout, and
  plan-mode preview + a review of the diff precede apply. the payoff (one command, zero hand edits)
  is the point of the lift — a guided manual move would forfeit it.
- **[research]** the fork-candidate verdicts: does each of `pnpm` / `typescript` / `tests` stay one
  usecase-aware practice, or earn a triad? — answerable by a small build spike per practice ("can one
  usecase-aware `contents` fn serve both runtimes?"), not by opinion.
- **[research — moot for policy]** what does glob+`EXISTS` do on a ZERO-match target? — a pipeline
  test settles the mechanism (blocks vs passes vacuously, assumptions #3). but the wisher's
  "every app has a domain" ruling makes it moot for POLICY: a conformant expo repo is never a true
  zero-match, so the severity is a blocker regardless of the glob behavior. the test is still worth
  a run for engineer confidence, but no design decision waits on it.
- **[answered — wisher, 2026-08-06]** given that behavior, should `domain` +
  `directory-structure-src`'s `EXISTS` mandates be a BLOCKER or advisory for the expo usecase? —
  BLOCKER, as-is. the "greenfield or UI-only app has no domain" premise is REJECTED: even apps have
  domain.objects and domain.operations — that is unavoidable. a UI app still holds its own domain
  (the objects it renders, the operations it performs) and talks to sdks via `access`. so the
  `EXISTS` mandate is earned for every expo repo, and stays a blocker like the node usecases — no
  expo-specific severity relaxation. (this also SETTLES the glob+`EXISTS` zero-match research question
  as moot for policy: a conformant expo repo is never a true zero-match, because it always has a
  domain to declare.)
- **[answered — wisher, 2026-08-06]** is the 72-file `logic/`+`data/` live-app migration bound-able
  as its own slice if the single pass proves unwieldy? — NO. do it ALL, in one pass. no separate
  slice, no deferral of the risky piece. the full carry stands: the as-is includes, the fork-candidate
  practices, the pnpm-for-expo lift, AND the 72-file migration ship together. the blast radius is
  managed by the guardrails (idempotent + integration-tested fixes, plan-preview before apply), not by
  a scope split.
- **[answered]** do the cheap as-is includes (`cache`, `errors`) risk a target repo? — no. read the
  code: `cache` declares only `.ifInstalled()` version-floors (forces no dep), `errors` declares only
  `helpful-errors` via CONTAINS. both are harmless no-ops for a repo that does not use them.
- **[answered]** does the fix wire in via `extends: [typescript-project]` or by INLINE additions to
  the expo usecase? — inline. VERIFIED against `src/useCases.yml`: `extends` IS supported (npm-package
  `:24`, lambda-service `:31` both `extends: [typescript-project]` + add their own), but it is
  ALL-OR-NONE — it would pull EVERY typescript-project practice (`:3-22`), among them `bottleneck`
  (a runtime lib the wish explicitly excludes) and the node-shaped `typescript`/`tests` builds the
  axis forbids wholesale. declapract has no "extends-minus-X". the expo usecase already lists its
  practices inline (`:62-77`, no `extends`), so the fix adds the selected practices directly there.
- **[research]** does the expo usecase already pull a node-shaped practice that fights expo TODAY? —
  a candidate surfaced: `app-react-native-expo` includes the `node` practice (`src/useCases.yml:70`).
  the wish's part-0 audit asks "what does the current usecase get WRONG, not just what it lacks" — the
  `node` practice is the first suspect (does it pin a node runtime/engines an expo app should not
  carry?). a code read of `src/practices/node/best-practice/` settles whether it stays, forks, or
  drops for expo.

### what to validate externally

- **[research]** check the pnpm + expo hoisted-linker requirement against the official expo and pnpm
  docs — the one external dependency the vision rests on, and the FIRST item the build spike verifies.

## what is awkward

- **the axis cuts through a practice, not between practices.** `typescript` is half domain-agnostic
  (the `tsc --noEmit` typecheck) and half runtime-bound (the `tsc` + `tsc-alias` build). so "is this
  a fork?" has no clean per-practice answer — the split runs inside it, which is exactly the case
  `rule.avoid.runtime-forks` says to handle with a usecase-aware `contents` fn, not a fork. still,
  it feels less tidy than the clean includes.
- **the `domain` EXISTS mandate feels forced on a greenfield app.** it demands
  `src/domain/objects/index.ts` exists — reasonable for a repo with a domain, but on a brand-new
  expo app it fires as a blocker for a file the app has not earned yet.
- **the 72-file auto-migration is powerful and scary at once.** a `directory-structure-src` fix that
  renames `logic/`/`data/` and rewrites every import is the graceful ideal — but a wrong rewrite
  breaks the app, so the tradeoff between full automation and blast radius is genuinely uncomfortable.
- **the "one fix" story's first step is a KNOWN prerequisite, not a hidden gotcha.** yes,
  `app-protools-native` on declapract `0.36.1` upgrades the practices dep before any of this applies —
  but "bump the dep, then `declapract fix`" is the standard, well-understood flow every declapract
  consumer already follows. it is clear to all consumers; it does not surprise anyone. (and per the
  wisher, the app team owns that upgrade — it is not this wish's step.) so this is not actually
  awkward; recorded here only to note the sequence, not as a wart.
- **the two reference repos are easy to confuse** — `app-hometools-native` (the source of the
  lesson) vs `app-protools-native` (the target of the migration). a reader one letter off reads the
  wrong repo.
- **the lift is NOT premature — more than two expo repos exist (wisher, 2026-08-06).**
  `rule.prefer.wet-over-dry`'s rule-of-three says abstract at the 3rd instance; the wisher confirms the
  expo-repo count is past two, so the lift clears the rule-of-three threshold outright. the
  abstraction is neither speculative nor at a boundary: the repos NEED the identical `.npmrc` hoist
  shape (proven, not predicted), and a shared template that multiple repos already demand is
  discovered, not invented. even the marginal parity adds (cache/errors) now serve a real set, so
  their DRY payoff is earned, not thin. the earlier rule-of-two tension is resolved.
