# 🌙 dream: retire the shipped pg-pool patch once pg-pool drops the fallback upstream

- kind: followup
- owner: declapract-typescript-ehmpathy, practice persist-with-rds
- caught 2026-10-24

## .the cue that fired

a peer review (enroll-impl-arch-defects, i004) noted the bare-name key has no off-ramp: `asPatchTarget` returns
`version: null` for it, so `stale-patched-dependency` never retires it, by design.

## .the gap, precisely

if pg-pool ever drops `|| require('pg').Client` itself, the shipped hunk no longer fits. pnpm then warns on every
install in every adopter (`ignorePatchFailures` keeps it a warn), with no cycle left to cure. declapract cannot
delete a file it no longer ships, so an adopter keeps both the key and `patches/pg-pool.patch` forever.

## .the shape of the fix

- at that point, drop the key and the file from `persist-with-rds/best-practice/`
- add a bad practice `persist-with-rds/bad-practices/obsolete-pg-pool-patch/` that detects
  `pnpm.patchedDependencies["pg-pool"] === "patches/pg-pool.patch"` and a lockfile pg-pool past the fix release,
  and fixes by removal of the key and the file
- its integration test: a fixture repo on the fixed pg-pool, apply, assert both gone and other keys kept

## .why it is not done in this round

no upstream release drops the fallback today (every release 3.2.1–3.14.0 holds it), so the trigger version is
unknown. a bad practice built now would key on a guess.
